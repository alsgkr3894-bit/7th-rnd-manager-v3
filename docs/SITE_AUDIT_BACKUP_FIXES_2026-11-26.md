## 2. 구현

### 2-1. 백업 파일 형식 (`7df5ee56`)

- `lib/backup/file-format.js`: gzip으로 압축한 줄 단위 JSON. 머리 줄, 저장소 머리 줄, 레코드 한 줄씩, 끝 줄. 전체를 문자열 하나로 만들거나 읽지 않는다.
- 끝 줄과 행 수를 대조해 잘리거나 저장이 끝나지 않은 파일을 거부한다. 압축을 푼 크기 3GB, 한 줄 64MB 상한.
- 백업 다운로드, 복원 직전 자동 백업, 브랜드 백업이 `.gz`로 바뀌었다. **예전 `.json` 백업은 그대로 복원된다.**
- `npm run db:import:backup`과 업무 흐름 QA 시나리오도 같은 읽기를 쓴다.
- 문자 수 약 5.8억 자의 시험 데이터는 예전 방식에서 `Invalid string length`로 실패했고 새 형식은 만들고 읽었다.

### 2-2. 화면 설정 서버 보관

- `app/api/db/settings`: 로컬 요청·로그인 검사를 거치며, 허용 목록의 설정 키만 받는다. 검증용 샌드박스는 쓰기를 거부한다.
- 대상은 백업에 담던 영속 설정(정렬, 표시 순서, 임계값, 핀, 브랜드 목록, 프로필 등)이다. **계정 선택, 로그인 인증값, 초안, 외부 로그인정보, 법인카드는 올리지 않는다.**
- 올리기: 운영 PC 브라우저가 앱을 연 뒤, 1분마다, 창을 벗어날 때, 서버 백업을 만들기 직전에 바뀐 설정만 올린다.
- 덮어쓰기 방지: 처음 올리는 브라우저는 서버에 **없는** 설정만 올린다. 서버에서 불러오기 전의 빈 브라우저는 올리지 않는다.
- 받기: "서버에서 불러오기"가 설정을 적용한다. 계정 선택은 바꾸지 않고 브랜드 목록은 합친다.
- 2026-09-15에 백업에서 한 번 가져온 낡은 설정 행은 돌려주지 않는다.
- 백업 화면에 "DB 백업에는 외부 로그인정보·법인카드와 로그인 인증 파일이 없다"는 안내를 넣었다. `db:restore:verify`도 설정 건수와 빠진 항목을 출력한다.
- 로그인 인증 파일은 백업하지 않는다. 새로 설정하는 절차를 [RECOVERY.md](RECOVERY.md)에 적었다.

**적용 시점 참고:** 켜 두었던 개발 서버(3000)가 새 코드를 바로 반영해, 2026-11-26 10:50에 운영 브라우저의 설정 36건이 운영 DB(`local_storage_entries`)에 저장됐다. 같은 키의 낡은 가져오기 값을 현재 값으로 갱신했다.

### 2-3. 복원 중단 지연 (`6fb3925b`)

- 원인(재현 확인): 모든 쓰기 요청을 한꺼번에 대기열에 넣으면, 페이지가 닫혀도 브라우저가 대기열을 끝까지 처리한 뒤에 트랜잭션을 취소한다.
- 시험 페이지 15만 행: 중단 뒤 읽기까지 **32.9초 → 0.19초**, 전체 쓰기 시간은 35초로 같다.
- `lib/db/backup.js`는 500건씩, 앞 묶음이 끝난 뒤 이어 넣는다. 같은 트랜잭션이라 전부 적용되거나 전부 취소된다.

## 4. 남은 한계

- **압축 파일에도 500MB 업로드 한도가 있다.** 현재 220MB이며 지금 증가 속도라면 반년 이상 여유가 있다고 추정한다. 용량의 대부분은 사진이므로 근본 해결은 사진을 별도 저장으로 분리하는 일(점검 문서 4단계)이다.
- 백업을 만들고 복원할 때 전체 데이터가 여전히 메모리에 올라간다.
- 백업 파일은 암호화하지 않는다. 외부 로그인정보가 들어 있으므로 보관 장소에 주의한다.
- 외부 로그인정보·법인카드는 DB 자동 백업에 없다. 브라우저 백업을 직접 받아 확인해야 한다.
- 설정은 최대 1분 늦게 서버에 반영된다.
- 중단 시험은 데이터가 없는 새 프로필에서 했다.
- 백업은 여전히 원본과 같은 디스크에 있다.
