# 편의성·추가 기능 개선 로드맵

기준일: 2026-06-22

## 최종 실행 요약

이 문서는 사이트에 추가할 만한 편의 기능과 후속 기능을 Claude Code가 단계별로 구현하고 Codex가 검수하기 위한 실행 플랜이다. 아래 순서를 이번 로드맵의 기준 순서로 사용한다. 뒤쪽의 상세 섹션은 각 단계별 요구사항과 검수 기준으로 참고한다.

진행 원칙:

1. 한 번에 여러 기능을 섞지 않는다.
2. 각 단계는 `구현 → 테스트/검사 → 화면 확인 → Codex 검수 → Claude 보완 → Codex 최종 검수 → 커밋` 순서로 닫는다.
3. 기존 미커밋 변경은 되돌리지 않고, 기능별로 충돌 범위를 먼저 확인한다.
4. 사용자 데이터 삭제, 대량 복원, 되돌리기, 일괄 변경 기능은 관리자 권한과 확인 절차 없이는 진행하지 않는다.
5. 외부 서비스 연동과 서버 DB 전환은 이 문서 범위에서 제외한다.

| 순서 | 단계 | 목표 | 핵심 작업 | 완료 기준 |
|---:|---|---|---|---|
| 0 | 기준선 고정 | 현재 작업트리와 테스트 상태를 확정 | `git status`, 관련 테스트 수치, 미완료 변경 확인 | 충돌 위험과 작업 범위가 문서화됨 |
| 1 | 구현 흔적 감사 | 이미 들어온 편의 기능 토대를 살릴지 판단 | action-center, readiness, impact, saved-view, monthly-close, change-log 사용처 확인 | 각 기능이 `보완/부분구현/보류`로 분류됨 |
| 2 | 커맨드 팔레트 상세 이동 | 검색 후 바로 수정 위치로 이동 | 식자재/메뉴 검색 결과에 query, highlight, productCode 연결 | 잘못된 URL fallback, 행 하이라이트, targeted test 통과 |
| 3 | 메뉴 출시 체크리스트 | 메뉴 출시 전 누락 방지 | 레시피, 가격, 원산지, 알레르기, 영양성분, 출력 가능 여부 진단 | L/R, 단일, 1인피자, 사이드, 소스, 음료, 엣지 기준이 분리됨 |

| 5 | 업무 액션 센터 | 오늘 처리할 일을 한곳에 모음 | 홈 위젯, 상단 알림, 진단 항목을 같은 builder로 통합 | 원인 해결 시 액션 자동 제거, 숨김/나중에 상태 안전 |
| 6 | 저장된 필터·뷰 | 반복 필터 설정 감소 | 식자재관리 이후 원가마진표, 판매량, 보고서에 단계 적용 | 브랜드별 분리, 손상 localStorage fallback 통과 |
| 7 | 메뉴·레시피 빠른 입력 | 메뉴마스터 입력 시간 감소 | 키보드 이동, 행 복사, 규격 드롭다운, 저장 전 경고 정리 | 메뉴 저장과 레시피 저장 흐름 회귀 없음 |
| 8 | 데이터 품질 점검판 | 누락, 중복, 이상값을 한 화면에서 확인 | readiness, impact, action 진단 로직을 품질 리포트로 묶음 | 빈 DB, 브랜드 전환, 중복 데이터에서 깨지지 않음 |
| 9 | 월마감·보고 패키지 | 반복 보고 업무 감소 | 기준월 체크리스트, 출력물 이동, 생성 기록 정리 | 실제 생성 파일과 기록 상태가 일치 |
| 10 | 모바일·현장 확인 모드 | 매장 현장에서 빠르게 확인 | 원산지, 알레르기, 영양성분, 가격 확인 전용 흐름 | 390px 화면에서 3터치 이내 핵심 정보 접근 |
| 11 | 변경 이력·되돌리기 센터 | 대량 작업 불안감 감소 | 1차는 기록 전용, undo는 정책 확정 후 별도 진행 | viewer 제한, 관리자 확인, 백업 안내가 명확 |

이번 1차 작업 추천 범위:

1. 0단계 기준선 고정.
2. 1단계 구현 흔적 감사.
3. 2단계 커맨드 팔레트 상세 이동.
4. 3단계 메뉴 출시 체크리스트 기준 검증.
5. 4단계 변경 영향도 미리보기 검증.

1차 범위가 끝나면 P1 업무 액션 센터와 P9 데이터 품질 점검판을 묶어 진행하는 것이 좋다. 두 기능은 같은 진단 데이터를 공유할 수 있어 중복 구현을 줄일 수 있다.

## 0. 빠른 실행 플랜

이 문서는 편의성·추가 기능 후보를 한 번에 크게 구현하기 위한 문서가 아니다. 현재 작업트리에 이미 들어와 있는 토대 파일을 먼저 살리고, 사용자가 바로 체감할 수 있는 기능부터 작은 단계로 마감하기 위한 실행 계획이다.

이번 작업의 기본 진행 방식:

1. Claude Code가 1차 구현 또는 보완을 진행한다.
2. Codex가 코드, 테스트, 화면 동작, 문서 반영 여부를 검수한다.
3. Claude Code가 Codex 지적사항만 좁게 수정한다.
4. Codex가 최종 검수 후 `승인 / 조건부 승인 / 수정 필요 / 검증 불가`로 판정한다.
5. 한 단계가 green일 때만 커밋하고 다음 단계로 넘어간다.

우선 실행 순서:

| 순서 | 단계 | 핵심 목표 | 이유 |
|---:|---|---|---|
| 0 | 기준선 확인 | 미커밋 변경, 테스트 수치, 충돌 파일 확인 | 현재 작업트리가 넓게 변경되어 있어 되돌림과 중복 구현을 막아야 한다 |
| 1 | 구현 흔적 감사 | 이미 있는 action/readiness/impact/saved-view/change-log 파일을 기능별로 판정 | 새로 만들기보다 살릴 수 있는 코드를 먼저 확인한다 |
| 2 | P4 커맨드 팔레트 상세 이동 | 검색 결과에서 식자재/메뉴의 실제 행 또는 수정 위치로 이동 | 작고 체감이 빠르며 회귀 위험이 낮다 |
| 3 | P2 신메뉴 출시 체크리스트 | 메뉴 출시 전 누락 데이터와 수정 위치를 한 화면에 표시 | 메뉴마스터 입력 실수를 줄이는 핵심 기능이다 |
| 4 | P3 변경 영향도 미리보기 | 식자재 단가·원산지·알레르기 변경 전 영향 메뉴와 출력물을 표시 | 저장 전 실수와 출력 회귀를 줄인다 |
| 5 | P1 업무 액션 센터 | 홈/상단 알림/진단 항목을 하나의 업무 큐로 통합 | 여러 화면에 흩어진 조치 필요 항목을 한곳에 모은다 |
| 6 | P6 저장된 필터·뷰 | 자주 쓰는 필터 조합 저장·적용·기본값 지정 | 반복 업무 클릭 수를 줄인다 |
| 7 | P8 메뉴·레시피 빠른 입력 | 키보드 입력, 행 복사, 규격 드롭다운, 저장 전 경고 개선 | 메뉴마스터 입력 속도와 정확도를 높인다 |
| 8 | P9 데이터 품질 점검판 | 전체 누락·중복·이상값을 한 화면에 진단 | 운영 데이터 신뢰도를 빠르게 판단하게 한다 |
| 9 | P5 월마감·보고 패키지 | 월별 출력 체크리스트와 생성 기록 정리 | 반복 보고 업무를 줄인다 |
| 10 | P10 모바일·현장 확인 모드 | 원산지·알레르기·영양성분·가격 확인을 모바일에 최적화 | 현장에서 빠른 확인이 가능해진다 |
| 11 | P7 변경 이력·되돌리기 센터 | 1차는 기록 전용, undo는 별도 정책 확정 후 진행 | 데이터 복구 책임이 커서 마지막에 다룬다 |

이번 사이클의 권장 범위는 0~4단계까지다. P1 이후는 여러 도메인 데이터를 묶으므로 P2/P3 기준이 안정된 뒤 진행하는 것이 안전하다.

## 1. 목적

현재 사이트는 메뉴마스터, 식자재, 원가, 영양성분, 판매량, 제때, 보고서, 노트 기능이 이미 넓게 구현되어 있다. 다음 개선은 새 화면을 무작정 늘리는 것보다 **흩어진 업무 흐름을 이어주고, 반복 작업을 줄이고, 실수 가능성을 낮추는 방향**이 가장 효과적이다.

이 문서는 Claude Code가 단계별로 구현하고 Codex가 검수할 수 있도록 편의성 개선 후보를 실행 계획으로 정리한 것이다.

## 2. 현재 전제

- 데이터는 현재 IndexedDB와 일부 localStorage를 기준으로 동작한다.
- 외부 서비스 연동은 이번 로드맵 범위에서 제외한다.
- 서버 DB 전환은 `LOCAL_DB_DEPLOY_PLAN.md`의 별도 장기 프로젝트로 본다.
- 기존 기능인 커맨드 팔레트, 홈 위젯, 알림, 헬스체크, 백업/복원, QA 스크립트는 최대한 재사용한다.
- 파괴적 작업이나 데이터 대량 변경은 관리자 권한, 미리보기, 확인 절차, 백업 안내를 반드시 둔다.

### 2.1 현재 코드 상태에서 먼저 확인할 점

현재 코드베이스에는 아래 기능의 토대 파일이 이미 존재하거나 작업 중인 흔적이 있다. Claude Code는 신규 구현으로 덮어쓰기 전에 반드시 `git status --short`, `rg`, 관련 화면 동작을 확인하고, **부분 구현을 살릴지 / 보완할지 / 폐기할지**를 먼저 판단해야 한다.

- 업무 액션 센터: `components/action-center/`, `lib/action-center/`, `components/home/ActionCenterWidget.jsx`
- 신메뉴 출시 체크리스트: `components/menu-master/MenuReadinessPanel.jsx`, `lib/menu-master/readiness.js`
- 변경 영향도 미리보기: `components/impact/`, `lib/impact/`
- 저장된 필터·뷰: `components/ui/SavedViewSelector.jsx`, `lib/saved-views.js`
- 월마감 패키지: `components/report/MonthlyClosePackageModal.jsx`, `lib/report/package-plan.js`
- 변경 이력: `components/change-log/`, `lib/change-log/`

검토 원칙:

1. 이미 구현된 기능은 같은 이름의 새 구조로 다시 만들지 않는다.
2. 기능이 동작하지만 테스트나 UX가 부족하면 보완 작업으로 분류한다.
3. 기능이 깨져 있거나 데이터 위험이 있으면 우선 수정 대상으로 분류한다.
4. 문서와 코드가 다르면 코드 동작을 기준으로 문서를 갱신한다.
5. 미커밋 변경이 많은 상태에서는 기능별 커밋 단위를 작게 유지한다.

### 2.2 최신 코드 판정 및 착수 방향

기준일: 2026-06-22

현재 작업트리 기준으로 편의 기능 후보 중 일부는 이미 코드 토대가 들어와 있다. 따라서 Claude Code의 다음 작업은 새 기능을 처음부터 만드는 것이 아니라, **이미 구현된 부분을 살리고 부족한 연결, 검증, 화면 확인을 채워 마감하는 방식**으로 진행한다.

### 2.4 Claude Code 1차 착수 플랜

아래 1차 범위만 먼저 진행한다. 한 번에 P1~P10 전체를 구현하지 않는다.

```md
# 작업: 편의성 개선 1차 마감

## 작업 목표
이미 작업트리에 들어온 편의 기능 토대를 살리면서, 가장 작은 체감 개선인 커맨드 팔레트 상세 이동을 마감하고 메뉴 출시 준비/영향도 기능의 기준을 검증한다.

## 1차 범위
1. 기준선 확인
   - `git status --short`
   - 현재 미커밋 변경은 되돌리지 않는다.
   - 관련 테스트가 이미 실패 중이면 구현 전에 원인과 범위를 보고한다.
2. P4 커맨드 팔레트 상세 이동 마감
   - 식자재 검색 결과 href에 `query`, `highlight`, 가능하면 `productCode`를 포함한다.
   - 식자재관리 화면은 URL 파라미터를 읽어 검색어 적용, 대상 행 페이지 이동, 스크롤, 2~3초 하이라이트를 처리한다.
   - 대상이 없거나 파라미터가 잘못되면 일반 목록으로 fallback한다.
   - 기존 `view`, `catFilter`, 저장된 뷰, 검색 필터 동작을 깨지 않는다.
3. P2 출시 준비 체크리스트 기준 검증
   - 현재 `readiness.js` 기준이 메뉴마스터 정책과 맞는지 확인한다.
   - 피자 L/R, 단일, 1인피자, 사이드, 소스, 음료, 엣지 기준이 섞이지 않는지 테스트한다.
   - 원산지/알레르기는 메뉴 단위, 원가/영양성분은 필요한 경우 사이즈 단위로 표시되는지 확인한다.
4. P3 영향도 미리보기 검증
   - 식자재 단가, 원산지, 알레르기 변경 영향 메뉴 수가 실제 레시피와 일치하는지 확인한다.
   - 저장 전 preview와 저장 후 결과가 달라지는 케이스가 있으면 수정 또는 보류 사유를 기록한다.

## 변경 금지
- 사용자 데이터 삭제, DB 초기화, 대량 복원 정책 변경 금지.
- 기존 메뉴 저장/레시피 저장/제때 업로드/백업복원 흐름을 깨지 않는다.
- 기능명이 실제 동작보다 과장되면 안 된다.

## 테스트
- 관련 targeted Jest 테스트 추가 또는 갱신.
- `npm run format:check`
- `npm run lint`
- `git diff --check`
- 화면 변경이 있으면 dev 서버에서 실제 URL 진입 확인.

## 완료 보고
변경 파일, 구현 내용, 실행 테스트, 수동 화면 확인, 남은 위험, Codex 검수 요청 항목을 보고한다.
```

### P0. 기준선과 충돌 방지

### P1. 업무 액션 센터

목표: 홈 위젯과 상단 알림에 흩어진 조치 필요 항목을 한곳에서 처리할 수 있게 만든다.

현재 문제:

- `TopBar` 알림은 미매칭/보고예정처럼 일부 항목만 표시한다.
- 홈에는 데이터 신선도, 헬스체크, 단가 없음, 원가율 경보, 백업 권장 등이 있지만 실제 작업 큐로 묶이지 않는다.
- 사용자는 “오늘 무엇부터 처리해야 하는지”를 여러 화면을 돌아다니며 확인해야 한다.

요구사항:

1. 액션 항목을 생성하는 순수 builder를 만든다.
   - 미매칭 메뉴
   - 보고예정 노트
   - 단가 없는 식자재
   - 원가율 경보 메뉴
   - 오래된 판매량/제때 단가/출고량 업로드
   - 백업 권장
   - 영양성분/원산지/알레르기 누락 진단 항목
2. 각 항목은 `id`, `source`, `title`, `desc`, `severity`, `href`, `createdAt`, `dueHint`를 가진다.
3. 사용자가 항목을 `완료`, `나중에`, `숨김 해제` 처리할 수 있게 한다.
4. 실제 원인 데이터가 해결되면 항목은 자동으로 사라져야 한다.
5. `완료`는 원인 해결이 아니라 사용자의 임시 처리 상태로 취급한다. 원인이 계속 남아 있으면 일정 시간이 지난 뒤 다시 표시한다.
6. 상단 알림 팝오버와 홈 위젯은 같은 action builder를 사용한다.

권장 구현:

- `lib/action-center/build.js`: 원천 데이터에서 action item 생성.
- `lib/action-center/state.js`: localStorage 기반 dismiss/snooze 상태 관리.
- `components/action-center/ActionCenterPanel.jsx`: 목록 UI.
- `components/topbar/NotificationPopover.jsx`: 기존 알림을 action item 기반으로 확장.
- 홈에는 작은 `오늘 할 일` 또는 `업무 액션` 위젯 추가.

테스트:

- builder 단위 테스트: 각 원인 데이터별 action 생성.
- dismiss/snooze 상태 테스트: 같은 source id가 일정 시간 숨겨지는지 확인.
- source 해결 시 local 상태가 남아 있어도 목록에서 제외되는지 확인.
- 브라우저 QA: 액션 클릭 시 정확한 화면으로 이동.

완료 기준:

- 사용자가 홈 또는 상단 알림에서 오늘 처리할 핵심 항목을 한 번에 볼 수 있다.
- 항목을 눌렀을 때 관련 화면으로 이동한다.
- 숨김/나중에 처리해도 실제 데이터가 삭제되거나 변경되지 않는다.

### P2. 신메뉴 출시 체크리스트

목표: 메뉴 하나가 실제 출시 가능한 상태인지 한 화면에서 확인한다.

현재 문제:

- 메뉴마스터, 레시피, 원가, 영양성분, 원산지, 알레르기, 출력표가 각각 존재한다.
- 특정 메뉴가 출시 준비 완료인지 확인하려면 여러 화면을 직접 이동해야 한다.

요구사항:

1. 메뉴별 준비 상태를 계산한다.
   - 메뉴마스터 기본정보 있음
   - 판매가 있음
   - 레시피 구성품 있음
   - 구성품 수량/단가 누락 없음
   - 원가율 계산 가능
   - 원산지 출력 가능
   - 알레르기 출력 가능
   - 영양성분 값 입력 완료
   - 표출력 대상 포함 가능
2. 상태는 `완료`, `주의`, `미작성`, `확인 불가`로 나눈다.
3. 각 항목은 바로 수정 화면으로 이동하는 액션을 가진다.
4. 메뉴마스터의 이슈 탭 또는 별도 `출시 준비` 탭에서 확인할 수 있게 한다.
5. 피자 L/R, 1인피자, 사이드, 소스, 음료, 엣지의 기준을 분리한다.

권장 구현:

- `lib/menu-master/readiness.js`: 메뉴별 readiness 계산.
- `components/menu-master/MenuReadinessPanel.jsx`: 메뉴마스터 내부 탭 또는 사이드 패널.
- 선택적으로 `/menu-master?tab=readiness` 또는 `/report`의 진단 카드와 연동.

테스트:

- 레시피 없는 메뉴는 `미작성`.
- 판매가 없는 메뉴는 `주의`.
- 단가 없는 구성품이 있으면 `주의`.
- 영양성분 누락 기준은 현재 정책과 일치.
- 원산지/알레르기 집계 가능한 메뉴는 `완료`.

완료 기준:

- 메뉴 하나를 선택하면 출시 전 누락 항목이 한 화면에 나온다.
- 각 누락 항목에서 수정 위치로 바로 이동할 수 있다.
- 기존 메뉴 저장/레시피 저장 흐름을 깨지 않는다.

### P3. 변경 영향도 미리보기

목표: 식자재나 레시피를 수정하기 전에 어떤 메뉴와 출력물이 영향을 받는지 보여준다.

현재 문제:

- 식자재 단가, 원산지, 알레르기, 레시피 구성품 변경은 여러 화면에 영향을 준다.
- 변경 후 원가율, 원산지 표시판, 알레르기표, 영양성분 출력에 어떤 변화가 생기는지 즉시 알기 어렵다.

요구사항:

1. 식자재 수정 모달 또는 저장 전 확인 단계에서 영향 메뉴 수를 표시한다.
2. 단가 변경 시 예상 원가율 변화 상위 메뉴를 보여준다.
3. 원산지/알레르기 변경 시 영향받는 메뉴와 출력표 종류를 보여준다.
4. 레시피 구성품 변경 시 원가, 원산지, 알레르기, 영양성분 준비 상태 변화를 보여준다.
5. 영향도 계산은 저장 전 preview와 저장 후 결과가 일치해야 한다.

권장 구현:

- `lib/impact/ingredient-impact.js`: 식자재 기준 영향 메뉴 계산.
- `lib/impact/recipe-impact.js`: 메뉴 레시피 기준 영향 계산.
- `components/impact/ImpactPreviewPanel.jsx`: 공통 UI.
- 식자재관리 저장 버튼 근처와 메뉴마스터 수정 모달에 붙인다.

테스트:

- 식자재 1개가 여러 메뉴에 쓰일 때 영향 메뉴 수가 맞는지 확인.
- 단가 변경 전후 원가율 delta 계산.
- 원산지/알레르기 변경 시 메뉴 집계 결과가 바뀌는지 확인.
- 영향 없는 변경은 “영향 없음”으로 표시.

완료 기준:

- 사용자가 저장 전에 영향 범위를 알 수 있다.
- preview 때문에 실제 저장 데이터가 변경되지 않는다.
- 계산 비용이 큰 경우에도 화면 입력이 느려지지 않는다.

### P4. 커맨드 팔레트 고도화

목표: 검색 결과에서 단순 화면 이동이 아니라 실제 항목 위치까지 바로 이동한다.

현재 문제:

- 커맨드 팔레트는 이미 메뉴, 노트, 샘플, 식자재 검색을 지원한다.
- 식자재 검색 결과는 `/ingredient/manage`로만 이동해 해당 행을 직접 찾아야 한다.
- 메뉴/보고서/원가 항목도 더 깊은 링크로 보낼 여지가 있다.

요구사항:

1. 식자재 검색 결과는 `ingredientId`, `productCode`, `view`, `query`를 URL에 반영한다.
2. 식자재관리 화면은 URL 파라미터를 읽어 해당 식자재를 검색/하이라이트/스크롤한다.
3. 메뉴 검색 결과는 메뉴마스터 수정 모달 또는 메뉴 행 위치로 이동한다.
4. 보고서 검색 결과는 보고서 미리보기 또는 상세 위치로 이동한다.
5. 최근 방문 목록에도 상세 항목명이 유지된다.

권장 구현:

- `hooks/usePaletteItems.js`의 ingredient/menu/report item href 확장.
- 대상 화면에 `highlightId`, `productCode`, `menuCode`, `open` 파라미터 처리.
- 행 하이라이트는 2~3초 후 자연스럽게 해제.

테스트:

- 팔레트에서 식자재 선택 시 해당 행이 보인다.
- 존재하지 않는 id는 일반 목록으로 fallback.
- URL 파라미터가 잘못되어도 화면이 깨지지 않는다.

완료 기준:

- 검색 후 추가 필터 입력 없이 원하는 항목에 도달한다.
- 키보드 Enter 선택 흐름이 유지된다.

### P5. 월마감·보고 패키지 생성

목표: 월별 보고/출력 반복 작업을 한 번의 흐름으로 묶는다.

현재 문제:

- 판매량 보고서, 원가 보고서, 식자재 단가 보고서, 원산지/알레르기/영양성분 출력이 각각 존재한다.
- 월마감 시 어떤 출력물을 만들었는지 확인 기록이 흩어진다.

요구사항:

1. 기준 월과 브랜드를 선택한다.
2. 생성할 항목을 체크한다.
   - 판매량 보고서
   - 원가 보고서
   - 식자재 단가 보고서
   - 출고량 보고서
   - 원산지 표시판
   - 알레르기표
   - 영양성분표
3. 생성 전 데이터 신선도와 누락 항목을 경고한다.
4. 생성 후 파일명/생성일/생성자/브랜드/기준월 체크리스트를 저장한다.
5. 실제 zip 묶음은 브라우저 환경 제약을 고려해 2차 기능으로 둔다. 1차는 순차 생성과 체크리스트 저장을 우선한다.

권장 구현:

- `/report` 허브에 `월마감 패키지` 카드 추가.
- `lib/report/package-plan.js`: 생성 항목과 readiness 계산.
- `components/report/MonthlyClosePackageModal.jsx`: 선택/검증/생성 UI.

테스트:

- 기준 월 데이터 없을 때 경고.
- 일부 항목만 선택 가능.
- 생성 기록이 보고서 목록 또는 백업 가능한 store에 저장되는지 확인.

완료 기준:

- 월마감 출력 작업을 하나의 체크리스트로 진행할 수 있다.
- 생성 전 누락 위험이 표시된다.
- 생성 기록이 남는다.

### P6. 저장된 필터·뷰

목표: 자주 쓰는 필터 조합을 저장해 반복 클릭을 줄인다.

대상 화면:

- 식자재관리
- 원가마진표
- 메뉴판매량 분석
- 보고서 목록
- 노트 목록

요구사항:

1. 현재 필터를 이름 붙여 저장한다.
2. 저장된 뷰를 선택하면 필터가 즉시 적용된다.
3. 기본 뷰로 지정할 수 있다.
4. 브랜드별로 분리한다.
5. 삭제/이름변경을 제공한다.

권장 구현:

- `lib/saved-views.js`: localStorage 기반 저장.
- `components/ui/SavedViewSelector.jsx`: 공통 UI.
- 화면별 query param과 동기화한다.

테스트:

- 저장/적용/삭제/기본값 지정.
- 다른 브랜드에서 저장 뷰가 섞이지 않는지 확인.
- 잘못된 저장 데이터는 무시하고 기본 필터로 fallback.

완료 기준:

- 사용자가 반복 필터 설정 없이 자주 쓰는 목록을 바로 열 수 있다.

### P7. 변경 이력·되돌리기 센터

목표: 데이터 변경 작업에 대한 신뢰도를 높인다.

현재 상태:

- 일부 삭제/복원/백업 흐름은 존재한다.
- 하지만 사용자가 최근 어떤 대량 작업을 했는지 한 화면에서 보기 어렵다.

요구사항:

1. 최근 변경 이력을 도메인별로 보여준다.
   - 식자재 저장/삭제/일괄 변경
   - 메뉴마스터 저장/삭제
   - 레시피 저장
   - 판매량/제때 업로드
   - 백업/복원
2. 되돌릴 수 있는 작업과 없는 작업을 명확히 표시한다.
3. 되돌릴 수 없는 작업은 관련 백업 위치를 안내한다.
4. 대량 변경 전 자동 백업과 연결한다.

권장 구현:

- 1차는 기록 전용으로 시작한다.
- 2차에서 제한적 undo를 추가한다.
- `generated_reports`처럼 기존 store를 재사용하지 말고 별도 change log 정책을 세운다.

테스트:

- 변경 작업 후 이력이 생성되는지 확인.
- viewer 권한에서 파괴적 되돌리기가 막히는지 확인.
- 오래된 이력 정리 정책 확인.

완료 기준:

- 최근 변경 원인을 추적할 수 있다.
- 위험 작업 후 복구 경로를 사용자가 이해할 수 있다.

### P8. 메뉴·레시피 빠른 입력 도우미

목표: 메뉴마스터와 레시피 구성품 입력 속도를 높이고, 저장 전 실수를 줄인다.

현재 문제:

- 구성품 입력은 행 단위 반복 작업이 많다.
- 메뉴별로 비슷한 레시피를 복사하거나 일부만 바꾸는 작업이 자주 발생한다.
- 단가 없음, 수량 없음, 규격 누락 같은 문제를 저장 후에야 발견하기 쉽다.

요구사항:

1. 최근 사용 식자재, 자주 쓰는 식자재 조합, 같은 카테고리 추천을 구성품 검색에 활용한다.
2. 구성품 행에서 Enter, 방향키, Tab 이동이 자연스럽게 동작한다.
3. 구성품 행 복사, 위/아래 이동, 빠른 삭제를 제공한다.
4. 규격/단위는 직접 입력과 드롭다운 선택을 모두 지원한다.
5. 같은 메뉴의 L/R 또는 비슷한 메뉴에서 레시피를 복사할 수 있게 한다.
6. 저장 전 누락 수량, 누락 단가, 중복 구성품, 공통원가 누락을 한 번에 보여준다.
7. 단가 없음은 레시피 임시 단가인지 식자재 원본 단가 수정인지 명확히 구분한다.

권장 구현:

- 기존 `components/menu-master/` 레시피 컴포넌트를 우선 재사용한다.
- 빠른 입력 로직은 UI에 직접 넣지 말고 helper/hook으로 분리한다.
- `menuCode`, `size`, `category` 기준으로 복사 후보를 계산한다.
- 저장 전 검증 결과는 메뉴마스터 이슈 탭과 공유 가능한 구조로 만든다.

테스트:

- 키보드 Enter로 식자재 선택 후 다음 입력칸으로 이동.
- 구성품 행 복사 후 저장하면 동일 구성품이 보존.
- L/R 복사 시 menuCode와 size가 잘못 섞이지 않는지 확인.
- 단가 없음 빠른 보정이 레시피 저장값에만 반영되는지 확인.
- 중복 구성품 경고가 저장을 과도하게 막지 않는지 확인.

완료 기준:

- 마우스 없이 기본 구성품 입력을 대부분 처리할 수 있다.
- 저장 전 누락 경고가 실제 저장 결과와 일치한다.
- 기존 메뉴 저장/레시피 저장 통합 흐름이 깨지지 않는다.

### P9. 데이터 품질 점검판

목표: 사이트 전체의 누락, 중복, 이상값을 한 화면에서 점검한다.

현재 문제:

- 식자재, 메뉴, 레시피, 가격, 영양성분, 원산지, 알레르기 진단이 여러 화면에 흩어져 있다.
- 운영자는 “현재 데이터가 믿을 만한 상태인지”를 한 번에 판단하기 어렵다.

요구사항:

1. 전체 데이터 품질 점수를 제공한다.
2. 항목별 진단을 제공한다.
   - 식자재 코드 중복
   - 식자재명 중복 의심
   - 단가 없음
   - baseQuantity/baseUnitType 누락
   - 메뉴 가격 없음
   - 레시피 없음
   - 레시피 수량 없음
   - 영양성분 누락
   - 원산지/알레르기 출력 불가
   - 오래된 업로드 데이터
3. 각 진단 항목은 수정 화면으로 이동하는 링크를 가진다.
4. 심각도는 `치명`, `주의`, `참고`로 나눈다.
5. 진단 결과를 CSV 또는 출력용으로 저장할 수 있게 한다.

권장 구현:

- `lib/quality/build-quality-report.js`: 순수 진단 builder.
- `/report` 또는 홈에 `데이터 품질 점검` 카드 추가.
- P1 액션 센터와 일부 진단 로직을 공유하되, 액션 센터는 “오늘 처리”, 품질 점검판은 “전체 감사” 역할로 분리한다.

테스트:

- 빈 DB에서도 화면이 깨지지 않는다.
- 중복 코드와 중복 이름이 구분된다.
- 다른 브랜드 데이터가 섞이지 않는다.
- 진단 항목 링크가 실제 수정 화면으로 이동한다.

완료 기준:

- 운영자가 현재 데이터의 위험도를 한 화면에서 파악할 수 있다.
- 각 문제를 어디서 고쳐야 하는지 명확하다.

### P10. 모바일·현장 확인 모드

목표: 좁은 화면에서 매장/현장 확인이 필요한 정보만 빠르게 볼 수 있게 한다.

현재 문제:

- 전체 관리자 화면은 데스크톱 업무에는 좋지만 모바일에서 반복 확인하기에는 정보량이 많다.
- 현장에서는 원산지, 알레르기, 영양성분, 메뉴 가격, 식자재 사진처럼 “확인용 정보”가 더 중요하다.

요구사항:

1. 모바일에서 확인 전용 화면을 우선 제공한다.
   - 원산지 표시
   - 알레르기 표시
   - 영양성분 표시
   - 메뉴 가격
   - 식자재 기본 정보와 사진
2. 편집 기능은 관리자 권한에서만 노출한다.
3. 좁은 화면에서 표가 잘리지 않도록 카드/아코디언 레이아웃을 제공한다.
4. 검색, 카테고리 필터, 최근 본 항목을 제공한다.
5. 인쇄/다운로드 버튼은 모바일에서 과도하게 전면에 나오지 않도록 정리한다.

권장 구현:

- 기존 화면을 새로 만들기보다 모바일 전용 섹션/뷰 모드를 추가한다.
- 공통 `MobileInfoList`, `MobileMenuSummaryCard` 같은 작은 컴포넌트를 둔다.
- `qa:mobile`에 핵심 확인 화면을 추가한다.

테스트:

- 390px viewport에서 주요 텍스트와 버튼 겹침 없음.
- 원산지/알레르기/영양성분 확인 흐름이 3번 이내 터치로 가능.
- viewer 권한에서 편집 버튼이 보이지 않는다.
- 모바일에서 긴 메뉴명과 긴 식자재명이 줄바꿈된다.

완료 기준:

- 매장 확인용 정보는 모바일에서 데스크톱보다 더 빠르게 찾을 수 있다.
- 편집/삭제 같은 위험 작업은 모바일에서 실수로 실행되지 않는다.

## 9. 지금 바로 착수 추천

가장 작고 충돌이 적은 시작점은 **P4 커맨드 팔레트 고도화**다.

1차 구현 범위:

- 식자재 검색 결과 href를 `/ingredient/manage?query=...&highlight=...` 형태로 확장.
- 식자재관리에서 해당 query/highlight 파라미터를 읽어 검색어 적용.

## 12. 단계별 완료 정의

각 단계는 아래 조건을 모두 만족해야 완료로 표시한다.

1. 요구사항 표의 필수 항목이 구현되어 있다.

6. 화면 영향이 있으면 실제 브라우저 또는 Playwright QA로 확인했다.

## 15. 최신 실행 플랜: 현재 구현 흔적 기준

기준일: 2026-06-22

현재 작업트리에는 편의 기능 후보의 토대 파일이 이미 일부 존재한다. 따라서 다음 작업은 새 기능을 처음부터 다시 만드는 것이 아니라, **이미 만들어진 파일을 검수하고 부족한 연결·테스트·화면 확인을 채우는 방식**으로 진행한다.

### 15.1 먼저 확인할 구현 토대

Claude Code는 착수 전에 아래 파일들이 실제로 어느 수준까지 동작하는지 확인한다.

| 기능 | 확인 대상 | 판단 기준 |
|---|---|---|
| 업무 액션 센터 | `components/action-center/`, `lib/action-center/`, `components/home/ActionCenterWidget.jsx` | 홈/상단 알림과 같은 action builder를 쓰는지, 숨김/나중에 상태가 원본 데이터를 바꾸지 않는지 |
| 신메뉴 출시 체크리스트 | `components/menu-master/MenuReadinessPanel.jsx`, `lib/menu-master/readiness.js` | 메뉴/레시피/가격/원산지/알레르기/영양성분 누락 기준이 현재 정책과 맞는지 |
| 변경 영향도 미리보기 | `components/impact/`, `lib/impact/ingredient-impact.js` | 저장 전 preview와 저장 후 계산 결과가 일치하는지 |
| 저장된 필터·뷰 | `components/ui/SavedViewSelector.jsx`, `lib/saved-views.js` | 브랜드별 분리, 손상된 localStorage fallback, 기본 뷰 적용이 되는지 |
| 월마감 패키지 | `components/report/MonthlyClosePackageModal.jsx`, `lib/report/package-plan.js` | 실제 파일 생성인지 체크리스트인지 기능명이 과장되지 않았는지 |
| 변경 이력 | `components/change-log/`, `lib/change-log/` | 기록 전용인지 undo까지 포함하는지, 권한/백업 안내가 있는지 |

판단 결과는 각 기능을 아래 셋 중 하나로 분류한다.

- `완성 보완`: 코드가 대부분 있으므로 테스트, 화면 연결, 문서만 보강한다.
- `부분 구현`: 핵심 helper는 있으나 화면 연결 또는 상태 저장이 부족하다.
- `재설계 필요`: 동작이 모호하거나 데이터 위험이 있어 요구사항부터 다시 잡는다.

### 15.3 Claude Code 작업 루프

각 단계는 아래 순서로만 닫는다.

1. 구현 전 조사
   - 관련 파일, 사용처, 기존 테스트를 확인한다.
   - 이미 구현된 코드가 있으면 살릴 수 있는지 먼저 판단한다.

2. 1차 구현
   - 기능 범위를 작게 자른다.
   - 계산 helper, 상태 저장, UI 연결, 문서 업데이트를 구분해서 작업한다.

3. 1차 테스트와 버그 탐색
   - targeted test를 먼저 실행한다.
   - 화면 기능이면 dev 서버에서 실제 진입 URL과 주요 클릭 흐름을 확인한다.
   - 빈 데이터, 잘못된 URL, 다른 브랜드, viewer 권한을 확인한다.

4. Codex 1차 검수
   - diff와 테스트 결과를 다시 확인한다.
   - 요구사항 누락과 데이터 위험을 찾는다.

5. Claude 보완
   - Codex 지적사항만 좁게 수정한다.
   - 같은 테스트를 다시 실행한다.

6. Codex 최종 검수
   - 승인/조건부 승인/수정 필요/검증 불가로 판정한다.
   - 완료된 항목은 문서에 구현 완료로 표시한다.

7. 커밋
   - 한 단계가 green일 때만 커밋한다.
   - 기능 커밋과 문서 커밋은 가능하면 분리한다.

- localStorage 손상값 fallback 확인

### 15.5 이번 사이클 추천 범위

이번 사이클은 아래까지만 진행하는 것을 추천한다.

1. 기준선 고정과 구현 흔적 감사.

- 과거 단가를 원가 계산에 실제 반영할지, 조회 전용으로 둘지.
- 모바일 현장 모드를 새 라우트로 둘지, 기존 화면의 보기 모드로 둘지.

## 16. Claude Code 실행용 최종 플랜

아래 내용은 Claude Code에 그대로 전달할 수 있는 1차 작업 지시서다. 목적은 새 기능을 한 번에 크게 만들지 않고, 이미 존재하는 토대 파일을 살리면서 충돌 위험이 낮은 순서로 편의성을 올리는 것이다.

```md
# 작업: 편의성 개선 로드맵 1차 실행

## 작업 목표
현재 사이트의 반복 작업을 줄이고, 메뉴/식자재/보고서 업무에서 사용자가 원하는 항목까지 더 빠르게 도달하도록 개선한다. 이번 1차 범위는 기준선 확인, 구현 흔적 감사, 커맨드 팔레트 상세 이동, 메뉴 출시 체크리스트 기준 검증, 식자재 영향도 계산 검증까지로 제한한다.

## 현재 문제
기능은 넓게 구현되어 있지만 일부 업무 흐름이 화면별로 흩어져 있다. 검색 결과가 상세 항목까지 바로 이동하지 못하고, 메뉴 출시 전 누락 데이터와 식자재 변경 영향도를 한눈에 확인하기 어렵다. 작업트리에 이미 관련 토대 파일이 있으므로 중복 구현보다 검수와 연결 보강이 우선이다.

## 1차 범위
1. 기준선 확인
   - `git status --short`로 현재 변경 범위를 확인한다.
   - 기존 미커밋 변경을 되돌리지 않는다.
   - 현재 failing test가 있으면 기능 구현 전 원인을 기록한다.
2. 구현 흔적 감사
   - `components/action-center/`, `lib/action-center/`
   - `components/menu-master/MenuReadinessPanel.jsx`, `lib/menu-master/readiness.js`
   - `components/impact/`, `lib/impact/`
   - `components/ui/SavedViewSelector.jsx`, `lib/saved-views.js`
   - `components/report/MonthlyClosePackageModal.jsx`, `lib/report/package-plan.js`
   - `components/change-log/`, `lib/change-log/`
   - 각 기능을 `완성 보완`, `부분 구현`, `재설계 필요`로 분류한다.
3. P4 커맨드 팔레트 상세 이동
   - 식자재 검색 결과가 `/ingredient/manage`의 해당 행까지 이동하도록 query/highlight/productCode 파라미터를 붙인다.
   - 식자재관리 화면은 URL 파라미터를 읽어 검색어 적용, 행 스크롤, 2~3초 하이라이트를 처리한다.
   - 잘못된 파라미터는 화면 오류 없이 일반 목록으로 fallback한다.
   - 기존 `view`, `catFilter`, 검색 필터 동작을 깨지 않는다.
4. P2 신메뉴 출시 체크리스트 기준 검증
   - 메뉴마스터 기본정보, 판매가, 레시피, 수량, 단가, 원산지, 알레르기, 영양성분, 표출력 가능 여부 기준이 현재 정책과 일치하는지 확인한다.
   - 피자 L/R, 단일, 1인피자, 사이드, 소스, 음료, 엣지가 서로 섞이지 않게 검증한다.
5. P3 식자재 영향도 계산 검증
   - 식자재 단가, 원산지, 알레르기 변경이 어떤 메뉴와 출력물에 영향을 주는지 계산한다.
   - 저장 전 preview와 저장 후 실제 결과가 일치해야 한다.

## 변경 금지 사항
- 사용자 데이터 삭제, DB 초기화, 대량 복원 정책 변경은 하지 않는다.
- 기존 백업/복원, 메뉴 저장, 레시피 저장, 제때 업로드 흐름을 깨지 않는다.
- 기능명이 실제 동작보다 과장되면 안 된다. 예를 들어 월마감 패키지가 실제 zip 생성이 아니라면 체크리스트/생성 기록으로 명확히 표시한다.

## 예외 처리
- 빈 DB에서도 화면이 깨지지 않아야 한다.
- 다른 브랜드 데이터가 섞이면 안 된다.
- viewer 권한에서는 편집/삭제/되돌리기 같은 위험 작업이 노출되거나 실행되면 안 된다.
- localStorage 값이 손상되어도 기본값으로 복구되어야 한다.
- URL 파라미터가 잘못되어도 hydration/runtime 오류가 없어야 한다.

## 테스트
필수:
- 관련 targeted Jest 테스트
- `npm run format:check`
- `npm run lint`
- `git diff --check`

화면 변경이 있으면 추가:
- 실제 dev 서버에서 URL 직접 진입 확인
- 필요한 경우 `npm run qa:smoke`
- 모바일 영향이 있으면 `npm run qa:mobile`

## 완료 보고 형식
1. 변경 파일
2. 구현/검수한 기능
3. 실행한 테스트와 결과
4. 화면 수동 확인 결과
5. 남은 위험
6. Codex 검수가 필요한 부분
7. 다음 단계 추천
```

## 17. Codex 검수 체크리스트

Claude Code가 1차 범위를 완료했다고 보고하면 Codex는 아래 순서로 확인한다.

1. 요구사항 일치
   - P4 상세 이동이 실제로 해당 행까지 도달하는가.
   - P2 readiness 기준이 사용자 정책과 일치하는가.
   - P3 영향도 preview가 실제 저장 결과와 어긋나지 않는가.

2. 회귀 위험
   - 메뉴 저장/레시피 저장 통합 흐름이 깨지지 않았는가.
   - 식자재관리 기존 필터, 탭, 일괄 선택, 제때 연동이 유지되는가.
   - 홈, 상단 알림, 보고서, 영양성분 출력으로 불필요한 영향이 번지지 않았는가.

3. 데이터 안전
   - 원본 식자재 단가와 레시피 임시 단가의 의미가 섞이지 않는가.
   - 브랜드별 데이터 분리가 유지되는가.
   - viewer 권한에서 위험 작업이 막히는가.

4. 테스트 신뢰도
   - 새 테스트가 단순 import 검사에 그치지 않고 실제 정책을 검증하는가.
   - 브라우저 동작이 필요한 기능은 화면 확인 결과가 있는가.
   - 테스트 수치가 바뀌면 `SITE_STATUS.md`가 갱신되었는가.

5. 최종 판정
   - 승인: 구현, 테스트, 화면 확인이 모두 충분하다.
   - 조건부 승인: 기능은 동작하지만 수동 QA나 문서 보완이 남았다.
   - 수정 필요: 요구사항 누락 또는 회귀 위험이 있다.
   - 검증 불가: 실행 결과나 코드 확인이 부족하다.
