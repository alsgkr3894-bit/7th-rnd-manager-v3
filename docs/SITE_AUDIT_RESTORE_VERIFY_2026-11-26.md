## 2. 10번 — 복원 검증

### 2-1. DB 백업 복원 (`npm run db:restore:verify`)

대상 `rnd_manager-20261126-085153.dump` (247.5MB). 임시 폴더에 새 PostgreSQL 클러스터를 만들어 `127.0.0.1:55432`로 띄우고 복원했다.

| 검사 | 결과 |
|---|---|
| `pg_restore` | 11.4초 (전체 검증 23.1초) |
| 마이그레이션 | 저장소의 1건 모두 적용 |
| 저장 행 | 303,662행 |
| 핵심 저장소 | 식자재 154, 메뉴 95, 레시피 89, 판매가 86, 단가 파일 28, 단가 행 3,174 |
| 원가 계산(복원본) | 메뉴 95, 화면 간 불일치 0 |
| 운영 DB와 비교 | 같음 303,662 · 백업 뒤 추가 2(`work_log` 1, `note_schedules` 1) · 설명 안 되는 차이 0 |
| 손상 파일 | 앞 60MB만 자른 백업은 실패로 기록됨 |

### 2-2. 별도 앱 + 새 브라우저 프로필

임시 DB에 연결한 프로덕션 빌드를 3101 포트에 띄웠다. 앱의 상태 API 행 수(303,662)가 임시 DB와 같고 운영 DB(303,664)와 다른 것으로 연결 대상을 확인했다.

| 검사 | 결과 |
|---|---|
| 새 프로필에서 "서버에서 불러오기" | 303,662행, 실패 0, **약 4분 30초~5분**(2회: 266초·302초) |
| 저장소별 건수 | 34개 저장소 모두 일치 |
| 레코드 내용 | 식자재·메뉴·레시피·판매가·공통묶음·엣지·단가·노트 326·시제품 192·영양값 71 모두 일치 |
| 화면 | 식자재·메뉴마스터·원가마진·원가보고서·노트 열림, 화면 오류 0 |
| 브라우저 JSON 백업 → 다른 새 프로필 복원 | 완료(317초, 47개 저장소, 오류 0), 건수 차이 없음, 핵심 내용 일치 |
| **복원 중 강제 새로고침** (9번 실제 확인) | 일지가 `running_group`으로 남고 홈에 경고 표시. 적용된 그룹 없음. 다시 복원해도 이전 경고가 보존되고 [확인 완료] 후 사라짐 |

강제 중단 시험은 데이터가 없는 새 프로필에서 했다. 기존 데이터가 있는 상태의 중단은 시험하지 않았다.

### 2-3. 복구되는 범위

| 데이터 | DB 백업(.dump) | 브라우저 JSON 백업 |
|---|---|---|
| 업무 데이터(서버 동기화 대상) | 복구됨 | 복구됨 |
| 외부 로그인정보, 법인카드 | **없음** (서버 동기화 제외) | 포함 대상 |
| 브라우저 설정(localStorage) | **복구 안 됨.** 서버의 설정 35건은 2026-09-15에 한 번 가져온 값이고 "서버에서 불러오기"는 적용하지 않는다 | 포함 대상 |
| 로그인 인증(`.runtime-auth.json`), `.env` | 없음 | 없음 |

새 프로필에는 로그인정보·법인카드가 0건이었다. JSON 백업 시험은 서버에서 불러온 프로필에서 만든 것이라, 이 두 항목과 실제 운영 PC 설정의 왕복은 확인하지 못했다.

### 2-4. 추가한 기능

- `prisma/verify-db-restore.mjs`, `prisma/restore-verify-core.mjs`: 반복 실행하는 복원 검증. 운영 포트와 겹치면 중단하고, 자기가 만든 임시 폴더만 지운다.
- 결과는 `<백업>.dump.verify.json`에 남고, 백업을 정리할 때 함께 지운다.
- 백업 화면: "복원 검증" 타일(마지막 성공 시각)과 목록의 성공·실패 열. 1~9번 중 8번에서 남겼던 "복원 검증 시각"을 DB 백업에 대해 채운다. 브라우저 JSON 백업의 복원 검증 시각은 기록하지 않는다.

```bash
npm run db:restore:verify
```

| 제안 | 내용 | 근거 |
|---|---|---|
| **P1** | **브라우저 JSON 백업이 크기 한계에 가깝다.** 현재 398.9MB, 복원 업로드 한도는 500MB(524,288,000바이트)이고 Node/Chrome 문자열 한계(약 5.37억 자)도 비슷하다. DB 백업 증가 속도(11-02→11-26에 +12.7%)가 유지된다고 가정하면 **약 2개월 뒤** 한도에 닿을 수 있다(추정) | `lib/upload-policy.js:32`, 2-2 측정 |

| P2 | 복원 중 새로고침한 뒤 브라우저가 데이터를 다시 읽기까지 약 6분 걸렸다(1회 관측). 중단된 대형 쓰기 정리로 추정하며 원인은 확인하지 않았다 | 시험 로그 373초→723초 |
| P2 | 앱 DB 계정 `rnd_app`이 PostgreSQL superuser다. 최소 권한 계정이 아니다 | `pg_roles` 조회 |

### 4-1. 건너뛴 13개

- `__tests__/audit/`의 2개 파일이다. 실데이터 사본 폴더(`RND_AUDIT_DATA_DIR`)가 있어야 실행되는데, 사본을 만드는 `scripts/pull-store-rows.mjs`가 저장소에 없었다.

- 결과: **13개 모두 통과.** `npm test`에서는 지금처럼 건너뛴다.


## 5. 확인하지 않은 것

- 다른 PC, 다른 PostgreSQL 버전에서의 복원(같은 PC의 16.14로만 확인)
- 백업 파일의 별도 장치·오프사이트 사본 — 지금 백업은 원본과 같은 디스크에 있다
- 운영 PC 브라우저에서 만든 JSON 백업의 복원, 암호화·복구 키 절차
- 재부팅 후 자동 실행
