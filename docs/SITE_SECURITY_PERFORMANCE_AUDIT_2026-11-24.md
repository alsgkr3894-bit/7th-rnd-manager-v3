현재 사이트는 Next.js 16.4.6, Prisma 7.10.1, PostgreSQL과 브라우저 IndexedDB를 함께 사용하는 내부 업무 시스템이다. 서명된 HttpOnly 세션, API 요청 출처 검사, 요청 크기 제한, 민감정보 로그 정책, 백업 보관 개수 제한 등 기본 방어는 이미 적용되어 있다. 원가·레시피·보고서 계산 정합성도 현재 데이터 기준 정상이다.

## 2. 현재 잘 적용된 보호와 정상 상태

- DB API는 `assertLocalRequest`와 `assertAuthenticatedRequest`를 함께 호출한다.
- 세션 쿠키는 `HttpOnly`, `SameSite=Strict`이며 HTTPS 요청에서는 `Secure`가 붙는다.

- 백업은 현재 14개 보관되며 최신 백업은 2026-11-24 생성본이다.
- 2026-11-24 원가 감사 결과:

## 3. 보안 보완 항목

### P0-1. 서버 계정·역할 인증

**확인된 상태**

- 서버 세션은 한 개의 공용 verifier만 확인하며 사용자 ID와 역할을 담지 않는다.
- `admin` / `viewer` 판정은 브라우저 IndexedDB의 `ref_accounts`와 localStorage 활성 계정 ID를 기준으로 한다.
- 로그인된 세션이라면 `/api/db/store-rows` POST가 서버에서 사용자 역할을 확인하지 않는다.

**위험**

브라우저 데이터나 클라이언트 코드를 조작하면 viewer 표시를 우회할 수 있다. 현재 API는 유효한 로그인 여부만 확인하므로 서버가 관리자 쓰기인지 판정할 근거가 없다.

**권장 조치**

1. PostgreSQL에 서버 정본 계정과 세션 모델을 추가한다.
2. 세션 payload에 불변 사용자 ID, 역할, 세션 버전, 만료 시각을 서명해 넣는다.
3. 읽기 API는 `viewer` 이상, 쓰기·백업 생성·복원·계정 관리는 `admin`만 허용한다.
4. 브라우저 `ref_accounts`는 표시용 캐시로만 사용하고 서버 응답으로 동기화한다.
5. 계정이 0개일 때 자동 admin 폴백은 최초 localhost 설정 절차에서만 허용한다.

**완료 기준**

- viewer 세션의 모든 쓰기 API가 403을 반환한다.
- localStorage와 IndexedDB 역할을 admin으로 바꿔도 서버 쓰기가 실패한다.
- 역할 변경 즉시 기존 세션 권한이 갱신되거나 무효화된다.

### P0-2. 로그인 실패 제한을 서버로 이동

**확인된 상태**

5회 실패·15분 잠금 로직은 `lib/auth.js`의 localStorage에만 저장된다. API route 자체에는 실패 횟수 제한이 없다.

**권장 조치**

- 사용자 ID와 요청 주소를 함께 사용해 서버에서 실패 횟수를 계산한다.
- 5회 실패 시 15분 차단하고 `429 Too Many Requests`, `Retry-After`를 반환한다.
- 성공 시 해당 사용자 실패 횟수만 초기화한다.
- 메모리 구현이라면 전체 키 수·키별 수명 상한을 두고, 다중 서버 가능성이 생기면 DB 또는 Redis로 이전한다.
- 응답 문구로 계정 존재 여부를 추측하지 못하게 한다.

### P0-3. 평문 외부 로그인정보 보호

`rnd_login_credentials.password`는 IndexedDB에 평문으로 저장된다. LAN 서버 동기화에서는 제외됐지만 브라우저 프로필, 개발자 도구, 전체 백업 파일에 노출될 수 있다.

**권장 순서**

1. 전체 백업 기본 범위에서 로그인정보와 법인카드를 제외하고 별도 명시 선택을 요구한다.
2. 화면에서 비밀번호를 기본 마스킹하고 복사·표시 행위를 감사 로그로 남긴다.
3. 사내 HTTPS와 서버 계정 인증 도입 후 서버 측 암호화 저장소 또는 OS 자격증명 저장소로 이전한다.
4. 암호화 키는 DB·백업과 같은 파일에 보관하지 않는다.
5. 기존 평문 레코드는 마이그레이션 성공 확인 후 제거한다.

### P1-1. 세션 수명과 폐기 정책

- 비밀번호 변경 후 이미 발급된 12시간·30일 세션이 계속 유효하다.
- 세션별 폐기 목록, 사용자별 session version, 전체 로그아웃 기능이 없다.

**권장 조치**: 사용자별 `sessionVersion`을 토큰에 넣고 비밀번호·역할 변경 시 증가시킨다. 관리자 화면에 활성 세션 목록과 전체 로그아웃을 제공하며, remember 세션은 절대 만료와 최근 활동 만료를 함께 적용한다.

### P1-2. 로그인 challenge 저장소 제한

challenge는 프로세스 메모리 Map에 2분간 저장되지만 최대 개수 제한이 없다. GET 요청을 반복하면 만료 전까지 메모리가 증가할 수 있다.

- 전체 challenge 최대 개수와 요청 주소별 발급 속도를 제한한다.
- 만료 항목을 주기적으로 제거한다.
- 동일 사용자에게 활성 challenge를 1~3개만 허용한다.

### P1-3. CSP와 응답 헤더

현재 CSP는 `base-uri`, `frame-ancestors`, `object-src`만 제한한다. `default-src`, 스크립트, 스타일, 연결, 이미지, 폼 전송 출처가 제한되지 않는다.

**권장 정책**

- 프로덕션에서 nonce 기반 `script-src`를 사용한다.
- `default-src 'self'`, `form-action 'self'`, `connect-src 'self'`, 필요한 이미지·폰트 출처만 허용한다.
- 개발 모드 HMR의 WebSocket과 인라인 개발 스크립트는 개발 정책에만 허용한다.
- `poweredByHeader: false`, 민감 API `Cache-Control: no-store`를 적용한다.
- HTTPS 전환 후 HSTS를 적용하고 HTTP 직접 접속을 차단한다.

### P1-4. 사내 HTTPS

LAN HTTP에서는 `Secure` 쿠키를 쓸 수 없고 네트워크 구간에서 페이지·세션 요청이 보호되지 않는다. 사내 리버스 프록시와 내부 인증서를 사용해 HTTPS를 기본으로 하고, 신뢰 프록시 목록과 전달 헤더를 명시적으로 제한한다.

## 4. 반응 속도와 성능 보완 항목

### P1-1. 전역 배지의 전체 데이터 재조회 제거

`usePageStats(pathname)`은 경로가 바뀔 때마다 판매 이슈, 메뉴마스터, 레시피 요약, 식자재 이슈를 다시 읽는다. 단순 페이지 이동이 대량 IndexedDB 조회와 계산을 유발한다.

**개선안**

- pathname 의존성을 제거하고 데이터 변경 이벤트·탭 복귀·명시적 새로고침 때만 갱신한다.
- 메뉴·레시피·식자재 이슈 개수를 한 번의 공유 스냅샷으로 계산한다.
- 마지막 결과와 계산 시각을 메모리 캐시에 두고 관련 store 쓰기 이벤트에서만 무효화한다.

### P1-2. 홈 대시보드 데이터 파이프라인 통합

홈은 여러 통계 함수가 각각 `menu_recipes`, `cost_ingredients`, 판매가와 단가 파일을 읽는다. 동시 `getAll` 병합은 적용됐지만, 첫 요청 완료 후 이어지는 독립 함수가 같은 저장소를 다시 읽을 수 있다.

- 홈 진입 시 필요한 정본 데이터를 한 번 읽어 `HomeDataSnapshot`으로 만든다.
- KPI·경고·변동 통계는 스냅샷을 입력으로 받는 순수 함수로 분리한다.
- 화면에 보이지 않는 하단 위젯은 idle 또는 viewport 진입 때 계산한다.
- 느린 위젯 하나 때문에 전체 홈이 늦어지지 않도록 핵심/보조 위젯 준비 상태를 분리한다.

### P1-3. 식자재·메뉴 조회 캐시

- 진행 중 동일 IndexedDB 조회 병합은 유지한다.
- 읽기 결과에 짧은 수명 캐시를 추가할 경우 시간만으로 갱신하지 말고 store 쓰기·복원·브랜드 전환 이벤트로 즉시 무효화한다.
- 캐시 키에는 활성 브랜드와 DB 이름을 반드시 포함한다.
- 배열을 호출부가 수정하지 못하도록 읽기 전용 계약 또는 복사 정책을 정한다.

### P2-1. 전역 CSS 24개 분리

`app/globals.css`가 판매, 식자재, 원가, 노트, 영양, 설정, 보고서, 모션 CSS를 모든 경로에서 불러온다.

- 토큰·기본 레이아웃·공용 컴포넌트만 전역에 유지한다.
- 기능 CSS는 해당 route layout 또는 페이지에서 불러온다.
- 오류·404 스타일처럼 Next.js가 경계 CSS를 불필요하게 preload하지 않는지 확인한다.
- 분리 전후 초기 CSS 전송량과 스타일 회귀 스크린샷을 비교한다.

### P2-2. 선택 기능 지연 로딩

- Command Palette의 노트·샘플·식자재 목록은 팔레트를 처음 열거나 검색을 시작할 때 로드한다.
- 홈 위젯 설정 모달의 `dnd-kit`은 모달을 열 때만 로드한다.
- Excel 패키지의 기존 dynamic import는 유지하고, export 모듈을 일반 화면 barrel export가 정적으로 끌어오지 않는지 번들 분석으로 확인한다.
- 레시피 드래그, 대형 보고서 미리보기, 사진 출력도 실제 기능 진입 시점에만 로드한다.

### P2-3. 대형 정적 데이터와 barrel export

식자재 시드와 판매 규칙 파일은 1천 줄 이상이다. 일반 조회용 `lib/ingredient/index.js`가 시드 모듈을 재수출하므로 트리 셰이킹 실패 시 불필요한 번들에 포함될 수 있다.

- 시드·마이그레이션·관리자 복구 데이터는 별도 admin entry로 분리한다.
- 일반 화면은 구체적인 하위 모듈을 import하고 대형 barrel 재수출을 피한다.
- Next 번들 분석 결과로 실제 포함 여부를 확인한 뒤 분리한다.

### P2-4. 이미지·폰트

- `public/logo-taemyeong.png`는 약 169KB다. 실제 표시 크기에 맞는 최적화 PNG/WebP를 추가한다.
- 로고·사진에 크기 속성을 지정해 레이아웃 이동을 막는다.
- Pretendard 조각 폰트는 유지하되 첫 화면에 필요한 조각만 preload하고 장기 캐시 헤더를 적용한다.
- 식자재 사진은 IndexedDB 저장 전 해상도·용량 제한을 유지하고 목록에서는 썸네일을 사용한다.

### 성능 완료 기준

- 일반 페이지 이동만으로 식자재·메뉴·레시피 전체 조회가 다시 실행되지 않는다.
- 동일 store의 동시 `getAll`은 실제 IndexedDB 요청 1회로 합쳐진다.
- 홈 핵심 정보는 보조 보고서 계산 완료를 기다리지 않고 표시된다.
- 라우트별 JS/CSS 전송량을 CI 또는 정기 QA에서 기록하고 기준 대비 20% 이상 증가하면 경고한다.
- 1천·1만 행 fixture에서 조회, 필터, 보고서 생성 시간을 기록한다.

## 5. 데이터 무결성·동기화 보완

### P1. 서버 권한과 동기화 원자성

- store-row batch는 서버 역할 검사 후에만 실행한다.
- 클라이언트 큐 항목에 사용자 ID, client ID, 요청 ID를 포함해 중복 재전송을 멱등 처리한다.
- 부분 성공이 허용되는 작업과 전체 롤백 작업을 API 계약으로 구분한다.
- 충돌 시 “마지막 저장 우선”만 적용하지 말고 서버 버전 또는 `updatedAt` 비교로 사용자에게 충돌을 알린다.

### P2. 삭제 cascade

`DEFERRED_WORK.md`의 BUG-011에 따르면 `deleteIngredient` 연관 정리는 완전한 단일 트랜잭션이 아니며 현재 라이브 결함은 아니지만 중간 실패 시 부분 정리 위험이 있다.

- 동일 DB store는 한 readwrite 트랜잭션으로 묶는다.
- 다른 저장소·서버 작업은 삭제 계획과 보상 작업을 기록한다.
- 실패 store와 복구 방법을 사용자에게 제공한다.

### P2. 계산·운영 정책의 명확화

- 현재 원가 감사는 불일치 0건이다.
- `OPT-EDGE-001 석쇠`, `OPT-EDGE-004 씬바사삭`은 레시피가 있으나 판매가가 없다. 구성품/옵션 전용이면 이슈에서 제외하는 명시 필드나 정책을 사용한다.
- 과거 단가 기능은 “조회만”인지 “원가 계산에 일시 적용”인지 먼저 확정한 뒤 구현한다.
- 영양성분 부분 누락 허용 기준과 크러스트 완전성 기준을 문서화한다.

### P2. 복원 후 정합성

- 복원 직후 메뉴↔레시피↔식자재↔판매가 참조 감사를 자동 실행한다.
- 실패 store가 있는 백업은 기본 복원을 막거나 명시적 위험 확인을 요구한다.
- 공유 DB와 브랜드 DB를 함께 복원할 때 체크포인트와 롤백 절차를 제공한다.

## 6. 백업·재해 복구 보완

### 현재 상태

- 최신 백업은 2026-11-24 생성되어 신선도는 정상이다.
- 약 220~243MB 백업 14개가 `.db-backups`에 있다.
- 보관 개수 제한은 작동하지만 원본 DB와 같은 PC·디스크에 있다.

### 필요한 보완

1. 암호화된 오프사이트 또는 별도 장치 사본을 최소 1개 유지한다.
2. 일간·주간·월간 보존 정책을 구분하고 용량 기준도 함께 적용한다.
3. 백업 생성 성공이 아니라 임시 DB 복원, 마이그레이션, 핵심 행 수 비교까지 성공해야 “검증됨”으로 표시한다.
4. 분기별 실제 복원 리허설과 RPO/RTO를 기록한다.
5. 백업 파일 체크섬과 메타데이터를 검증하고 손상 파일을 최신 백업으로 세지 않는다.
6. 백업 암호화 키는 백업 파일과 다른 위치에 보관한다.
7. 디스크 여유 공간이 임계치 이하이면 백업 전에 경고하고, 실패 잔해를 자동 정리한다.

## 7. 오류 처리·관측성·운영 보완

### P1. 오류 분류 통일

- 인증 필요 401, 권한 부족 403, 입력 오류 400/422, 충돌 409, 제한 413/429, 일시 장애 503을 일관되게 사용한다.
- 사용자 메시지에는 행동 가능한 해결 방법과 재시도 여부를 표시한다.
- 내부 로그에는 요청 ID와 고정된 오류 코드만 남기고 민감 payload는 기록하지 않는다.

### P2. 상태 화면과 알림

- DB 연결, 마지막 동기화, 미전송 큐, 마지막 검증 백업, 디스크 여유 공간을 관리자 상태 화면에 표시한다.
- 반복 실패는 토스트만 쌓지 말고 지속 배너와 진단 다운로드를 제공한다.
- 백업 실패, 동기화 큐 누적, DB 마이그레이션 실패는 관리자에게 명확한 경고를 표시한다.

### P2. 구조화 로그

- `console.warn/error`를 영역, 오류 코드, request ID, 발생 시각이 있는 구조화 로거로 점진 교체한다.
- 운영 로그 보존기간과 최대 크기를 제한한다.
- 민감정보 정규식 검사 테스트를 유지하고 카드번호·비밀번호·세션 쿠키 사례를 추가한다.

**확인된 상태**

- 로그인 화면은 최초 비밀번호를 4자 이상으로 제한한다.
- `POST /api/auth/session`의 최초 설정 경로는 64자리 16진수 verifier 형식만 확인한다.
- API를 직접 호출하면 길이·복잡도 검사를 거치지 않은 verifier를 서버 인증값으로 설정할 수 있다.
- 서버에 저장된 SHA-256 verifier와 브라우저 localStorage의 `v3:auth-hash`는 challenge 응답을 만들 수 있는 비밀번호 대체값이다.

**위험**

클라이언트 UI 검사는 보안 경계가 아니다. 약한 비밀번호가 설정될 수 있고, 브라우저 저장소의 verifier가 노출되면 원래 비밀번호를 몰라도 로그인 challenge에 응답할 수 있다.

**권장 조치**

1. 최초 설정은 localhost와 일회용 설치 토큰을 동시에 요구한다.
2. 서버가 최소 길이, 금지 비밀번호, 사용자 식별자 포함 여부를 검사한다. 현재 4자 기준은 폐기하고 내부 정책에 맞는 10~12자 이상을 권장한다.
3. 사내 HTTPS 도입 후 원문 비밀번호를 Argon2id 또는 scrypt로 서버에서 해시한다.
4. verifier를 브라우저 영구 localStorage에 저장하지 않는다. 자동 로그인은 HttpOnly 세션만 사용한다.
5. 최초 설정 완료 후 설치 토큰과 bootstrap 경로를 영구 폐기한다.

**완료 기준**

- 직접 API 호출로 약한 비밀번호나 임의 verifier를 등록할 수 없다.
- localStorage를 복사해 다른 브라우저에서 challenge 로그인을 재현할 수 없다.
- 최초 설정은 한 번만 가능하고 감사 로그에 남는다.

### P1-6. proxy가 쿠키 존재만 검사

`proxy.ts`는 `v3:session` 쿠키가 존재하면 보호 화면 진입을 허용하고 서명을 검증하지 않는다. DB API는 다시 서명을 검증하므로 서버 DB는 보호되지만, 임의 문자열 쿠키로 페이지 셸과 해당 브라우저에 이미 저장된 IndexedDB 화면을 열 수 있다.

**권장 조치**

- 보호 route group의 서버 layout에서 세션을 실제 검증하거나 proxy가 공유 가능한 서명 키로 토큰을 검증한다.
- 위조·만료 쿠키는 삭제한 뒤 `/login`으로 보낸다.
- 페이지 보호와 API 보호가 같은 세션 검증 함수를 사용하도록 계약 테스트를 추가한다.
- 쿠키 존재, 위조 서명, 만료, 비밀번호 변경 전 세션, viewer 세션을 각각 E2E로 검사한다.

### P1-7. 인증 상태 파일의 Windows 권한과 손상 복구

`.runtime-auth.json`은 Git에서 제외되고 임시 파일 rename으로 기록되지만, Node의 `mode: 0o600`은 Windows ACL을 충분히 보장하지 않는다. JSON이 부분 손상되거나 읽을 수 없으면 현재 `state()`가 안전한 복구 안내 없이 인증 요청 전체를 실패시킬 수 있다.

**권장 조치**

- Windows에서 파일 소유자와 ACL을 검사·설정하는 설치 단계 또는 DPAPI 기반 저장을 사용한다.
- 상태 파일에 버전과 무결성 검사를 추가한다.
- 손상 시 임의 새 secret을 자동 발급해 기존 인증을 조용히 무효화하지 말고, 백업·복구 또는 운영 PC 재설정 절차를 안내한다.
- 인증 상태 파일과 암호화 키를 DB 백업과 분리한다.

### P1-8. 백업 생성 API 동시 실행·남용 방어

인증된 사용자는 `/api/db/backups` POST를 반복 호출할 수 있다. 현재 route와 `createLocalDbBackup`에는 전역 in-flight 잠금, 사용자별 cooldown, 최근 작업 상태가 없다. 여러 `pg_dump`가 동시에 실행되면 DB·CPU·디스크 I/O가 급증하고 120초 timeout 뒤 잔해가 남을 수 있다.

**권장 조치**

- 서버 프로세스와 OS lock file 양쪽에 단일 실행 잠금을 둔다.
- admin만 실행 가능하게 하고 최소 호출 간격을 적용한다.
- 실행 중에는 409와 현재 작업 시작 시각을 반환한다.
- timeout 시 자식 프로세스 종료와 임시 파일 정리를 보장한다.
- 백업 작업 ID, 성공·실패, 크기, 체크섬을 기록한다.

### P1-9. 종료 시 대형 동기화 작업 유실 가능성

서버 동기화 큐는 `pagehide`와 `beforeunload`에서 약 56KB 단위로 `sendBeacon`을 사용한다. 그러나 사진이 포함된 단일 operation은 최대 16MB까지 허용되며, 분할 함수는 operation 내부를 나누지 않는다. 이 작업은 beacon 한도를 넘고 전송 실패 후 메모리 큐로 돌아오지만 페이지가 종료되면 사라진다.

**권장 조치**

1. 서버 미전송 큐를 IndexedDB 전용 outbox store에 먼저 기록한다.
2. 서버가 수신·커밋한 요청 ID를 확인한 뒤 outbox에서 제거한다.
3. 사진·대형 payload는 별도 업로드 또는 작은 chunk 프로토콜로 전송한다.
4. 앱 시작·온라인 복귀·로그인 성공 때 outbox를 재전송한다.
5. OfflineIndicator는 “로컬 저장 완료”와 “서버 동기화 완료”를 구분해 표시한다.

**완료 기준**

- 16MB에 가까운 사진 레코드를 저장하자마자 탭을 닫아도 다음 실행에서 서버 전송이 완료된다.
- 중복 재전송이 같은 요청 ID로 한 번만 반영된다.
- 전송 대기 건수와 마지막 오류를 사용자가 확인할 수 있다.

### P1-10. 백업 JSON의 메인 스레드 메모리·파싱 위험

복원은 최대 500MB JSON 파일을 `readFileAsText`로 한 번에 메모리에 올리고 `JSON.parse`한다. 문자열과 파싱 객체가 동시에 존재해 실제 메모리 사용량은 파일 크기의 수 배가 될 수 있으며, 저사양 PC에서 화면 정지 또는 탭 종료가 발생할 수 있다. 중첩 깊이와 총 레코드 수에 대한 선제 상한도 없다.

**권장 조치**

- 500MB 허용치를 실제 운영 데이터와 메모리 기준으로 재산정한다.
- Web Worker에서 파싱·검증하고 진행률과 취소 기능을 제공한다.
- 가능하면 스트리밍 JSON 또는 store별 압축 컨테이너 형식으로 전환한다.
- 최대 store 수, store별 행 수, 문자열 길이, 사진 총량, 중첩 깊이를 제한한다.
- 파싱 전 파일 checksum·버전·manifest를 검증한다.

### P1-11. XLSX 압축폭탄과 행·셀 상한

Excel 업로드는 압축 파일 크기만 20~30MB로 제한하고 `arrayBuffer()` 전체를 SheetJS에 전달한다. 작은 XLSX가 압축 해제 후 매우 큰 XML, 과도한 행·열·공유 문자열을 만들 수 있다. 현재 공통 파서에 최대 sheet 수, 행 수, 열 수, 셀 문자열 길이 제한이 확인되지 않는다.

**권장 조치**

- 파싱을 Worker에서 실행하고 시간·메모리 예산을 둔다.
- 업무별 최대 sheet, 행, 열, 셀 길이와 총 셀 수를 제한한다.
- 가능하면 압축 엔트리 수와 압축 해제 예상 크기를 파싱 전에 검사한다.
- 초과 파일은 일부만 읽지 말고 명확히 거부한다.
- CSV에도 최대 행·열·한 셀 길이를 동일하게 적용한다.

### P2-5. 충돌 분기 행의 해결 수단 부족

서버는 다른 client source가 같은 recordKey를 쓰면 `__client:<hash>` 분기 행을 생성하고 기본 조회에서는 숨긴다. 설정 화면은 “무시된 중복” 개수만 표시하며 원본과 분기 값을 비교·선택·병합·삭제하는 UI가 확인되지 않는다.

**위험**

- 사용자는 어떤 값이 누락됐는지 알 수 없다.
- 숨은 분기 행이 계속 누적되어 백업 크기와 진단 복잡도가 증가한다.
- 단순 개수 차이가 0이어도 최신 변경이 기본 행에 반영되지 않았을 수 있다.

**권장 조치**

- store, recordKey, client, 수정 시각, 필드 차이를 보여 주는 충돌 관리 화면을 추가한다.
- 원본 유지, 분기 채택, 필드 병합, 안전 삭제를 제공한다.
- 해결 작업은 admin만 수행하고 감사 로그를 남긴다.
- 일정 기간 미해결 충돌과 급증을 관리자 알림으로 표시한다.

### P2-6. store별 데이터 스키마 검증 부족

서버 store-row 동기화는 store 이름, 키 길이, JSON 직렬화 가능 여부와 크기는 검사하지만 각 store의 필수 필드와 타입은 검증하지 않는다. 인증된 잘못된 클라이언트가 임의 객체를 넣으면 서버 사본과 다른 PC의 hydrate 데이터가 손상될 수 있다.

- 중요 store부터 공유 schema validator를 도입한다.
- 클라이언트 저장, 서버 POST, 백업 복원에서 같은 schema를 사용한다.
- 스키마 버전과 마이그레이션 경로를 payload에 포함한다.
- 알 수 없는 필드는 보존·제거 정책을 store별로 명시한다.

### P2-7. 민감 store의 단일 기기 의존성

로그인정보와 법인카드는 LAN 서버 동기화에서 제외된다. 이는 네트워크 노출을 줄이지만 해당 브라우저 프로필이 손상되면 중앙 서버에서 복구할 수 없다는 뜻이다. 전체 JSON 백업에 포함할 수 있으나 평문 민감정보 위험과 충돌한다.

**권장 조치**

- 민감 store별로 “서버 미동기화·로컬 암호화 백업” 정책을 화면에 명시한다.
- 암호화된 별도 백업과 복구 키 보관 절차를 제공한다.
- 일반 업무 백업과 민감정보 백업을 분리하고 각각 마지막 성공·복원 검증 시각을 표시한다.

### P2-8. API 조회 오류 상태코드 일관성

`GET /api/db/store-rows`는 인증·출처 오류 외의 모든 실패를 400으로 반환한다. DB 연결 실패나 일시 장애도 잘못된 요청으로 분류되면 클라이언트가 영구 실패로 오해하고 재시도하지 않을 수 있다.

- 쿼리 검증 오류는 400, 충돌은 409, DB·네트워크 장애는 503으로 분리한다.
- 오류 코드와 retryable boolean을 공통 API 오류 형식에 추가한다.
- 클라이언트 큐·hydrate가 상태코드가 아니라 명시적 오류 코드로 재시도 여부를 판단하게 한다.

### P2-9. 오프라인 표시의 의미 분리

현재 OfflineIndicator는 `navigator.onLine`을 기준으로 “데이터는 기기에 저장됩니다”라고 표시한다. 이는 IndexedDB 로컬 저장에는 맞지만 서버 동기화 완료나 DB 서버 접근 가능 여부를 보장하지 않는다.

- 인터넷 연결, 앱 서버 접근, DB 상태, 미전송 outbox를 별도 상태로 표현한다.
- `navigator.onLine`만으로 “복구됨”을 선언하지 말고 경량 인증 상태 API 성공을 확인한다.
- 서버 동기화 실패 중에도 로컬 저장 성공 여부를 별도로 알려 사용자가 데이터 상태를 오해하지 않게 한다.

### 추가 완료 체크리스트

- [ ] 위조된 `v3:session` 쿠키로 보호 화면에 진입할 수 없다.
- [ ] API 직접 호출로 약한 최초 비밀번호를 설정할 수 없다.
- [ ] Windows 운영 PC에서 인증 상태 파일 ACL과 손상 복구 절차가 검증된다.
- [ ] 동시에 여러 백업 생성 요청을 보내도 `pg_dump`는 하나만 실행된다.
- [ ] 대형 사진 저장 직후 탭을 종료해도 서버 동기화 작업이 다음 실행에서 복구된다.
- [ ] 500MB에 가까운 복원 파일을 처리해도 UI가 멈추지 않고 취소할 수 있다.
- [ ] XLSX/CSV의 행·열·셀·압축 해제 상한을 초과하면 안전하게 거부된다.
- [ ] 충돌 분기 행을 비교·해결·삭제할 수 있다.
- [ ] 중요 store의 잘못된 필드 타입이 서버 저장과 복원 단계에서 거부된다.
- [ ] 오프라인·서버 장애·동기화 대기 상태가 서로 다르게 표시된다.

### P2-10. 단일 대형 행이 조회 응답 상한을 초과할 수 있음

`readStoreRowPage`는 페이지 응답을 최대 8MB로 제한하지만 첫 번째 행은 제한을 넘더라도 그대로 반환한다. 쓰기 경로의 단일 레코드 상한은 16MB이므로 사진이 포함된 노트·샘플 한 건이 조회 응답 예산의 두 배까지 커질 수 있다.

- 사진 원본을 store row JSON과 분리해 별도 blob 저장소로 이전한다.
- 단일 행도 응답 상한을 넘으면 명시적인 `413`과 레코드 식별자를 반환한다.
- 클라이언트가 해당 행을 건너뛰거나 축소본·청크로 복구할 수 있게 한다.
- 서버 직렬화 메모리와 브라우저 JSON 파싱 메모리를 함께 성능 시험한다.

### P2-11. 인증 상태 파일의 요청별 동기 I/O

세션 검증과 challenge 생성 때 `.runtime-auth.json`을 동기 방식으로 읽고 JSON 파싱한다. 현재 트래픽에서는 작지만 API 호출이 몰리거나 디스크가 느려질 때 Node.js 이벤트 루프를 막을 수 있고, 파일이 손상되면 모든 인증 요청이 동시에 실패한다.

- 시작 시 검증된 상태를 메모리에 적재하고 변경 시에만 원자적으로 갱신한다.
- 다중 프로세스가 필요해지면 파일 대신 DB 또는 전용 세션 저장소를 사용한다.
- 파일 손상·권한 거부·디스크 지연을 주입한 회귀 테스트를 추가한다.

### P2-12. 파괴적 동기화 작업의 서버 감사 이력 부족

인증된 POST는 store 전체 `clear`와 다수 `delete`를 한 트랜잭션에서 실행할 수 있다. 현재 서버는 누가 어떤 store를 몇 건 지웠는지 별도 감사 이력이나 복구 지점을 남기지 않는다. 역할 인증 문제를 해결한 뒤에도 운영자 실수와 계정 오용을 추적하기 어렵다.

- `clear`, 대량 삭제, 복원, 백업 생성은 사용자·시각·대상·건수·요청 ID를 감사 로그로 남긴다.
- 대량 작업은 미리보기와 재확인 토큰을 요구하고 동일 요청의 중복 실행을 막는다.
- 작업 직전 복구 지점 또는 논리 삭제 기간을 제공한다.
- 감사 로그는 일반 업무 데이터 삭제와 분리해 보존한다.

## 14. 추가로 찾아야 할 보완 항목

아래 항목은 아직 결함으로 확정한 것이 아니라, 실제 운영 조건과 실패 상황을 재현해 확인해야 할 **추가 감사 대기 목록**이다. 점검 결과 문제가 없으면 통과 근거를 남기고, 문제가 확인되면 P0~P3 개선 항목으로 승격한다.

### 14-1. 계정·권한·감사 추적

- 관리자 생성·삭제·역할 변경·비밀번호 변경 이력이 남는지 확인한다.
- 마지막 관리자를 삭제하거나 viewer로 낮출 수 없는지 확인한다.
- 퇴사자·공용 PC 세션을 즉시 원격 폐기할 수 있는지 확인한다.
- 백업, 복원, 전체 삭제, 데이터 내보내기를 누가 실행했는지 추적 가능한지 확인한다.

### 14-2. 다중 사용자·동시 수정

- 두 PC가 같은 메뉴·레시피·식자재를 동시에 수정했을 때 조용히 덮어쓰지 않는지 확인한다.
- 삭제 직후 다른 PC가 오래된 레코드를 다시 업로드해 부활시키는지 확인한다.
- 클라이언트 시계가 틀려도 최신 데이터 판정이 깨지지 않는지 확인한다.
- 충돌 해결 중 재충돌하거나 네트워크가 끊겼을 때 원본이 보존되는지 확인한다.

### 14-3. 브라우저 저장공간·장시간 사용

- 사진과 대형 레코드로 IndexedDB quota가 가득 찼을 때 저장 실패를 사용자에게 알리는지 확인한다.
- 8시간 이상 사용, 화면 반복 이동, 인쇄 미리보기 반복 후 메모리·이벤트 리스너가 증가하지 않는지 측정한다.
- 브라우저 강제 종료, OS 재부팅, 저장 중 전원 차단 후 임시 저장과 outbox가 복구되는지 확인한다.
- 시크릿 모드·브라우저 데이터 정리·프로필 손상 시 복구 안내가 충분한지 확인한다.

### 14-4. 파일·출력·인쇄 보안

- 모든 인쇄용 HTML 문자열에 사용자 입력이 escape되어 스크립트나 임의 마크업이 실행되지 않는지 확인한다.
- CSV뿐 아니라 XLSX 수식, 외부 링크, 숨김 시트, 매크로 유사 입력을 안전하게 처리하는지 확인한다.
- 파일명에 경로 문자·제어 문자·매우 긴 문자열이 들어가도 다운로드가 안전한지 확인한다.
- PDF·Excel·브라우저 인쇄가 같은 원가·단위·반올림 규칙을 사용하는지 스냅샷 비교한다.

### 14-5. 법정 표시·업무 규칙 회귀

- 공산품의 알레르기·원산지 표시 면제와 일반 식자재의 필수 표시가 서로 섞이지 않는지 확인한다.
- 단종, 구성품 전용, 판매 중지, 폐기 상태가 메뉴 이슈·판매가 누락 경고에 정확히 반영되는지 확인한다.
- 대체 식자재 연결 후 원본 참조 경고가 사라지고 원가·알레르기·원산지가 올바르게 이어지는지 확인한다.
- 메뉴 상태 변경이 원가 보고서, 레시피 출력, 이슈 알림에서 동시에 반영되는지 확인한다.

### 14-6. 재해 복구·Windows 운영

- PostgreSQL 자동 시작, 사이트 자동 시작, 백업 예약이 Windows 업데이트·재부팅 후에도 동작하는지 확인한다.
- 디스크 부족, 백업 폴더 권한 거부, `pg_dump` 중단 시 실패 잔해를 정상 백업으로 세지 않는지 확인한다.
- 다른 PC와 다른 PostgreSQL 버전에 백업을 복원해 실제 업무 화면까지 열리는지 확인한다.
- DB뿐 아니라 인증 상태, 환경 설정, 암호화 키, 운영 문서를 함께 복구할 수 있는지 확인한다.

### 14-7. 네트워크·배포 경계

- 허용 LAN 호스트 설정 오류, 프록시 사용, IPv6, 호스트명 접속에서도 출처 검사가 의도대로 동작하는지 확인한다.
- HTTP 환경에서 세션 쿠키가 네트워크 도청에 노출되지 않도록 HTTPS 전환 시험을 수행한다.
- 개발 서버가 운영에 사용되지 않고 프로덕션 빌드만 자동 시작되는지 확인한다.
- `.next` 캐시 손상, 부분 배포, 오래된 정적 청크 혼합 시 자동 복구 절차를 검증한다.

### 14-8. 가용성·부하·오류 복구

- 다수 사용자가 동시에 전체 hydrate, 보고서 생성, 백업을 실행할 때 DB와 Node.js가 버티는지 측정한다.
- 느린 요청·중단된 요청·DB 연결 고갈에 timeout과 취소가 적용되는지 확인한다.
- API 재시도가 무한 반복되거나 같은 변경을 중복 적용하지 않는지 확인한다.
- 오류 경계가 반복 오류 루프를 만들지 않고 사용자가 안전하게 다시 시도할 수 있는지 확인한다.

### 14-9. 공급망·배포 무결성

- lockfile 고정, 설치 스크립트, 직접 URL 의존성, 패키지 출처와 해시를 정기 검토한다.
- CI에서 의존성 감사, secret 검사, 라이선스 검사, 프로덕션 빌드와 smoke test를 강제한다.
- 배포 산출물과 DB 마이그레이션의 버전을 연결하고 이전 버전으로 되돌릴 절차를 검증한다.
- 운영 브랜치 보호, 리뷰, 서명된 릴리스 또는 변경 승인 절차를 마련한다.

### 14-10. 접근성·모바일·실수 방지

- 키보드만으로 모달, 표, 드롭다운, 삭제 확인, 파일 업로드를 완료할 수 있는지 확인한다.
- 포커스 복원, 스크린리더 이름, 색상 외 상태 표시, 200% 확대를 실제 화면별로 검사한다.
- 모바일에서 표 편집·저장·취소 버튼이 가려지거나 잘못 눌리지 않는지 확인한다.
- 대량 삭제·복원·덮어쓰기는 영향 범위와 되돌리기 가능 여부를 실행 전에 명확히 보여준다.

### 추가 감사 완료 기준

- [ ] 각 항목에 통과·실패·미검증 상태와 근거 파일 또는 재현 절차가 기록된다.
- [ ] 실패 항목은 영향도와 재현 가능성을 기준으로 P0~P3 우선순위를 받는다.
- [ ] 운영 PC, 보조 PC, 모바일, 재부팅 후 환경에서 핵심 시나리오를 한 번 이상 검증한다.
- [ ] 보안 조치가 원가·메뉴·식자재·보고서 기능을 깨뜨리지 않는 회귀 테스트가 존재한다.
