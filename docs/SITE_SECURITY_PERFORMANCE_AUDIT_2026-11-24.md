# 사이트 보안·성능·운영 품질 종합 감사

> 기준일: 2026-11-24 (Asia/Seoul)  
> 기준 브랜치: `codex/next16-prisma-security-upgrade`  
> 운영 전제: 사내 LAN 전용, 계정별 `admin` / `viewer` 권한 적용 목표

## 1. 결론

현재 사이트는 Next.js 16.4.6, Prisma 7.10.1, PostgreSQL과 브라우저 IndexedDB를 함께 사용하는 내부 업무 시스템이다. 서명된 HttpOnly 세션, API 요청 출처 검사, 요청 크기 제한, 민감정보 로그 정책, 백업 보관 개수 제한 등 기본 방어는 이미 적용되어 있다. 원가·레시피·보고서 계산 정합성도 현재 데이터 기준 정상이다.

다만 **로그인 사용자의 서버 권한을 구분하지 못하는 문제**, **브라우저에서만 동작하는 로그인 실패 제한**, **평문 자격정보 저장**, **불충분한 CSP**, **동일 데이터를 여러 화면 기능이 반복 집계하는 구조**는 우선 보완해야 한다. 운영 측면에서는 백업이 같은 디스크에만 있고 실제 복원 성공을 정기적으로 증명하지 않으며, 문서가 코드보다 오래된 상태다.

## 2. 현재 잘 적용된 보호와 정상 상태

- DB API는 `assertLocalRequest`와 `assertAuthenticatedRequest`를 함께 호출한다.
- 세션 쿠키는 `HttpOnly`, `SameSite=Strict`이며 HTTPS 요청에서는 `Secure`가 붙는다.
- API JSON 본문은 서버에서 크기를 제한하고, proxy에서도 `Content-Length`가 큰 요청을 먼저 거부한다.
- `rnd_login_credentials`, `rnd_corporate_card_entries`는 LAN 서버 동기화 대상에서 제외된다.
- API 오류 응답은 DB 경로·스키마·원본 예외 객체를 사용자에게 노출하지 않는다.
- CSV 수식 인젝션 방어와 업로드 확장자·크기 정책이 존재한다.
- 백업은 현재 14개 보관되며 최신 백업은 2026-11-24 생성본이다.
- 2026-11-24 원가 감사 결과:
  - 화면 간 원가 불일치 0건
  - 원가표·레시피 시트·PDF 간 불일치 0건
  - 없는 제품 코드 0건
  - 판매 중 메뉴의 단종 식자재 참조 0건
- Next.js 16 Turbopack 프로덕션 빌드와 전체 Jest 테스트가 통과한 상태다.

이 항목들은 새 보안 작업에서 제거하거나 약화하지 말아야 할 회귀 기준이다.

## 3. 보안 보완 항목

### P0-1. 서버 계정·역할 인증

**확인된 상태**

- 서버 세션은 한 개의 공용 verifier만 확인하며 사용자 ID와 역할을 담지 않는다.
- `admin` / `viewer` 판정은 브라우저 IndexedDB의 `ref_accounts`와 localStorage 활성 계정 ID를 기준으로 한다.
- 로그인된 세션이라면 `/api/db/store-rows` POST가 서버에서 사용자 역할을 확인하지 않는다.

**위험**

브라우저 데이터나 클라이언트 코드를 조작하면 viewer 표시를 우회할 수 있다. 현재 API는 유효한 로그인 여부만 확인하므로 서버가 관리자 쓰기인지 판정할 근거가 없다.

**권장 조치**

1. PostgreSQL에 서버 정본 계정과 세션 모델을 추가한다.
2. 세션 payload에 불변 사용자 ID, 역할, 세션 버전, 만료 시각을 서명해 넣는다.
3. 읽기 API는 `viewer` 이상, 쓰기·백업 생성·복원·계정 관리는 `admin`만 허용한다.
4. 브라우저 `ref_accounts`는 표시용 캐시로만 사용하고 서버 응답으로 동기화한다.
5. 계정이 0개일 때 자동 admin 폴백은 최초 localhost 설정 절차에서만 허용한다.

**완료 기준**

- viewer 세션의 모든 쓰기 API가 403을 반환한다.
- localStorage와 IndexedDB 역할을 admin으로 바꿔도 서버 쓰기가 실패한다.
- 역할 변경 즉시 기존 세션 권한이 갱신되거나 무효화된다.

### P0-2. 로그인 실패 제한을 서버로 이동

**확인된 상태**

5회 실패·15분 잠금 로직은 `lib/auth.js`의 localStorage에만 저장된다. API route 자체에는 실패 횟수 제한이 없다.

**권장 조치**

- 사용자 ID와 요청 주소를 함께 사용해 서버에서 실패 횟수를 계산한다.
- 5회 실패 시 15분 차단하고 `429 Too Many Requests`, `Retry-After`를 반환한다.
- 성공 시 해당 사용자 실패 횟수만 초기화한다.
- 메모리 구현이라면 전체 키 수·키별 수명 상한을 두고, 다중 서버 가능성이 생기면 DB 또는 Redis로 이전한다.
- 응답 문구로 계정 존재 여부를 추측하지 못하게 한다.

### P0-3. 평문 외부 로그인정보 보호

`rnd_login_credentials.password`는 IndexedDB에 평문으로 저장된다. LAN 서버 동기화에서는 제외됐지만 브라우저 프로필, 개발자 도구, 전체 백업 파일에 노출될 수 있다.

**권장 순서**

1. 전체 백업 기본 범위에서 로그인정보와 법인카드를 제외하고 별도 명시 선택을 요구한다.
2. 화면에서 비밀번호를 기본 마스킹하고 복사·표시 행위를 감사 로그로 남긴다.
3. 사내 HTTPS와 서버 계정 인증 도입 후 서버 측 암호화 저장소 또는 OS 자격증명 저장소로 이전한다.
4. 암호화 키는 DB·백업과 같은 파일에 보관하지 않는다.
5. 기존 평문 레코드는 마이그레이션 성공 확인 후 제거한다.

### P1-1. 세션 수명과 폐기 정책

- 비밀번호 변경 후 이미 발급된 12시간·30일 세션이 계속 유효하다.
- 세션별 폐기 목록, 사용자별 session version, 전체 로그아웃 기능이 없다.

**권장 조치**: 사용자별 `sessionVersion`을 토큰에 넣고 비밀번호·역할 변경 시 증가시킨다. 관리자 화면에 활성 세션 목록과 전체 로그아웃을 제공하며, remember 세션은 절대 만료와 최근 활동 만료를 함께 적용한다.

### P1-2. 로그인 challenge 저장소 제한

challenge는 프로세스 메모리 Map에 2분간 저장되지만 최대 개수 제한이 없다. GET 요청을 반복하면 만료 전까지 메모리가 증가할 수 있다.

- 전체 challenge 최대 개수와 요청 주소별 발급 속도를 제한한다.
- 만료 항목을 주기적으로 제거한다.
- 동일 사용자에게 활성 challenge를 1~3개만 허용한다.

### P1-3. CSP와 응답 헤더

현재 CSP는 `base-uri`, `frame-ancestors`, `object-src`만 제한한다. `default-src`, 스크립트, 스타일, 연결, 이미지, 폼 전송 출처가 제한되지 않는다.

**권장 정책**

- 프로덕션에서 nonce 기반 `script-src`를 사용한다.
- `default-src 'self'`, `form-action 'self'`, `connect-src 'self'`, 필요한 이미지·폰트 출처만 허용한다.
- 개발 모드 HMR의 WebSocket과 인라인 개발 스크립트는 개발 정책에만 허용한다.
- `poweredByHeader: false`, 민감 API `Cache-Control: no-store`를 적용한다.
- HTTPS 전환 후 HSTS를 적용하고 HTTP 직접 접속을 차단한다.

### P1-4. 사내 HTTPS

LAN HTTP에서는 `Secure` 쿠키를 쓸 수 없고 네트워크 구간에서 페이지·세션 요청이 보호되지 않는다. 사내 리버스 프록시와 내부 인증서를 사용해 HTTPS를 기본으로 하고, 신뢰 프록시 목록과 전달 헤더를 명시적으로 제한한다.

### P1-5. 의존성 취약점

2026-11-24 `npm audit` 결과 고위험 6건이 남아 있다.

| 패키지 경로 | 상태 | 조치 |
|---|---|---|
| `brace-expansion` | 수정 버전 있음 | lockfile 업데이트 후 전체 테스트 |
| `browserslist` | 수정 버전 있음 | lockfile 업데이트 후 빌드 검사 |
| `js-yaml` | 수정 버전 있음 | Jest/coverage 도구 업데이트 |
| `prisma` → `@prisma/config` → `effect` | 현재 안정판에 직접 수정 경로 없음 | Prisma 안정판 릴리스 추적, 강제 6.12 다운그레이드 금지 |

개발 도구 취약점은 런타임 직접 노출과 구분하되 CI·개발 PC에서 악성 입력을 처리할 가능성 때문에 방치하지 않는다.

### P2 보안·개인정보 보완

- 공인 IP 조회가 `api.ipify.org`에 접속자의 IP를 전송한다. 기본 비활성화하고 사용자 버튼 실행과 개인정보 안내를 유지한다.
- 인증·권한·백업 생성·복원·민감정보 열람에 보안 감사 로그를 남긴다. 비밀번호, 쿠키, 카드번호 원문은 기록하지 않는다.
- 서버 상태 API의 시간 정보도 꼭 필요한 값만 제공하고 운영 경로·DB 이름은 계속 숨긴다.
- `DELETE /api/auth/session`에도 동일 출처 검사를 적용해 정책을 일관되게 한다.
- `docs/SECURITY_POLICY.md`의 “서버 인증 없음”, `middleware.ts`, `v3:auth` 설명을 현재 서명 세션과 `proxy.ts` 기준으로 수정한다.

## 4. 반응 속도와 성능 보완 항목

### P1-1. 전역 배지의 전체 데이터 재조회 제거

`usePageStats(pathname)`은 경로가 바뀔 때마다 판매 이슈, 메뉴마스터, 레시피 요약, 식자재 이슈를 다시 읽는다. 단순 페이지 이동이 대량 IndexedDB 조회와 계산을 유발한다.

**개선안**

- pathname 의존성을 제거하고 데이터 변경 이벤트·탭 복귀·명시적 새로고침 때만 갱신한다.
- 메뉴·레시피·식자재 이슈 개수를 한 번의 공유 스냅샷으로 계산한다.
- 마지막 결과와 계산 시각을 메모리 캐시에 두고 관련 store 쓰기 이벤트에서만 무효화한다.

### P1-2. 홈 대시보드 데이터 파이프라인 통합

홈은 여러 통계 함수가 각각 `menu_recipes`, `cost_ingredients`, 판매가와 단가 파일을 읽는다. 동시 `getAll` 병합은 적용됐지만, 첫 요청 완료 후 이어지는 독립 함수가 같은 저장소를 다시 읽을 수 있다.

- 홈 진입 시 필요한 정본 데이터를 한 번 읽어 `HomeDataSnapshot`으로 만든다.
- KPI·경고·변동 통계는 스냅샷을 입력으로 받는 순수 함수로 분리한다.
- 화면에 보이지 않는 하단 위젯은 idle 또는 viewport 진입 때 계산한다.
- 느린 위젯 하나 때문에 전체 홈이 늦어지지 않도록 핵심/보조 위젯 준비 상태를 분리한다.

### P1-3. 식자재·메뉴 조회 캐시

- 진행 중 동일 IndexedDB 조회 병합은 유지한다.
- 읽기 결과에 짧은 수명 캐시를 추가할 경우 시간만으로 갱신하지 말고 store 쓰기·복원·브랜드 전환 이벤트로 즉시 무효화한다.
- 캐시 키에는 활성 브랜드와 DB 이름을 반드시 포함한다.
- 배열을 호출부가 수정하지 못하도록 읽기 전용 계약 또는 복사 정책을 정한다.

### P2-1. 전역 CSS 24개 분리

`app/globals.css`가 판매, 식자재, 원가, 노트, 영양, 설정, 보고서, 모션 CSS를 모든 경로에서 불러온다.

- 토큰·기본 레이아웃·공용 컴포넌트만 전역에 유지한다.
- 기능 CSS는 해당 route layout 또는 페이지에서 불러온다.
- 오류·404 스타일처럼 Next.js가 경계 CSS를 불필요하게 preload하지 않는지 확인한다.
- 분리 전후 초기 CSS 전송량과 스타일 회귀 스크린샷을 비교한다.

### P2-2. 선택 기능 지연 로딩

- Command Palette의 노트·샘플·식자재 목록은 팔레트를 처음 열거나 검색을 시작할 때 로드한다.
- 홈 위젯 설정 모달의 `dnd-kit`은 모달을 열 때만 로드한다.
- Excel 패키지의 기존 dynamic import는 유지하고, export 모듈을 일반 화면 barrel export가 정적으로 끌어오지 않는지 번들 분석으로 확인한다.
- 레시피 드래그, 대형 보고서 미리보기, 사진 출력도 실제 기능 진입 시점에만 로드한다.

### P2-3. 대형 정적 데이터와 barrel export

식자재 시드와 판매 규칙 파일은 1천 줄 이상이다. 일반 조회용 `lib/ingredient/index.js`가 시드 모듈을 재수출하므로 트리 셰이킹 실패 시 불필요한 번들에 포함될 수 있다.

- 시드·마이그레이션·관리자 복구 데이터는 별도 admin entry로 분리한다.
- 일반 화면은 구체적인 하위 모듈을 import하고 대형 barrel 재수출을 피한다.
- Next 번들 분석 결과로 실제 포함 여부를 확인한 뒤 분리한다.

### P2-4. 이미지·폰트

- `public/logo-taemyeong.png`는 약 169KB다. 실제 표시 크기에 맞는 최적화 PNG/WebP를 추가한다.
- 로고·사진에 크기 속성을 지정해 레이아웃 이동을 막는다.
- Pretendard 조각 폰트는 유지하되 첫 화면에 필요한 조각만 preload하고 장기 캐시 헤더를 적용한다.
- 식자재 사진은 IndexedDB 저장 전 해상도·용량 제한을 유지하고 목록에서는 썸네일을 사용한다.

### 성능 완료 기준

- 일반 페이지 이동만으로 식자재·메뉴·레시피 전체 조회가 다시 실행되지 않는다.
- 동일 store의 동시 `getAll`은 실제 IndexedDB 요청 1회로 합쳐진다.
- 홈 핵심 정보는 보조 보고서 계산 완료를 기다리지 않고 표시된다.
- 라우트별 JS/CSS 전송량을 CI 또는 정기 QA에서 기록하고 기준 대비 20% 이상 증가하면 경고한다.
- 1천·1만 행 fixture에서 조회, 필터, 보고서 생성 시간을 기록한다.

## 5. 데이터 무결성·동기화 보완

### P1. 서버 권한과 동기화 원자성

- store-row batch는 서버 역할 검사 후에만 실행한다.
- 클라이언트 큐 항목에 사용자 ID, client ID, 요청 ID를 포함해 중복 재전송을 멱등 처리한다.
- 부분 성공이 허용되는 작업과 전체 롤백 작업을 API 계약으로 구분한다.
- 충돌 시 “마지막 저장 우선”만 적용하지 말고 서버 버전 또는 `updatedAt` 비교로 사용자에게 충돌을 알린다.

### P2. 삭제 cascade

`DEFERRED_WORK.md`의 BUG-011에 따르면 `deleteIngredient` 연관 정리는 완전한 단일 트랜잭션이 아니며 현재 라이브 결함은 아니지만 중간 실패 시 부분 정리 위험이 있다.

- 동일 DB store는 한 readwrite 트랜잭션으로 묶는다.
- 다른 저장소·서버 작업은 삭제 계획과 보상 작업을 기록한다.
- 실패 store와 복구 방법을 사용자에게 제공한다.

### P2. 계산·운영 정책의 명확화

- 현재 원가 감사는 불일치 0건이다.
- `OPT-EDGE-001 석쇠`, `OPT-EDGE-004 씬바사삭`은 레시피가 있으나 판매가가 없다. 구성품/옵션 전용이면 이슈에서 제외하는 명시 필드나 정책을 사용한다.
- 과거 단가 기능은 “조회만”인지 “원가 계산에 일시 적용”인지 먼저 확정한 뒤 구현한다.
- 영양성분 부분 누락 허용 기준과 크러스트 완전성 기준을 문서화한다.

### P2. 복원 후 정합성

- 복원 직후 메뉴↔레시피↔식자재↔판매가 참조 감사를 자동 실행한다.
- 실패 store가 있는 백업은 기본 복원을 막거나 명시적 위험 확인을 요구한다.
- 공유 DB와 브랜드 DB를 함께 복원할 때 체크포인트와 롤백 절차를 제공한다.

## 6. 백업·재해 복구 보완

### 현재 상태

- 최신 백업은 2026-11-24 생성되어 신선도는 정상이다.
- 약 220~243MB 백업 14개가 `.db-backups`에 있다.
- 보관 개수 제한은 작동하지만 원본 DB와 같은 PC·디스크에 있다.

### 필요한 보완

1. 암호화된 오프사이트 또는 별도 장치 사본을 최소 1개 유지한다.
2. 일간·주간·월간 보존 정책을 구분하고 용량 기준도 함께 적용한다.
3. 백업 생성 성공이 아니라 임시 DB 복원, 마이그레이션, 핵심 행 수 비교까지 성공해야 “검증됨”으로 표시한다.
4. 분기별 실제 복원 리허설과 RPO/RTO를 기록한다.
5. 백업 파일 체크섬과 메타데이터를 검증하고 손상 파일을 최신 백업으로 세지 않는다.
6. 백업 암호화 키는 백업 파일과 다른 위치에 보관한다.
7. 디스크 여유 공간이 임계치 이하이면 백업 전에 경고하고, 실패 잔해를 자동 정리한다.

## 7. 오류 처리·관측성·운영 보완

### P1. 오류 분류 통일

- 인증 필요 401, 권한 부족 403, 입력 오류 400/422, 충돌 409, 제한 413/429, 일시 장애 503을 일관되게 사용한다.
- 사용자 메시지에는 행동 가능한 해결 방법과 재시도 여부를 표시한다.
- 내부 로그에는 요청 ID와 고정된 오류 코드만 남기고 민감 payload는 기록하지 않는다.

### P2. 상태 화면과 알림

- DB 연결, 마지막 동기화, 미전송 큐, 마지막 검증 백업, 디스크 여유 공간을 관리자 상태 화면에 표시한다.
- 반복 실패는 토스트만 쌓지 말고 지속 배너와 진단 다운로드를 제공한다.
- 백업 실패, 동기화 큐 누적, DB 마이그레이션 실패는 관리자에게 명확한 경고를 표시한다.

### P2. 구조화 로그

- `console.warn/error`를 영역, 오류 코드, request ID, 발생 시각이 있는 구조화 로거로 점진 교체한다.
- 운영 로그 보존기간과 최대 크기를 제한한다.
- 민감정보 정규식 검사 테스트를 유지하고 카드번호·비밀번호·세션 쿠키 사례를 추가한다.

### 작업 안전성

- 저장 중 버튼 재진입 차단을 모든 쓰기 화면에 적용한다.
- 대량 삭제·복원·초기화는 영향 건수와 대상 브랜드를 확인하도록 한다.
- 자동저장, 저장 완료, 서버 전송 대기 상태를 구분한다.
- 미저장 이탈 방어를 노트 외 주요 편집 화면에도 동일하게 적용한다.

## 12. 이번 감사에서 변경하지 않은 것

이 문서는 발견 사항과 실행 우선순위를 정리한 감사 보고서다. 계정 DB 스키마, 인증 API, CSP, 캐시, 백업 정책 및 화면 동작은 이 문서 작성만으로 변경되지 않는다. P0·P1 항목은 각각 별도 브랜치와 마이그레이션·롤백 계획을 갖고 구현해야 한다.
