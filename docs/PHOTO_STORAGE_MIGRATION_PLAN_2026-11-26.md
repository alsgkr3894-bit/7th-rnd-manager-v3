# 사진 저장 방식 이전 계획 (점검 4단계 2번)

> 상태: **계획만 작성. 구현하지 않았고 데이터 형식도 그대로다.** (2026-11-26 사용자 결정)
>
> 대상: `docs/SITE_SECURITY_PERFORMANCE_AUDIT_2026-11-24.md` "4단계" 2번

## 1. 현재

사진은 각 업무 행 안에 글자(base64 JPEG data URL)로 들어 있다. 2026-11-26 서버 DB(main) 기준:

| 저장소 | 행 | 사진 있는 행 | 사진 수 | 사진 글자 크기 |
|---|---:|---:|---:|---:|
| `menu_dev_notes` | 328 | 252 | 471 | 123MB |
| `cost_ingredients` | 154 | 112 | 294 | 69MB |
| `sample_records` | 193 | 175 | 238 | 51MB |
| `market_research` | 83 | 79 | 168 | 23MB |
| `menu_master` | 95 | 51 | 51 | 10MB |
| 합계 | | | 1,222 | 약 276MB |

`menu_master`·`cost_ingredients`는 원가·표시 화면이 자주 통째로 읽는 저장소라, 사진이 없어도 되는 화면까지 함께 읽는다.

## 2. 옮기면 달라지는 것

| 항목 | 예상 | 근거 |
|---|---|---|
| 화면 메모리 | 식자재·메뉴를 읽는 화면에서 약 80MB 감소 | 3단계에서 보관한 `cost_ingredients`가 홈 힙 증가(약 62MB)의 대부분 |
| 전체 조회 시간 | 사진 저장소의 조회가 짧아짐 | 행 크기가 KB 단위가 됨 |
| 저장·동기화 | 글자만 고쳐도 사진을 다시 보내지 않음 | 지금은 행 전체(최대 2.4MB)를 다시 보냄 |
| 백업 크기 | 크게 줄지 않음 | 압축 뒤에는 base64와 원본 JPEG의 차이가 작다 |

## 3. 권장 구조

- 브라우저: 새 저장소 `attachments` — `{ id, hash, mime, width, height, bytes, blob, createdAt }`. 업무 행의 사진은 `{ attachmentId, name, caption, uploadedAt }`.
- 서버: 별도 표 `attachments(brand_id, id, hash, mime, bytes bytea)`와 업로드·내려받기 API. 업무 행 동기화에는 사진이 없다.
- 같은 사진은 `hash`로 한 번만 저장한다(지금 일지·노트는 data 글자 비교로 중복을 거른다 — `app/note/journal/journalPhotos.js`).

대안: 서버에도 지금처럼 행(JSON)에 base64로 저장하고 브라우저만 바꾸는 방법은 서버 쪽 작업이 없지만, 동기화·서버 메모리 문제가 남는다. 파일 시스템 저장은 DB 백업 하나로 복구할 수 없게 되어 권장하지 않는다.

## 4. 영향 범위

`.photo`/`.photos`를 읽는 파일 약 52개: 화면 약 33, 계산·저장(lib) 약 12, 인쇄·보고서 8(`lib/note/report-print/*`, `lib/note/journal-print*.js`, `lib/sample/report-print.js`, `lib/ingredient/manage-print/*`). 그 밖에 백업 형식·복원 검증, 서버 전체 재전송, 시제품 복구 화면, 식자재 중복 병합, 브랜드 백업.

## 5. 순서

각 단계는 따로 배포하고, 앞 단계가 확인된 뒤에 다음으로 간다.

| 순서 | 내용 | 형식 변경 | 되돌리기 |
|---|---|---|---|
| 1 | 사진을 읽는 곳을 한 함수(`photoSrc(photo)`)로 모음. `data`와 `attachmentId`를 모두 이해 | 없음 | 코드만 되돌림 |
| 2 | 백업 파일에 첨부를 담고 복원 검증에 사진 수·hash 대조 추가. 서버 표·API 추가 | 서버 표 추가 | 표를 비워 두면 영향 없음 |
| 3 | DB v30에 `attachments` 추가, **새 사진부터** 새 형식 | 있음 | 아래 6절 |
| 4 | 기존 사진을 50장씩 옮김. 중단해도 이어서 실행. 옮긴 행은 hash를 대조한 뒤에만 `data` 제거 | 있음 | 이전 직전 백업 복원 |
| 5 | 옛 형식 읽기 유지(예전 백업 복원용) | | |

## 6. 되돌리기와 위험

- **DB 버전을 올리면 이전 버전 앱은 브라우저 DB를 열지 못한다.** 순서 3을 배포한 뒤에 되돌려야 하면 `DB_VERSION=30`을 유지한 채 코드만 되돌리는 배포를 미리 준비한다.
- 순서 4를 마친 뒤에는 이전 버전 앱이 사진을 읽지 못한다. 되돌리려면 이전 직전의 브라우저 백업과 DB 백업을 복원해야 하고, 그 뒤의 수정은 사라진다.
- 서버에 보내지 못한 사진이 있으면 이전을 시작하지 않는다.
- LAN 뷰어 PC는 불러오기를 다시 해야 한다.
- Blob URL은 화면을 벗어날 때 해제해야 한다. 인쇄는 별도 창이라 인쇄가 끝날 때까지 유지해야 한다.

## 7. 완료 기준

- 이전 전후에 사진 수와 hash 목록이 같다(1,222장 기준으로 다시 센 값).
- 모든 화면·인쇄·Excel에서 사진이 이전과 같게 보인다.
- 새 형식 백업을 빈 브라우저와 임시 서버에 복원해 같은 결과가 나온다. 예전 백업도 복원된다.
- 이전 중 강제 종료 후 다시 실행해도 유실·중복이 없다.

## 8. 시작 전에 정할 것

1. 서버에 사진을 DB 표(권장)와 파일 중 어디에 둘지
2. 이전 직전 백업과 원본 `data`를 얼마나 보관할지
3. 다른 디스크의 백업 위치 (0단계에서 남은 항목 — 이전 전에 먼저 해야 한다)
