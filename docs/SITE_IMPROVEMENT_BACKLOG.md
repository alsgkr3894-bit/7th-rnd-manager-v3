### P0. clean build 실패 원인 고정 — 완료

**현재 상태**
- 후속 확인에서 `npm run build:clean`과 `npm run build`가 모두 57 pages로 통과했다.
- `scripts/clean-build.mjs`는 build 성공/실패와 무관하게 `.next.stale-*`를 `finally`에서 정리한다.
- 실제 `build:clean` 실행 후 stale 디렉터리가 남지 않는 것을 확인했다.

**개선 방향**
- 권장 Node 버전을 확정하면 해당 버전에서 release checklist로 `build:clean`을 반복 검증한다.
- dev 서버가 떠 있는 상태에서 build/clean/build가 겹치지 않도록 현재 가드와 문서를 유지한다.

**성공 기준**
- `npm run build:clean`과 `npm run build`가 동일 환경에서 안정적으로 통과한다. 현재 충족.
- 실패하더라도 `.next.stale-*` 누적 여부와 복구 방법이 명확하다. 현재 충족.

### P0. dev `.next` chunk 충돌 방지

**현재 상태**

**개선 방향**

- 3000 포트 외부 접속 기준(`dev:lan`)과 로컬 QA 기준을 문서화한다.

### P1. smoke QA 스크립트 신뢰성 복구

**현재 상태**
- `scripts/smoke-qa.mjs`는 하나의 page를 모든 라우트에 재사용한다.
- Next dev RSC/Fast Refresh console error가 직전 라우트에서 다음 라우트로 오염될 수 있다.
- `/menu-sales/rank`는 307 redirect로 `/menu-sales/rank-compare`로 이동한다.
- 현재 smoke 대표 route는 최종 목적지인 `/menu-sales/rank-compare`로 정리됐다.

**개선 방향**
- smoke 라우트마다 새 page를 생성하거나, route 간 console/error listener 상태를 완전히 격리한다.
- RSC fallback console error가 false positive인지 분리 규칙을 둔다.
- smoke 대상 route는 실제 목적지 기준을 유지한다. redirect route 자체 검증은 `qa:runtime`에서 별도로 확인한다.

**성공 기준**
- 같은 dev 서버 상태에서 smoke 결과가 반복 실행해도 안정적으로 같다.
- 실제 UI 정상인데 QA만 실패하는 false positive가 줄어든다.

### P1. `qa:runtime` 전체 라우트 검증 안정화

**현재 상태**
- `scripts/full-rt.mjs`는 Playwright browser health check, `localhost` → `127.0.0.1` fallback, route별 `fatal` 기록을 갖췄다.
- 정적/주요 브랜드 runtime 순회는 `npm run qa:runtime` 63/63 통과로 기준선이 회복됐다.
- smoke QA는 빠른 대표 라우트 확인용이고, 동적 edit/detail 라우트와 실업무 fixture 흐름은 아직 충분히 보장하지는 않는다.

**개선 방향**
- 동적 상세 라우트는 seed fixture를 넣은 뒤 별도 케이스로 검증한다.
- `app/**/page.jsx` 기준 라우트 목록과 QA 대상 목록을 비교하는 route drift 테스트를 추가한다.
- redirect 전용 라우트(`/settings` 등)와 인증 전용 라우트(`/login`)는 제외 사유를 명시한다.

**성공 기준**
- dev 서버가 떠 있으면 `npm run qa:runtime`이 전체 정적/주요 브랜드 라우트 결과를 끝까지 출력한다.
- 동적 상세/수정 화면은 seed fixture 기반으로 최소 1회 이상 진입 검증된다.
- 신규 정적 라우트가 생겼는데 QA 목록에서 빠지면 테스트가 실패한다.

### P2. console-only/silent catch 정리

**현재 상태**
- 버그 감사 문서 기준 `console.error`, `console.warn`, `.catch(() => {})` 계열이 많다.
- 일부는 의도된 background 작업이지만, 사용자 액션 실패와 섞여 있다.

**개선 방향**
- 사용자 클릭/저장/삭제/복원/출력에서 시작된 실패는 toast나 화면 오류 상태로 노출한다.
- background hydrate, optional log, cleanup 실패는 의도 주석 또는 helper로 분리한다.
- 동일 패턴을 `reportErrorForUserAction`, `ignoreBackgroundError` 같은 작은 helper로 정리한다.

**성공 기준**
- 사용자가 실행한 작업이 실패했는데 아무 안내가 없는 케이스가 줄어든다.
- 의도적으로 무시하는 오류는 코드에서 이유가 보인다.

### P2. 데이터 id/key fallback 안정화 — 완료

**현재 상태**

**성공 기준**

## 4. 성능·반응속도 개선

### P1. 홈 대시보드 통계 조회 단일화

**현재 상태**
- `hooks/useHomeDashboardData.js`로 홈 로딩 책임은 분리되어 있다.
- 다만 내부에서는 `getSalesKpi`, `getSalesTrend`, `getCategoryShare`, `getTopMenusWithTrend`, `getMonthlyBriefing`이 각각 `sales_rows`를 읽는 구조가 남아 있다.
- 노트/샘플/원가/이슈도 홈 첫 진입 때 한꺼번에 많이 조회한다.

**개선 방향**
- `getHomeDashboardStats({ anchor, chartTab, rankCategory })` 같은 단일 집계 API를 만든다.
- `sales_rows`는 한 번만 읽고 KPI, 트렌드, 카테고리 비중, 베스트/워스트, 브리핑을 한 번에 계산한다.
- 홈 위젯 설정에서 숨긴 위젯은 데이터 조회도 생략한다.
- 첫 화면 필수 데이터와 아래쪽 위젯 데이터를 분리한다.

**성공 기준**
- 홈 진입 시 `sales_rows` 전체 조회가 1회로 줄어든다.
- 숨긴 위젯의 통계 함수는 호출되지 않는다.
- 새로고침 후 인사말/핵심 KPI가 먼저 표시되고, 나머지 위젯은 순차 로딩된다.

**현재 상태**

### P1. 대형 표 페이지네이션·검색 최적화

**대상**
- `app/ingredient/usage/page.jsx`
- `app/nutrition/allergen/page.jsx`
- `app/nutrition/origin/page.jsx`
- `app/report/sales/page.jsx`
- `app/report/menu-sales-compare/page.jsx`

**현재 상태**
- 식자재 리스트/메뉴마스터 등 일부 화면은 pagination이 적용되어 있다.
- 제품별 사용현황은 `displayRows.map(...)`로 전체 행을 렌더한다.
- 알레르기/원산지도 집계는 분리됐지만, 화면 렌더와 검색 결과는 대량 데이터에서 무거워질 수 있다.

**개선 방향**
- 공통 `usePagination` 또는 lightweight windowing을 적용한다.
- 검색어는 `useDebounce` 또는 `useDeferredValue`로 처리한다.
- 검색용 normalize 문자열을 row 생성 단계에서 캐시한다.
- 전체 펼치기 기능은 현재 화면/현재 필터 범위만 대상으로 제한하거나, 대량 행일 때 확인을 띄운다.

**성공 기준**
- 1천/1만 행 테스트 데이터에서 검색 입력 중 화면 멈춤이 없다.
- 1천/1만 행 기준의 렌더 시간, 검색 응답, 출력 생성 시간을 QA 기록으로 남긴다.
- 페이지네이션/출력/CSV 대상 범위가 UI에 명확히 표시된다.

### P2. 시각 효과 비용 관리

**현재 상태**
- `useVisualEffects`가 전역 click ripple과 card tilt를 처리한다.
- 체감 UX에는 좋지만 저사양 기기나 큰 화면에서 이벤트 비용이 생길 수 있다.

**개선 방향**
- 사용자 설정에 "애니메이션 최소화" 옵션을 추가한다.
- `prefers-reduced-motion`을 감지해 ripple/tilt를 끈다.
- 카드 tilt는 `.card-lift`가 실제 필요한 카드에만 제한한다.

**성공 기준**
- 설정 변경 즉시 시각 효과가 켜지고 꺼진다.
- 접근성 설정이 켜진 환경에서는 불필요한 모션이 줄어든다.

## 9. 테스트·QA 체계 개선

### 자동 테스트 추가 후보

- `build:clean`: clean build 성공, 실패 시 stale cleanup/안내 유지
- `dev/prepare-dev`: stale `.next` 상태에서 dev 재시작 후 정적 리소스 500 미발생 확인
- `smoke-qa`: route 간 console error 오염 방지, redirect route 정책 확인
- `qa:runtime`: 서버 health check, 전체 정적 라우트 유지, seed 기반 동적 상세 라우트 검증
- route drift: `app/**/page.*`와 runtime/smoke 대상 목록을 비교하고, 제외 라우트는 사유를 문서화
- `format:check`: format 기준선 유지
- random id/key guard: 데이터 id/key fallback에서 `Math.random()` 재도입 방지
- 실업무 Excel fixture 확대: 기존 `business-fixtures.test.mjs`의 파서/계산 fixture를 저장·중복 차단·다운로드 헤더·보고서 출력 검증까지 확장
- 홈 통계 단일 조회: 같은 store를 반복 조회하지 않는지 mock으로 확인
- `usePageStats`: pathname 변경만으로 전체 노트 재조회가 반복되지 않는지 확인
- 제품별 사용현황: 피자/사이드 메뉴 수, 숨김/복원, 제외 메뉴 localStorage 처리
- 원산지/알레르기: 메뉴마스터 순서, 메뉴명 override, 제외 메뉴 반영
- 영양성분: 파생메뉴, 추가토핑, 식자재 영양값, 출력 반영
- 출력 파일명: 한글명 + 날짜 suffix, 백업/복원 임시백업 이름
- Excel: sheet name 금지문자/31자/중복 처리
- PDF/인쇄: 사진 contain, 긴 텍스트 page-break, 다운로드 날짜 표시

3. 식자재 등록/사진 3종 추가 → 식자재 리스트 PDF 출력
4. 원가 레시피 입력 → 원가마진표 → 원가보고서 출력
5. 영양성분 베이스/파생/토핑 입력 → 영양성분표/알레르기/원산지 출력
6. 일정 체크리스트 완료 → 연구일지/달력 반영 확인
7. 백업 생성 → 선택 복원 → 임시백업 파일 확인
8. 비-main 브랜드에서 공유 DB와 브랜드 DB 데이터가 의도대로 보이는지 확인
9. stale `.next`가 있는 상태에서 dev 서버를 재시작해 chunk 오류가 없는지 확인
10. smoke QA를 2회 연속 실행해 결과가 흔들리지 않는지 확인
11. seed fixture로 노트/샘플/보고서/메뉴 상세 동적 라우트에 직접 진입해 오류가 없는지 확인

## 10. 우선 실행 백로그: 데이터 손상·정합성·UX 안전성

> 기준: 지금까지 조사/수정/검증한 항목을 "무엇을 해야 하는지"와 "왜 해야 하는지" 중심으로 재정리했다.
> 주의: 아래 항목은 실행 후보이며, 실제 수정은 업무 데이터/실파일 QA와 사용자 승인 후 진행한다.

### 1순위: 데이터 손상 방지

| 항목 | 해야 할 내용 | 해야 하는 이유 |
|---|---|---|
| 백업 export 실패 처리 | store 조회 실패 시 `[]`로 백업하지 말고 백업 생성을 실패 처리하거나 오류 manifest를 넣어 복원을 막기 | 조회 실패가 빈 데이터로 저장되면, 나중에 복원할 때 정상 데이터가 삭제될 수 있음 |
| 대용량 복원 보완 | 500건 초과 store 복원 시 사전 검증, 롤백, 부분 실패 차단 추가 | 현재는 `clear()` 후 청크 저장이라 중간 실패 시 데이터가 일부만 남을 수 있음 |
| 부분 복원 범위 안내 수정 | 항상 포함되는 공통 store를 UI에 명확히 표시하거나 별도 선택 가능하게 변경 | 사용자는 "선택한 모듈만 복원"한다고 생각하지만 설정/메뉴마스터/보고서도 바뀔 수 있음 |
| 보고서 자동 삭제 제거 | 보고서센터 진입 시 자동 삭제하지 말고 정리 후보 미리보기/확인 후 삭제로 변경 | 오래된 보고서가 사용자 모르게 사라질 수 있음 |
| 메뉴판매량 자동 재분류 분리 | 규칙 저장과 기존 업로드 재분류를 분리하고, 영향 범위 확인 후 실행 | 과거 매출 보고 기준이 조용히 바뀌면 이전 보고서와 현재 결과가 달라질 수 있음 |
| 메뉴 마스터 삭제 동기화 | `menu_master` 삭제 시 판매가 미러 데이터도 같이 정리하거나 tombstone 정책 적용 | 판매가 데이터가 남아 삭제한 메뉴가 다시 생성될 수 있음 |

### 2순위: 코드 연결성·정합성

| 항목 | 해야 할 내용 | 해야 하는 이유 |
|---|---|---|
| 영양 메뉴/원시값 중복 방지 | `menuCode`, `menuCode + crustType` 기준 중복 저장 차단/정리 | 중복이 있으면 마지막 값이 앞 값을 덮어 영양성분표가 틀릴 수 있음 |
| 알레르기 링크 기준 정리 | `nutrition_allergy_links`를 메뉴 기준인지 식자재 기준인지 확정하고 스키마/삭제 로직 통일 | 현재 주석/인덱스와 실제 코드 기준이 다르면 삭제·집계가 엇갈릴 수 있음 |
| 식자재 `productCode` 중복 정리 | 저장/가져오기 시 중복 차단, 기존 중복 진단/병합 UI 추가 | 같은 제품코드가 여러 행이면 가격, 영양값, 알레르기 연결이 어느 행을 기준으로 하는지 불명확함 |
| 합산 식자재 가격 정책 통일 | `compositeOf` 가격 계산을 공통 유틸로 통합 | 화면마다 같은 식자재 가격이 다르게 보이면 원가율/마진 계산 신뢰도가 떨어짐 |
| 원가 detail 인덱스 통일 | personal/side/set detail store에도 `menuCode` 인덱스와 마이그레이션 추가 | 로직은 `menuCode` 기준인데 DB 인덱스가 없으면 조회·진단·중복 관리가 불안정함 |
| 메뉴코드 base/full 정책 명시 | 영양/원가/판매가별 `menuCode` 처리 기준을 명시하고 유틸화 | 어떤 화면은 사이즈 제거 코드, 어떤 화면은 전체 코드가 필요해서 잘못 연결될 수 있음 |
| 피자 카테고리 판정 공통화 | `isPizzaCategory()` 같은 공통 기준 도입 | 엣지/도우, 영양, 식자재 사용처가 서로 다른 카테고리 기준을 쓰면 집계 누락 발생 |
| 업로드 파일 중복 코드 진단 | 제때 가격/식자재 단가 업로드 시 중복 `productCode` 표시 및 차단 | 같은 코드가 여러 번 있으면 마지막 행으로 조용히 덮이고 이력도 왜곡될 수 있음 |

### 4순위: 화면·내보내기·품질 게이트

| 항목 | 해야 할 내용 | 해야 하는 이유 |
|---|---|---|

## 13. 완료 처리 기준

각 항목을 완료로 판단하려면 다음 증거가 필요하다.

- 관련 코드와 테스트가 현재 worktree에 존재한다.
- `npm run format:check`가 통과하거나, format 미적용 범위와 이유가 문서화되어 있다.
- `npm run lint`, `npm run test:ci`가 통과한다.
- 빌드/운영 기준선 영향이 있으면 `npm run build:clean`과 `npm run build` 결과가 있다.
- UI 영향이 있으면 `npm run qa:smoke` 또는 관련 route 수동 확인 결과가 있다.
- 출력물 영향이 있으면 PDF/Excel/CSV 실제 파일을 열어 확인했다.
- 데이터 마이그레이션/백업 영향이 있으면 기존 백업 파일 복원 케이스를 확인했다.
- 완료 항목은 `docs/DEFERRED_WORK.md` 또는 별도 작업 이력에 완료일과 검증 명령을 남긴다.
