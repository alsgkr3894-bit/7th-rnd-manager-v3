# 메뉴마스터 통합 계획

작성: 2026-06-15
상태: 메뉴마스터 통합 계획 범위 구현 완료
전제: 기존 데이터는 가능하면 살리되, 통합 과정에서 기준 충돌이나 품질 문제가 크면 초기화 후 새 기준으로 다시 입력할 수 있다.

---

## 1. 결정 요약

메뉴마스터, 레시피마스터, 원가레시피는 사용자 관점에서 하나의 흐름으로 합친다.

최종 구조는 **메뉴마스터를 단일 진입점**으로 두고, 메뉴별 상세 안에서 기본정보, 판매가, 레시피, 원가 계산 결과를 함께 관리하는 방식이다.

```text
메뉴마스터
 ├─ 메뉴 기본정보
 ├─ 판매가
 ├─ 레시피
 ├─ 원가 자동계산
 └─ 원산지/알레르기/영양 연결
```

현재 별도 메뉴로 보이는 레시피마스터와 원가레시피는 장기적으로 메뉴마스터 안으로 흡수한다.

---

## 2. 현재 문제

현재 메뉴 관련 데이터 입력 흐름은 기능별로 나뉘어 있다.

```text
메뉴마스터
레시피마스터
원가레시피
재료 단가표
원가마진표
영양성분/원산지/알레르기
```

이 구조에서는 사용자가 메뉴 하나를 만들 때 다음 질문이 생긴다.

- 메뉴는 어디서 만들고, 레시피는 어디서 입력해야 하는가?
- 레시피마스터와 원가레시피 중 어느 쪽이 실제 기준인가?
- 원가마진표, 원산지, 알레르기, 제품별 사용현황이 같은 레시피를 보고 있는가?

구형 데이터 유지가 필요 없다면, 이 복잡도를 계속 가져갈 이유가 적다.

---

## 3. 목표 구조

### 3.1 사용자 화면 기준

```text
/menu-master
 ├─ 메뉴 목록
 ├─ 메뉴 추가/수정
 └─ 메뉴 상세
     ├─ 기본정보
     ├─ 판매가
     ├─ 레시피
     ├─ 원가 계산
     └─ 영양/원산지/알레르기 연결 상태
```

### 3.2 유지할 화면

| 화면 | 방향 |
|------|------|
| `/menu-master` | 메인 메뉴 관리 화면으로 유지 |
| `/cost/margin` | 원가마진표 결과/분석 화면으로 유지 |
| `/ingredient/manage?view=price` | 식자재관리 안의 단가 탭으로 유지 |
| `/nutrition/*` | 메뉴마스터와 레시피 기준을 읽는 출력/관리 화면으로 유지 |

### 3.3 축소 또는 제거할 화면

| 화면 | 방향 |
|------|------|
| `/cost/recipe-master` | 메뉴마스터 상세의 레시피 영역으로 흡수 |
| `/cost/recipe` | 제거하거나 공통묶음/엣지 관리만 남김 |
| 기존 구형 레시피 입력 UI | 새 기준 입력 완료 후 제거 |

## 4. 데이터 기준

### 4.1 메뉴 기본정보

메뉴 기준은 `menu_master`가 가진다.

```text
menu_master
  - brandId
  - menuCode
  - menuName
  - category
  - size
  - price
  - status
  - displayOrder
  - hidden
  - excludeFromOrigin
  - displayGroupKey
```

모든 메뉴 기준 키는 `brandId` 범위 안에서만 고유해야 한다. 브랜드가 다르면 같은 `menuCode`나 `displayGroupKey`가 있어도 별도 메뉴로 본다.

`displayGroupKey`는 원산지/알레르기처럼 사이즈와 무관하게 단일 출력해야 하는 메뉴 묶음 기준이다. 예를 들어 같은 메뉴의 L/R은 각각 다른 `menuCode`를 가지더라도 같은 `displayGroupKey`를 공유한다.

`displayGroupKey`는 별도 화면 탭이 아니라 **메뉴 기본정보 안의 표기그룹 필드**다. 기본값은 자동 생성하고, 예외 메뉴만 고급 설정에서 수동 수정할 수 있게 한다.

추천 생성 규칙:

| 메뉴 유형 | `displayGroupKey` 추천 |
|-----------|------------------------|
| 일반 단일 메뉴 | `menuCode` |
| L/R처럼 사이즈가 나뉜 메뉴 | 사이즈 suffix를 제거한 공통 코드 |
| 코드 규칙으로 묶기 어려운 L/R 메뉴 | 정규화한 메뉴명 |
| 하프앤하프 | 기본은 개별 메뉴, 예외는 수동 그룹 지정 |
| 세트 | 기본은 개별 메뉴 |
| 엣지/토핑/추가옵션 | 기본은 개별 메뉴 또는 출력 제외 정책 적용 |

예시:

```text
PZ-001-L → PZ-001
PZ-001-R → PZ-001

displayGroupKey = PZ-001
```

브랜드 분리 원칙:

- 브랜드는 별도 운영 단위로 본다.
- 메뉴, 레시피, 판매가, 원가, 영양성분, 원산지, 알레르기, 판매량, 제때/식자재 연결은 모두 `brandId` 기준으로 분리한다.
- 브랜드를 전환하면 목록, 계산, 출력, 백업 대상도 함께 바뀐다.
- 브랜드 간 복사가 필요하면 신규 생성 복사로 처리하고, 원본 브랜드 데이터와 연결하지 않는다.
- 브랜드 추가/수정/숨김/기본 브랜드 선택은 `설정/백업 > 브랜드마스터`에서 관리한다.
- 브랜드 전환은 앱 상단에 고정된 브랜드 선택기로 처리한다.
- 숨김 브랜드는 상단 전환 목록과 신규 입력 기본값에서 제외하되, 기존 데이터와 백업/복원 대상에서는 유지한다.
- `displayGroupKey` 중복/충돌 검사는 같은 브랜드 안에서만 수행한다.

### 4.2 새 레시피 기준

구형 `cost_recipes`와 카테고리별 상세 레시피를 계속 병행하지 않고, 새 기준 저장소 하나로 단순화하는 방향이 좋다.

예상 형태:

```text
menu_recipes
  - id
  - brandId
  - menuCode
  - displayGroupKey
  - components[]
      - productCode
      - ingredientName
      - quantity
      - unit
      - note
  - updatedAt
```

핵심은 모든 후속 화면이 `brandId + menuCode` 기준으로 같은 레시피를 읽는 것이다. `displayGroupKey`는 원산지/알레르기 출력 묶음용이지 레시피 저장 기준이 아니다.

```text
menu_master + menu_recipes
 → 원가마진표
 → 제품별 사용현황
 → 원산지 정보
 → 알레르기 정보
 → 표 출력
```

### 4.3 사이즈별/단일 출력 기준

출력과 계산 기준은 성격에 따라 분리한다.

| 항목 | 기준 | 이유 |
|------|------|------|
| 원가 | `menuCode` | L/R처럼 사이즈별 사용량과 판매가가 다르다. |
| 영양성분 | `menuCode` | 사이즈별 중량과 영양값이 다르다. |
| 원산지 | `displayGroupKey` | 같은 메뉴의 L/R은 원산지를 단일 메뉴명으로 출력해야 한다. |
| 알레르기 | `displayGroupKey` | 같은 메뉴의 L/R은 알레르기를 단일 메뉴명으로 출력해야 한다. |
| 엣지 파생 알레르기 | `displayGroupKey + edgeCode` | 엣지별 포함 식자재와 알레르기가 다를 수 있다. |
| 엣지 파생 영양성분 | `menuCode + edgeCode` | 기본 메뉴 영양값에 엣지 조정값을 반영해야 한다. |

예시:

```text
슈퍼콤비네이션 L
슈퍼콤비네이션 R

원가/영양성분:
  - 슈퍼콤비네이션 L 별도
  - 슈퍼콤비네이션 R 별도

원산지/알레르기:
  - 슈퍼콤비네이션 단일 출력
```

원산지/알레르기 단일 출력 시에는 같은 `brandId + displayGroupKey`에 속한 레시피의 식자재를 합산하고 중복 제거한다.

단, 엣지처럼 선택 옵션에 따라 알레르기가 달라지는 경우는 단일 메뉴 출력과 별도로 **메뉴명 + 엣지명** 출력행을 만든다.

```text
기본 출력:
  - 슈퍼콤비네이션

엣지 파생 출력:
  - 슈퍼콤비네이션 치즈크러스트
  - 슈퍼콤비네이션 골드링
```

엣지 파생 알레르기는 기본 메뉴 레시피 식자재와 해당 엣지 레시피 식자재의 알레르기를 합산한다. 엣지별 알레르기가 다르면 `brandId + displayGroupKey + edgeCode` 기준으로 별도 출력한다.

### 4.4 레시피 단위 기준

레시피 구성품 입력 단위는 `g`, `개` 두 가지만 허용한다.

| 단위 | 사용 기준 |
|------|-----------|
| `g` | 중량 기준 식자재 |
| `개` | 낱개, 장, 봉, 통처럼 개수 기준으로 관리할 식자재 |

`kg`, `ml`, `L`, `ea` 등은 레시피 입력 단위로 쓰지 않는다. 구매/제때 데이터가 다른 단위로 들어오면 식자재마스터의 기준수량과 환산 기준에서 `g` 또는 `개`로 정리한다.

`g` 단가 환산 결과는 소수점 1자리에서 반올림한다. 원가 계산은 이 확정된 1자리 `g` 단가를 기준으로 진행한다.

환산할 수 없는 식자재는 원가 계산에 조용히 포함하지 않고, 단위 미확정으로 표시한 뒤 레시피 저장 또는 원가 발행을 차단한다.

### 4.5 가격 기준

판매가와 식자재 단가는 다음 기준으로 고정한다.

```text
판매가 = menu_master.price

식자재 유효 단가
  1. 제때 productCode가 있고 최신 제때 단가가 있으면 최신 제때 단가
  2. 제때 productCode가 없거나 최신 제때 단가가 없으면 식자재 수동 입력 단가
```

레시피에는 단가 스냅샷을 주 기준으로 저장하지 않는다. 원가 계산은 최신 유효 단가를 기준으로 다시 계산한다. 단가 변경 이력이나 과거 원가 보존이 필요할 때만 별도 스냅샷/히스토리 기능을 둔다.

제때 단가 fallback 세부 규칙:

| 상태 | 처리 |
|------|------|
| `productCode`가 있고 최신 제때 파일에 단가가 있음 | 제때 최신 단가 사용 |
| `productCode`가 있으나 최신 제때 파일에 없음 | 식자재 수동 단가 사용 |
| `productCode`가 없고 수동 단가가 있음 | 식자재 수동 단가 사용 |
| 제때 단가와 수동 단가가 모두 없음 | 단가 미확정으로 표시하고 원가 계산/발행 차단 |
| 기준수량 `baseQuantity`가 없음 | 개당/g당 단가 계산 불가로 표시하고 원가 계산/발행 차단 |

단가 미확정 항목은 조용히 0원 처리하지 않는다. 메뉴 상세와 식자재관리 양쪽에서 누락 경고를 보여준다.

### 4.6 영양성분 기준

영양성분 출력은 **메뉴 기준 직접 입력값을 최우선**으로 한다.

```text
1순위: 메뉴별/사이즈별 영양성분 직접 입력값
2순위: 없음
```

식자재 영양값 기반 자동계산 기능은 제거됐다. 영양성분은 법적/표기 영향이 크므로 자동계산 결과를 최종값으로 쓰지 않는다.

엣지 파생 영양성분은 기본 메뉴 영양값을 기준으로, 기본 엣지 4종의 사이즈별 조정값을 별도 입력해 만든다.

```text
기본 메뉴 영양성분 = menuCode 직접 입력값
엣지 파생 영양성분 = 기본 메뉴 영양성분 + edgeNutritionAdjustment
출력명 = 메뉴명 + 엣지명
```

추천 저장 기준:

| 데이터 | 기준 |
|--------|------|
| 기본 메뉴 영양성분 | `brandId + menuCode` |
| 엣지 조정값 | `brandId + size + edgeCode` |
| 메뉴별 엣지 override | `brandId + menuCode + edgeCode` |
| 엣지 파생 출력 | `brandId + menuCode + edgeCode` |

기본 엣지마스터:

| 엣지명 | 사이즈 | 영양성분 기준 |
|--------|--------|---------------|
| 석쇠 | L, R | 사이즈별 조정값 직접 입력 |
| 치즈크러스트 | L, R | 사이즈별 조정값 직접 입력 |
| 골드스윗 | L, R | 사이즈별 조정값 직접 입력 |
| 씬바샤삭 | L 전용 | L 사이즈 조정값 직접 입력 |

엣지 영양값은 식자재 영양 자동계산으로 만들지 않고 직접 입력/검수한다. 기본은 사이즈별 엣지 조정값을 사용하고, 특정 메뉴에서만 값이 달라지면 메뉴별 override를 둔다. 기본 메뉴에 기본 엣지 영양값이 이미 포함되어 있다면, 엣지 조정값은 "선택 엣지값 - 기본 엣지값"의 차이값으로 저장한다.

`씬바샤삭` 엣지는 L 사이즈 피자용 엣지로만 관리한다. `1인용 씬바샤삭`은 별도 메뉴/별도 영양성분 기준으로 관리하고, 이 엣지마스터의 `씬바샤삭`과 자동 연결하지 않는다.

## 5. 구현 단계

### Phase 1. 메뉴마스터 상세 구조 만들기

상태: **구현 완료**
관련 커밋: `5781532 feat: surface menu recipe cost status`, `22ef420 feat: align recipe master cost units`

- 메뉴마스터에서 메뉴를 선택하면 상세 영역을 연다.
- 상세 안에 기본정보, 판매가, 레시피, 원가 계산 탭을 둔다.
- 기존 메뉴마스터 목록은 유지한다.
- 레시피 입력은 메뉴 상세 안에서 가능하게 한다.

완료 기준:

- 메뉴 하나를 만들고 같은 화면에서 레시피까지 입력할 수 있다.
- 사용자는 레시피마스터 화면으로 이동하지 않아도 된다.

구현 메모:

- 메뉴마스터 편집 모달 안에서 레시피 구성품을 입력/저장할 수 있게 했다.
- 메뉴마스터 목록에 `레시피/원가` 상태와 원가율 요약을 표시한다.
- 레시피 입력 단위는 `g`, `개`로 제한했고 최신 유효 단가를 우선 반영한다.

### Phase 2. 새 레시피 저장소 도입

상태: **구현 완료**
관련 커밋: `0c72c95 feat: introduce canonical menu recipes`

- 새 `menu_recipes` 저장소 또는 동등한 단일 레시피 기준을 만든다.
- 브랜드 안에서 메뉴코드 1개당 레시피 1개를 기본 정책으로 둔다.
- L/R처럼 사이즈가 다른 메뉴는 메뉴코드별로 레시피를 따로 가진다.
- 원산지/알레르기 출력은 `displayGroupKey`로 다시 묶는다.
- 피자, 1인피자, 사이드, 세트 모두 같은 레시피 구조를 사용한다.
- 카테고리별 차이는 UI와 계산 표시에서만 처리한다.

완료 기준:

- 새로 입력한 메뉴/레시피는 구형 `cost_recipes` 또는 카테고리별 상세 store에 의존하지 않는다.

구현 메모:

- `menu_recipes` IndexedDB store를 추가하고 백업 범위에 포함했다.
- 메뉴마스터와 레시피마스터 저장은 `menu_recipes`를 canonical 기준으로 사용한다.
- 기존 카테고리별 detail store와 구형 `cost_recipes`는 DB v22에서 제거했다.
- 개발 모드 중복 로드에서도 `menuCode` unique 충돌이 나지 않도록 `menu_recipes` upsert를 단일 transaction 기준으로 정리했다.

### Phase 3. 계산/출력 화면 연결 변경

상태: **구현 완료**
관련 커밋: `4767b9e feat: read canonical recipes in output flows`

완료 기준:

- 같은 메뉴의 레시피가 화면마다 다르게 보이지 않는다.
- 식자재 사용 메뉴 수, 원산지, 알레르기, 원가가 같은 레시피 기준으로 계산된다.

구현 메모:

- 원가마진표, 원가 전체요약, 원가 보고서가 `menu_recipes`를 우선 읽도록 연결했다.
- 제품별 사용현황, 원산지 정보, 알레르기 정보, 영양/원산지 표 출력이 단일 레시피 기준을 공유한다.

### Phase 4. 기존 화면 정리

상태: **구현 완료**

완료 기준:

구현 메모:

- `/cost/recipe-master`와 구형 카테고리별 원가 편집 route는 새 기준 화면으로 redirect한다.
- `/cost/recipe`는 메뉴별 레시피 입력을 제거하고 공통묶음/엣지 관리만 남겼다.

- 더 이상 사용하지 않는 legacy cost editor 컴포넌트와 hook을 제거했다.
- redirect 이후 사용하지 않는 레시피마스터 전용 hook, form/table 컴포넌트, data/rows helper도 제거했다.

## 7. 정책 메모

### 7.1 브랜드

- 모든 운영 데이터는 브랜드별로 분리한다.
- 메뉴코드, 표기그룹, 레시피, 영양성분, 원산지, 알레르기, 판매량, 제때 연결은 브랜드 범위 안에서만 연결한다.
- 브랜드 간 데이터 공유는 기본적으로 금지하고, 필요하면 복사 기능으로만 처리한다.
- 브랜드마스터는 `설정/백업` 영역에 둔다.
- 브랜드마스터에서는 브랜드 추가, 수정, 숨김, 기본 브랜드 선택, 브랜드별 백업, 브랜드별 복원을 처리한다.
- 앱 상단에는 현재 브랜드를 항상 볼 수 있는 고정 브랜드 선택기를 둔다.
- 전체 백업/복원은 시스템 백업에서 유지하고, 브랜드별 백업/복원은 브랜드마스터에서 바로 실행할 수 있게 한다.
- 브랜드별 복원은 기존 브랜드 데이터를 덮어쓰는 방식으로 처리한다.
- 브랜드마스터와 복원/덮어쓰기 작업은 관리자만 실행할 수 있다.

### 7.2 메뉴코드

- 메뉴코드는 모든 연결의 기준이다.
- 메뉴명 변경은 허용하되, 메뉴코드는 가능한 한 유지한다.
- 운영 화면에서는 기존 메뉴코드를 읽기전용으로 유지한다.
- 내부/복구 경로에서 메뉴코드가 변경되는 경우 `menu_master`, `cost_selling_prices`, `menu_recipes`, `nutrition_menu_ref`, `nutrition_raw_values`를 같은 transaction으로 갱신한다. (구현 완료: `752c2aa`)
- 변경 대상 코드가 메뉴마스터나 연결 store에 이미 남아 있으면 저장을 중단한다.

### 7.3 판매가

- 판매가는 메뉴마스터 안에서 관리한다.
- 원가마진표는 메뉴마스터의 판매가를 읽는다.
- 별도 판매가 mirror가 필요하다면 내부 호환용으로만 유지한다.
- 식자재 단가는 제때 최신 단가를 우선한다.
- 제때에 없는 품목은 식자재 수동 단가를 사용한다.

### 7.4 레시피

- 새 기준에서는 메뉴 1개당 레시피 1개를 원칙으로 한다.
- L/R처럼 사이즈가 다른 메뉴는 메뉴코드가 다르면 별도 레시피로 본다.
- 레시피 입력 단위는 `g`, `개`만 허용한다.
- 원가와 영양성분은 사이즈별로 계산/입력한다.
- 원산지와 알레르기는 같은 `displayGroupKey` 단위로 단일 출력한다.
- 엣지마스터는 기본 엣지 4종의 파생 영양성분/알레르기 출력을 위해 필수 보조 기준으로 관리한다.
- 공통묶음은 현재 통합 범위에서 제외하고, 별도 신규 프로젝트의 보조 기능으로만 다룬다.

### 7.5 영양성분

- 메뉴 기준 직접 입력값을 최우선으로 한다.
- 식자재 영양값 자동계산 기능은 제거한다.
- 기존 식자재 영양값 참조 store는 v23 마이그레이션에서 제거하고, 백업/복원 범위에서도 제외한다.

### 7.6 구형 데이터

- 구형 데이터는 가능하면 살리되, 기준이 충돌하면 이관보다 초기화를 우선할 수 있다.
- 기존 레시피가 사라져도 운영상 새로 입력 가능하다는 전제로 진행한다.
- 구현 중 임시 fallback은 둘 수 있지만, 최종 목표는 제거다.

## 8. 기대 효과

- 메뉴 생성부터 원가 확인까지 한 화면 흐름으로 정리된다.
- 레시피 기준이 하나로 고정된다.
- 원가마진표, 제품별 사용현황, 원산지, 알레르기, 영양 출력의 결과 불일치가 줄어든다.
- 신규 사용자나 운영자가 메뉴 구조를 이해하기 쉬워진다.
- 구형 호환 로직을 줄여 유지보수가 쉬워진다.

## 9. 우선순위
