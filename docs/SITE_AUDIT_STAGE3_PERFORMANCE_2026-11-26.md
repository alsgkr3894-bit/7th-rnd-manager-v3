## 3. 측정

`npm run baseline:perf` (303,662행, i7-12700K, 3회의 가운데 값). "이전"은 2단계까지 반영한 같은 날의 측정이고, 수정 뒤에는 같은 코드로 두 번 쟀다.

### 화면 이동 (이미 방문한 화면)

| 화면 | 이전 | 수정 뒤 1차 | 수정 뒤 2차 | 전체 조회 횟수 |
|---|---:|---:|---:|---:|
| 홈 | 453ms | 505ms | 340ms | 27 → 5 |
| 메뉴마스터 | 498ms | 179ms | 104ms | 35 → 1 |
| 식자재 관리 | 489ms | 270ms | 153ms | 28 → 2 |
| 원가마진표 | 177ms | 76ms | 46ms | 18 → 1 |
| 노트 목록 | 969ms | **1,217ms** | 729ms | 16 → 2 |

### 새로 열기

| 화면 | 이전 | 수정 뒤 1차 | 수정 뒤 2차 | 전체 조회 횟수 | JS 힙 |
|---|---:|---:|---:|---:|---:|
| 홈 | 692ms | 677ms | 679ms | 32 → 27 | 187 → 271MB |
| 메뉴마스터 | 781ms | 527ms | 518ms | 37 → 22 | 8 → 82MB |
| 식자재 관리 | 769ms | 577ms | 569ms | 30 → 18 | 43 → 76MB |
| 원가마진표 | 425ms | 431ms | 417ms | 22 → 16 | 6 → 90MB |
| 원가 보고서 | 422ms | 440ms | 424ms | 21 → 16 | 7 → 90MB |
| 노트 목록 | 1,255ms | 1,097ms | 1,102ms | 18 → 16 | 206 → 185MB |

1차에서 홈·노트 이동이 느려져 원인을 따로 확인했다. 두 빌드를 같은 임시 DB에 붙여 이동 시간과 CPU 프로필을 비교했을 때 새 빌드에만 있는 느린 함수는 없었고, 대부분의 회차에서 새 빌드가 빨랐다(홈 약 500 → 370ms, 노트 약 1,000~1,060 → 800ms). 새로 불러온 브라우저에서는 새 빌드의 노트 이동이 6회 중 3회 1.8~2.2초로 튀었고, 그때는 화면 그리기까지 모든 함수가 함께 느렸다. 2차 공식 측정에서는 모든 이동이 이전보다 빨랐다. 편차의 원인은 특정하지 못했다.

### 다시 방문할 때 읽는 저장소

| 화면 | 읽는 것 |
|---|---|
| 메뉴마스터, 원가마진표 | 단가 행(파일별 조회) 1회 |
| 식자재 관리 | 단가 행 2회 |
| 노트 목록 | 메뉴개발노트, 시제품 |
| 홈 | 메뉴개발노트, 시제품, 단가 행 3회 |

메뉴·식자재·레시피·판매가 저장소는 다시 읽지 않는다.

### 완료 조건

| 조건 | 결과 |
|---|---|
| 일반 화면 이동 때 전체 메뉴·식자재 재조회 없음 | 충족 |
| 홈 핵심 정보 1초 안에 표시 | 충족 (새로 열기 679ms, 이동 340~505ms) |

## 5. 남은 것과 한계

- 홈의 단계별 표시, 위젯별 시간 제한, 진행 중 조회 취소는 하지 않았다.
- 파일별 단가 행 조회(색인 조회)는 보관하지 않는다.
- 다른 탭의 변경은 브라우저 알림이 도착한 뒤에 반영된다(보통 즉시). 개발자 도구에서 DB를 직접 고치면 새로고침해야 보인다.
- 앱의 쓰기는 모두 `lib/db/init.js`가 연 연결을 거친다. 이 연결을 거치지 않고 앱 DB를 여는 코드를 새로 만들면 보관본이 낡는다.
- 메뉴 하나를 저장해도 서버로 약 90건이 가는 문제는 그대로다(4단계에서 검토).
- 느린 PC와 LAN의 다른 PC에서는 재지 않았다.
