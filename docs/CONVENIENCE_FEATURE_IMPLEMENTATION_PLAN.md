# 편의성·추가 기능 구현 실행 플랜

기준일: 2026-06-22

이 문서는 사이트에 추가할 편의 기능을 Claude Code가 단계별로 구현하고 Codex가 검수하기 위한 실행 계획이다. 상세 후보와 배경은 `docs/CONVENIENCE_FEATURE_ROADMAP.md`를 참고하고, 실제 작업 순서는 이 문서를 우선한다.

## 0. 확정 실행 요약

현재 편의성 개선은 새 기능을 크게 늘리기보다 **이미 들어와 있는 토대 기능을 검수하고, 사용자 입력 시간을 줄이며, 저장 전 실수를 줄이는 방향**으로 진행한다. 현재 작업트리에 미커밋 변경이 많으므로 Claude Code는 구현 전에 반드시 기준선을 먼저 확인하고, 기존 변경을 되돌리거나 덮어쓰지 않는다.

진행 루프:

1. Claude 1차: 파일 확인, 구현, targeted test, 화면 확인.
2. Codex 1차: diff, 테스트, 실제 동작, 정책 일치 검수.
3. Claude 2차: Codex 지적사항만 좁게 보완.
4. Codex 2차: 최종 검수 후 `승인 / 조건부 승인 / 수정 필요 / 검증 불가` 판정.
5. 단계 green일 때만 커밋하고 다음 단계로 이동.

1차 착수 범위:

| 순서 | 패킷 | 작업 | 완료 기준 |
|---:|---|---|---|
| 1 | A | 기준선·충돌 감사 | `git status`, 현재 테스트 수치, 구현 토대 사용처가 문서화됨 |
| 2 | B | 커맨드 팔레트 상세 이동 | 검색 결과에서 식자재/메뉴 실제 위치로 이동, 잘못된 URL fallback |
| 3 | C | 메뉴 출시 체크리스트 안정화 | 가격·레시피·수량·단가·원산지·알레르기·영양성분 누락 기준 검증 |
| 4 | D | 변경 영향도 미리보기 | 식자재 단가·원산지·알레르기 변경 preview와 저장 후 결과 일치 |

2차 착수 범위:

| 순서 | 패킷 | 작업 | 완료 기준 |
|---:|---|---|---|
| 5 | E | 업무 액션 센터 통합 | 홈 위젯과 상단 알림이 같은 action builder를 사용 |
| 6 | F | 저장된 필터·뷰 확산 | 브랜드별 저장/적용/삭제/기본 뷰와 손상값 fallback 검증 |
| 7 | G | 메뉴·레시피 빠른 입력 | 키보드 이동, 행 복사, 규격 드롭다운, 저장 전 경고 회귀 없음 |

3차 착수 범위:

| 순서 | 패킷 | 작업 | 완료 기준 |
|---:|---|---|---|
| 8 | H | 데이터 품질 점검판 | 누락·중복·이상값을 브랜드별로 진단하고 수정 링크 제공 |
| 9 | I | 월마감·보고 패키지 | 체크리스트와 생성 기록이 실제 출력 가능 상태와 일치 |
| 10 | J | 모바일·현장 확인 모드 | 390px 화면에서 3터치 이내 원산지·알레르기·영양성분·가격 확인 |
| 11 | K | 변경 이력·되돌리기 센터 | 1차는 기록 전용, undo는 사용자 승인 전까지 보류 |

이번 주 작업 권장 범위는 **1차 착수 범위(A~D)** 까지다. E 이후는 여러 도메인 데이터를 같이 묶으므로 A~D가 green이 된 뒤 진행한다.

절대 먼저 하지 않을 것:

- 식자재, 메뉴, 레시피, 판매량, 제때 데이터를 대량 삭제하거나 자동 병합하지 않는다.
- 변경 이력의 실제 undo 기능은 사용자 승인 전까지 만들지 않는다.
- 월마감 패키지를 실제 zip 생성 기능으로 확장하지 않는다.
- 외부 서비스 연동, 서버 DB 전환, 원격 백업은 이 문서 범위에서 제외한다.

## 0.1 이번 요청 기준 최종 작업 큐

사용자가 요청한 "사이트 편의성이나 추가 기능"은 아래 7개 묶음으로 정리한다. Claude Code는 이 순서를 우선하고, 각 묶음은 `작은 구현 -> targeted test -> 화면 확인 -> Codex 검수 -> 보완 -> 커밋` 단위로 닫는다.

| 우선순위 | 묶음 | 사용자 가치 | 포함 기능 | 먼저 할 일 |
|---:|---|---|---|---|
| 1 | 빠른 이동·검색 | 원하는 데이터까지 다시 찾는 시간을 줄인다 | 커맨드 팔레트 상세 이동, 최근 방문, 검색 결과 하이라이트, 수정 모달 자동 열기 | 식자재관리와 메뉴마스터부터 deep link를 완성 |
| 2 | 저장 전 실수 방지 | 저장 후 되돌리는 일을 줄인다 | 메뉴 출시 체크리스트, 변경 영향도 미리보기, 저장 전 누락 경고, 공통원가 오탐 제거 | 메뉴마스터 readiness와 식자재 impact를 실제 계산과 맞춤 |
| 3 | 입력 속도 개선 | 메뉴·레시피·식자재 입력 시간을 줄인다 | 레시피 구성품 키보드 입력, 행 복사, 규격 드롭다운, 비슷한 메뉴 레시피 복사, 최근 사용 식자재 추천 | 메뉴마스터 레시피 입력 흐름을 먼저 정리 |
| 4 | 오늘 할 일 통합 | 여러 화면을 돌지 않고 처리할 일을 본다 | 업무 액션 센터, 홈 위젯, 상단 알림, 단가 없음·미매칭·백업 권장 액션 | action builder를 홈/TopBar가 함께 쓰게 함 |
| 5 | 반복 업무 저장 | 같은 필터와 보고 작업을 반복하지 않는다 | 저장된 필터·뷰, 기본 뷰, 월마감 체크리스트, 출력 생성 기록 | 식자재관리 적용 상태 확인 후 원가마진표/판매량으로 확산 |
| 6 | 데이터 품질 점검 | 운영 데이터가 믿을 만한지 한 화면에서 본다 | 품질 점검판, 누락·중복·이상값 진단, 수정 링크, 브랜드별 점검 | readiness/action/impact 계산을 재사용하는 quality builder 설계 |
| 7 | 현장 확인·감사 | 매장 확인과 변경 추적을 안전하게 한다 | 모바일 현장 확인 모드, 변경 이력, 백업 안내, 제한적 되돌리기 후보 | 모바일 조회 모드와 기록 전용 change log부터 진행 |

### 0.1.1 1차 스프린트

목표:

- 가장 작고 체감이 빠른 편의성 개선을 먼저 완성한다.
- 기존 미커밋 변경과 충돌하지 않게 이미 들어온 토대 코드를 살린다.

범위:

1. 기준선·충돌 감사.
2. 식자재관리 커맨드 팔레트 상세 이동.
3. 메뉴마스터 커맨드 팔레트 상세 이동.
4. 메뉴 출시 체크리스트의 오탐 검증.
5. 식자재 변경 영향도 미리보기의 실제 계산 일치 검증.

완료 기준:

- 검색 결과에서 대상 화면으로 이동한 뒤 추가 검색 없이 대상 행이나 수정 위치가 보인다.
- 잘못된 URL 파라미터, 삭제된 대상, 다른 브랜드 데이터에서 화면이 깨지지 않는다.
- 메뉴 출시 체크리스트가 레시피 미작성, 수량 누락, 단가 누락, 판매가 누락을 서로 구분한다.
- 공통원가 때문에 수량 누락으로 오탐하지 않는다.
- 관련 targeted test, `format:check`, `lint`, `git diff --check`가 통과한다.

### 0.1.2 2차 스프린트

목표:

- 메뉴마스터와 식자재관리에서 저장 전 실수를 줄이고 입력 속도를 높인다.

범위:

1. 레시피 구성품 입력 키보드 흐름.
2. 구성품 행 복사, 위/아래 이동, 빠른 삭제.
3. 규격 드롭다운과 직접 입력 병행.
4. 같은 메뉴 L/R 또는 비슷한 메뉴에서 레시피 복사.
5. 저장 전 경고를 `수량`, `단가`, `중복 구성품`, `공통원가`, `판매가`로 분리.

완료 기준:

- 마우스 없이 기본 구성품 입력 흐름이 가능하다.
- 메뉴 저장 하나로 기본정보와 레시피가 함께 저장된다.
- 레시피 임시 단가 보정과 식자재 원본 단가 수정이 UI와 저장 로직에서 구분된다.
- 저장 전 경고가 실제 저장 결과와 일치한다.

### 0.1.3 3차 스프린트

목표:

- 홈과 상단에서 "오늘 처리할 일"을 한 번에 보게 한다.

범위:

1. action item builder 정리.
2. 홈 위젯과 TopBar 알림 통합.
3. 미매칭 메뉴, 단가 없음, 오래된 업로드, 백업 권장, readiness 이슈 연결.
4. `완료`, `나중에`, `숨김` 상태를 local state로 관리.
5. 원인 해결 시 action 자동 제거.

완료 기준:

- 홈과 TopBar 숫자가 같은 기준으로 표시된다.
- action 클릭 시 실제 수정 화면이나 필터 상태로 이동한다.
- 원본 데이터는 action 처리만으로 삭제되거나 변경되지 않는다.

### 0.1.4 4차 스프린트

목표:

- 반복 조회와 보고 업무를 줄인다.

범위:

1. 저장된 필터·뷰를 원가마진표와 메뉴판매량으로 확산.
2. 브랜드별 저장, 기본 뷰, 이름 변경, 삭제.
3. 월마감 체크리스트와 생성 기록 정리.
4. 출력 가능 상태와 생성 기록의 불일치 방지.

완료 기준:

- 브랜드를 바꿔도 저장된 뷰가 섞이지 않는다.
- 손상된 localStorage 값은 화면을 깨뜨리지 않고 기본값으로 복구된다.
- 월마감 기능은 실제 zip 기능처럼 과장하지 않고 체크리스트/기록 중심으로 표시된다.

### 0.1.5 5차 스프린트

목표:

- 운영 데이터 품질과 현장 확인 UX를 개선한다.

범위:

1. 데이터 품질 점검판.
2. 빈 DB, 중복 데이터, 누락 데이터, 오래된 업로드 진단.
3. 모바일 현장 확인 모드.
4. 변경 이력 기록 전용 센터.

완료 기준:

- 품질 점검판은 브랜드별로 누락·중복·이상값을 보여주고 수정 링크를 제공한다.
- 390px 화면에서 원산지, 알레르기, 영양성분, 가격 확인이 겹침 없이 가능하다.
- 변경 이력은 기록 전용으로 시작하고, 실제 undo는 사용자 승인 전까지 만들지 않는다.

## 1. 작업 목적

현재 사이트는 메뉴마스터, 식자재관리, 원가계산, 영양성분, 판매량, 제때데이터, 보고서, 노트, 설정 기능이 넓게 구현되어 있다. 다음 개선은 새 화면을 무작정 늘리는 것보다 아래 세 가지에 집중한다.

1. 사용자가 원하는 항목까지 더 빨리 도달하게 한다.
2. 메뉴 출시, 식자재 수정, 출력 전 실수를 줄인다.
3. 반복 필터, 보고서 생성, 점검 업무를 한곳에서 처리하게 한다.

## 2. 공통 진행 방식

모든 단계는 아래 순서로 진행한다.

1. Claude 1차 구현
2. Claude 자체 테스트와 버그 탐색
3. Codex 1차 검수
4. Claude 보완
5. Codex 최종 검수
6. 단계별 커밋
7. 다음 단계 착수

단계 하나가 green이 되기 전에는 다음 기능을 섞어 구현하지 않는다.

## 3. 공통 완료 기준

각 단계는 최소 아래 조건을 만족해야 완료로 본다.

- 기존 미커밋 변경을 되돌리지 않는다.
- 사용자 데이터 삭제, 초기화, 대량 복원, 대량 변경은 관리자 권한과 확인 절차 없이 실행하지 않는다.
- 관련 targeted Jest 테스트를 추가하거나 갱신한다.
- `npm run format:check`, `npm run lint`, `git diff --check`를 통과한다.
- 화면 동작이 있는 단계는 dev 서버에서 실제 화면을 확인한다.
- 테스트 수치나 완료 상태가 바뀌면 관련 문서를 갱신한다.

## 5. 단계별 작업 명세

### 0단계. 기준선 고정

작업 목표:

- 현재 작업트리, 테스트 상태, 문서 수치를 먼저 고정한다.

요구사항:

1. `git status --short`로 미커밋 변경을 확인한다.
2. 관련 문서의 테스트 수치와 실제 테스트 결과가 맞는지 확인한다.
3. 실패 중인 테스트가 있으면 기능 구현 전에 원인과 영향 범위를 기록한다.

검수 기준:

- 현재 변경 범위와 새 작업 범위가 구분된다.
- 되돌리거나 덮어쓴 파일이 없다.

### 1단계. 구현 흔적 감사

작업 목표:

- 이미 존재하는 편의 기능 토대를 살릴지, 보완할지, 재설계할지 판단한다.

확인 대상:

- `components/action-center/`, `lib/action-center/`
- `components/menu-master/MenuReadinessPanel.jsx`, `lib/menu-master/readiness.js`
- `components/impact/`, `lib/impact/`
- `components/ui/SavedViewSelector.jsx`, `lib/saved-views.js`
- `components/report/MonthlyClosePackageModal.jsx`, `lib/report/package-plan.js`
- `components/change-log/`, `lib/change-log/`

완료 기준:

- 각 기능을 `완성 보완`, `부분 구현`, `재설계 필요`, `보류` 중 하나로 분류한다.
- 부족한 테스트와 화면 확인 항목을 문서화한다.

### 2단계. 커맨드 팔레트 상세 이동

작업 목표:

- 검색 결과 선택 후 사용자가 다시 필터를 치지 않아도 실제 항목 위치까지 이동하게 한다.

요구사항:

1. 식자재 검색 결과는 `query`, `highlight`, `productCode`를 URL에 반영한다.
2. 식자재관리 화면은 URL 파라미터를 읽어 검색어 적용, 페이지 이동, 스크롤, 행 하이라이트를 처리한다.
3. 메뉴 검색 결과는 가능하면 메뉴마스터의 해당 메뉴 수정 위치까지 이동한다.
4. 잘못된 URL 파라미터는 일반 목록으로 fallback한다.
5. 기존 `view`, `catFilter`, 저장된 뷰, 검색 필터 동작을 깨지 않는다.

테스트:

- 식자재 id로 진입 시 대상 행 하이라이트.
- productCode fallback.
- 없는 id 또는 잘못된 query fallback.
- 팔레트 Enter 선택 흐름 유지.

### 3단계. 메뉴 출시 체크리스트

작업 목표:

- 메뉴 하나가 출시 가능한 상태인지 한 화면에서 확인하게 한다.

요구사항:

1. 메뉴 기본정보, 판매가, 레시피 구성품, 수량, 단가, 원산지, 알레르기, 영양성분, 표출력 가능 여부를 진단한다.
2. 상태는 `완료`, `주의`, `미작성`, `확인 불가`로 나눈다.
3. 각 이슈에서 바로 수정 위치로 이동할 수 있게 한다.
4. 피자 L/R, 단일, 1인피자, 사이드, 소스, 음료, 엣지 기준을 섞지 않는다.
5. 원산지/알레르기는 메뉴 단위, 원가/영양성분은 필요한 경우 사이즈 단위 기준을 유지한다.

테스트:

- 레시피 없는 메뉴.
- 판매가 없는 메뉴.
- 단가 없는 구성품.
- L/R이 있는 피자와 단일 메뉴 구분.
- 영양성분 일부 누락 메뉴.

### 4단계. 변경 영향도 미리보기

작업 목표:

- 식자재나 레시피를 저장하기 전에 어떤 메뉴와 출력물이 영향을 받는지 보여준다.

요구사항:

1. 식자재 단가 변경 시 영향 메뉴 수와 원가율 변화 후보를 보여준다.
2. 원산지 변경 시 원산지 표시판에 영향받는 메뉴를 보여준다.
3. 알레르기 변경 시 알레르기표에 영향받는 메뉴를 보여준다.
4. 레시피 구성품 변경 시 원가, 원산지, 알레르기, 영양성분 준비 상태 변화를 보여준다.
5. 저장 전 preview와 저장 후 실제 계산 결과가 일치해야 한다.

테스트:

- 한 식자재가 여러 메뉴에 쓰이는 경우.
- 단가 변경 전후 원가율 delta.
- 원산지/알레르기 변경 전후 집계 결과.
- 영향 없는 변경의 빈 상태.

### 5단계. 업무 액션 센터

작업 목표:

- 오늘 처리해야 할 이슈를 홈과 상단 알림에서 같은 기준으로 보여준다.

요구사항:

1. 액션 항목은 `id`, `source`, `title`, `desc`, `severity`, `href`, `createdAt`, `dueHint`를 가진다.
2. 미매칭 메뉴, 보고예정 노트, 단가 없는 식자재, 원가율 경보, 오래된 업로드, 백업 권장, 영양/원산지/알레르기 누락을 포함한다.
3. `완료`, `나중에`, `숨김` 상태를 지원한다.
4. 원인 데이터가 해결되면 action은 자동으로 사라진다.
5. 홈 위젯과 TopBar 알림은 같은 builder를 사용한다.

테스트:

- 각 원인 데이터별 action 생성.
- dismiss/snooze 상태.
- 원인 해결 후 자동 제거.
- action 클릭 시 올바른 화면 이동.

### 6단계. 저장된 필터·뷰

작업 목표:

- 자주 쓰는 필터 조합을 저장하고 빠르게 재사용하게 한다.

대상 우선순위:

1. 식자재관리
2. 원가마진표
3. 메뉴판매량 분석
4. 보고서 목록
5. 노트 목록

요구사항:

1. 현재 필터를 이름 붙여 저장한다.
2. 저장된 뷰를 선택하면 즉시 적용한다.
3. 기본 뷰 지정, 이름 변경, 삭제를 지원한다.
4. 브랜드별로 분리한다.
5. 손상된 localStorage 값은 무시하고 기본값으로 복구한다.

### 7단계. 메뉴·레시피 빠른 입력

작업 목표:

- 메뉴마스터와 레시피 구성품 입력 시간을 줄이고 저장 전 실수를 줄인다.

요구사항:

1. 최근 사용 식자재와 자주 쓰는 식자재 추천을 구성품 검색에 활용한다.
2. Enter, Tab, 방향키 이동을 자연스럽게 만든다.
3. 구성품 행 복사, 위/아래 이동, 빠른 삭제를 제공한다.
4. 규격은 직접 입력과 드롭다운을 모두 지원한다.
5. 같은 메뉴의 L/R 또는 비슷한 메뉴에서 레시피를 복사할 수 있게 한다.
6. 저장 전 수량 누락, 단가 누락, 중복 구성품, 공통원가 누락을 한 번에 보여준다.
7. 레시피 임시 단가와 식자재 원본 단가 수정은 UI에서 명확히 구분한다.

### 8단계. 데이터 품질 점검판

작업 목표:

- 운영 데이터의 누락, 중복, 이상값을 한 화면에서 점검한다.

요구사항:

1. 메뉴, 레시피, 식자재, 단가, 판매량, 영양성분, 원산지, 알레르기 진단을 묶는다.
2. 각 이슈는 심각도, 영향 범위, 수정 링크를 가진다.
3. 브랜드 전환 시 해당 브랜드 데이터만 보여준다.
4. 빈 DB에서도 깨지지 않는다.

### 9단계. 월마감·보고 패키지

작업 목표:

- 월별 보고 출력 업무를 체크리스트로 묶고 생성 기록을 남긴다.

요구사항:

1. 기준월과 브랜드를 선택한다.
2. 판매량, 원가, 식자재 단가, 출고량, 원산지, 알레르기, 영양성분 출력 항목을 체크한다.
3. 생성 전 데이터 신선도와 누락 항목을 경고한다.
4. 생성 후 파일명, 생성일, 생성자, 브랜드, 기준월 기록을 남긴다.
5. 실제 zip 생성은 2차 기능으로 두고, 1차는 체크리스트와 순차 생성 기록을 우선한다.

### 10단계. 모바일·현장 확인 모드

작업 목표:

- 매장에서 원산지, 알레르기, 영양성분, 가격을 빠르게 확인하게 한다.

요구사항:

1. 390px 화면에서 핵심 정보가 겹치지 않아야 한다.
2. 메뉴 검색 후 3터치 이내에 핵심 정보에 도달해야 한다.
3. 편집 기능보다 조회 편의성을 우선한다.
4. 출력용 화면과 현장 확인 화면의 표시 기준이 다르면 안 된다.

테스트:

- `npm run qa:mobile`
- 실제 390px 화면 수동 확인.
- 긴 메뉴명, 긴 원산지, 다수 알레르기 표시 확인.

### 11단계. 변경 이력·되돌리기 센터

작업 목표:

- 최근 변경 작업을 추적하고, 복구 가능한 작업과 불가능한 작업을 명확히 보여준다.

요구사항:

1. 1차는 기록 전용으로 진행한다.
2. 식자재 저장/삭제/일괄변경, 메뉴 저장/삭제, 레시피 저장, 판매량/제때 업로드, 백업/복원을 기록한다.
3. 되돌리기 기능은 정책 확정 전까지 보류한다.
4. viewer 권한에서는 위험 작업을 실행할 수 없어야 한다.
5. 되돌릴 수 없는 작업은 백업 위치와 복구 안내를 보여준다.

## 8. Codex 검수 기준

Codex는 Claude 보고만 믿지 않고 아래를 직접 확인한다.

1. 요구사항이 실제 구현에 반영되었는지.
2. 메뉴 저장, 레시피 저장, 식자재 저장, 백업/복원 등 기존 핵심 흐름이 깨지지 않았는지.
3. 브랜드별 데이터가 섞이지 않는지.
4. viewer/admin 권한 차이가 유지되는지.
5. 테스트가 실제 정책을 검증하는지.
6. 화면에서 빈 상태, 오류 상태, 긴 텍스트, 모바일 폭이 깨지지 않는지.

검수 판정은 `승인`, `조건부 승인`, `수정 필요`, `검증 불가` 중 하나로 남긴다.

## 9. Claude 작업 패킷

아래 패킷 순서를 실제 실행 순서로 사용한다. 각 패킷은 독립적으로 구현, 테스트, 검수, 커밋할 수 있어야 한다. 한 패킷 안에서도 변경 파일이 넓어지면 `lib/helper`, `UI`, `테스트`, `문서` 순으로 더 작게 나눈다.

### A. 기준선·충돌 감사

목표:

- 현재 작업트리와 테스트 상태를 먼저 고정하고, 이미 들어온 기능 토대를 덮어쓰지 않는다.

수정 대상:

- 문서만 수정 가능.
- 코드 변경은 실패 테스트나 명백한 충돌 원인 정리에 한정한다.

확인 항목:

1. `git status --short`로 미커밋 변경을 파일 단위로 분류한다.
2. `docs/CONVENIENCE_FEATURE_ROADMAP.md`와 이 문서의 우선순위가 충돌하지 않는지 확인한다.
3. `components/action-center/`, `lib/action-center/`, `components/impact/`, `lib/impact/`, `components/ui/SavedViewSelector.jsx`, `lib/saved-views.js`, `components/change-log/`, `lib/change-log/`가 이미 사용 중인지 `rg`로 확인한다.
4. 현재 테스트 수치가 문서와 다르면 실제 실행 결과 기준으로 문서를 고친다.

완료 기준:

- 각 후보 기능을 `사용 중`, `부분 구현`, `미연결`, `보류`로 분류한다.
- 실패 테스트가 있으면 다음 기능 구현 전에 별도 이슈로 분리한다.

### B. 커맨드 팔레트 상세 이동

목표:

- 검색 결과 선택 후 실제 행, 수정 모달, 또는 관련 탭까지 바로 이동한다.

우선 대상:

1. 식자재관리: 식자재명, productCode, 분류, 태그 검색 결과.
2. 메뉴마스터: 메뉴명, menuCode 검색 결과.
3. 원가마진표: 메뉴명 검색 결과.

구현 방향:

- 팔레트 item은 단순 URL 문자열만 만들지 말고 `href`, `highlightId`, `query`, `fallbackHref` 의미가 유지되게 구성한다.
- 대상 화면은 URL 파라미터를 1회 읽고 검색어 적용, 페이지 이동, 스크롤, 하이라이트를 처리한다.
- 대상이 삭제되었거나 필터에 걸려 없으면 빈 화면이 아니라 일반 목록으로 fallback한다.

검수 기준:

- Enter로 선택했을 때 마우스 클릭과 같은 결과가 나온다.
- 다른 페이지에 있는 행도 pagination 이동 후 하이라이트된다.
- 잘못된 id, 없는 productCode, 빈 query에서 화면이 깨지지 않는다.

테스트:

- `usePaletteItems` 구조 테스트.
- 식자재관리 URL 파라미터 처리 테스트.
- 가능하면 workflow에 팔레트 검색 후 이동 시나리오 1개 추가.

### C. 메뉴 출시 체크리스트 안정화

목표:

- 메뉴 출시 전에 누락된 가격, 레시피, 수량, 단가, 원산지, 알레르기, 영양성분, 출력 가능 여부를 한 화면에서 확인한다.

수정 대상:

- `lib/menu-master/readiness.js`
- `components/menu-master/MenuReadinessPanel.jsx`
- `app/menu-master/page.jsx`
- 관련 테스트: `__tests__/lib/menu-readiness-output-coverage.test.mjs`, 필요 시 신규 테스트

구현 방향:

- 계산 로직은 `lib/menu-master/readiness.js`에 두고 UI는 상태 표시와 이동 버튼만 담당한다.
- 피자 L/R, 단일, 1인피자, 사이드, 소스, 음료, 엣지 기준을 섞지 않는다.
- 원산지와 알레르기는 메뉴 단위, 원가와 영양성분은 필요한 경우 사이즈 단위로 판단한다.

검수 기준:

- 레시피 미작성, 수량 누락, 단가 누락, 판매가 누락이 서로 다른 이슈로 표시된다.
- 공통원가 때문에 실제 구성품 수량이 있는데도 "수량 확인"으로 오탐하지 않는다.
- 이슈 버튼은 수정 가능한 실제 위치로 이동한다.

### D. 변경 영향도 미리보기

목표:

- 저장 전에 변경이 영향을 주는 메뉴, 원가율, 원산지 표시판, 알레르기표를 보여준다.

수정 대상:

- `lib/impact/ingredient-impact.js`
- `components/impact/ImpactPreviewPanel.jsx`
- `app/ingredient/manage/IngredientForm.jsx`
- 레시피 영향도 확장 시 별도 `lib/impact/recipe-impact.js` 신규 가능

구현 방향:

- 1차는 식자재 단가, 원산지, 알레르기 변경 영향도를 정확히 만든다.
- 레시피 변경 영향도는 계산 범위가 넓으므로 별도 패킷으로 분리할 수 있다.
- preview는 저장 전 값과 저장 후 예상 값이 같은 계산 함수를 공유해야 한다.

검수 기준:

- 영향 메뉴 수, 메뉴명, 원가율 변화 후보가 실제 레시피와 일치한다.
- 영향 없는 변경은 명확한 빈 상태를 보여준다.
- viewer 권한은 preview는 볼 수 있어도 저장은 할 수 없다.

### E. 업무 액션 센터 통합

목표:

- 홈, 상단 알림, 진단 화면의 "처리할 일"을 같은 기준으로 묶는다.

수정 대상:

- `lib/action-center/build.js`
- `lib/action-center/state.js`
- `components/action-center/ActionCenterPanel.jsx`
- `components/home/ActionCenterWidget.jsx`
- TopBar 연동 파일은 실제 사용처 확인 후 최소 변경

구현 방향:

- action item의 `id`는 원인 데이터가 같으면 안정적으로 유지한다.
- `숨김`, `나중에`는 원본 데이터를 바꾸지 않고 local state로만 관리한다.
- 원인 데이터가 해결되면 숨김 상태와 관계없이 액션 목록에서 사라진다.

검수 기준:

- 미매칭 메뉴, 단가 없음, 백업 권장, 오래된 업로드, readiness 이슈가 같은 builder에서 나온다.
- 홈과 상단 알림 숫자가 서로 다르게 표시되지 않는다.
- action 클릭 시 관련 화면과 필터로 이동한다.

### F. 저장된 필터·뷰 확산

목표:

- 자주 쓰는 필터 조합을 저장하고 브랜드별로 재사용한다.

우선 적용 순서:

1. 식자재관리 현 적용 상태 점검.
2. 원가마진표.
3. 메뉴판매량 분석.
4. 보고서 목록.
5. 노트 목록.

구현 방향:

- `lib/saved-views.js` public API를 유지한다.
- 화면별 saved view key는 브랜드와 route를 포함해 충돌을 피한다.
- 손상된 localStorage 값은 조용히 복구하고 사용자 데이터 전체를 지우지 않는다.

검수 기준:

- 기본 뷰 지정, 이름 변경, 삭제가 가능하다.
- 브랜드 전환 시 다른 브랜드의 저장 뷰가 섞이지 않는다.
- 필터 구조가 바뀌어도 구형 저장값이 화면을 깨뜨리지 않는다.

### G. 메뉴·레시피 빠른 입력

목표:

- 메뉴마스터에서 레시피 구성품 입력 시간을 줄이고 저장 전 오류를 줄인다.

수정 대상:

- `components/menu-master/MenuRecipeSection.jsx`
- `components/menu-master/MenuRecipeComponentsTable.jsx`
- `components/menu-master/recipe/`
- `components/menu-master/useMenuRecipeEditor.js`
- `components/menu-master/useRecipeIngredientSearch.js`
- `app/menu-master/useMenuMasterActions.js`

구현 방향:

- 최근 사용 식자재, 자주 쓰는 식자재, 같은 메뉴 L/R 복사, 다른 메뉴에서 복사 기능을 정리한다.
- Enter, Tab, 방향키 흐름을 실제 입력 순서와 맞춘다.
- 레시피 임시 단가 보정과 식자재 원본 단가 수정은 UI 문구와 저장 로직에서 명확히 분리한다.

검수 기준:

- 별도 "레시피 저장" 버튼 없이 메뉴 저장 하나로 구성품과 기본정보가 함께 저장된다.
- 저장 전 경고는 실제 누락만 잡고 공통원가 때문에 오탐하지 않는다.
- 규격 드롭다운과 직접 입력이 모두 가능하다.

### H. 데이터 품질 점검판

목표:

- 누락, 중복, 이상값, 오래된 데이터, 출력 불가 상태를 한 화면에서 점검한다.

구현 방향:

- action-center, readiness, impact 계산 로직을 재사용한다.
- 새 계산 로직을 만들 때는 UI보다 `lib/quality/` 같은 순수 helper를 먼저 만든다.
- 각 이슈는 심각도, 영향 범위, 수정 링크, 자동 해결 가능 여부를 가진다.

검수 기준:

- 빈 DB에서 "점검할 데이터 없음" 상태로 안전하게 표시된다.
- 브랜드별 데이터가 섞이지 않는다.
- 동일 이슈가 action-center와 품질 점검판에서 서로 다른 숫자로 나오지 않는다.

### I. 월마감·보고 패키지

목표:

- 월별 보고에 필요한 출력물 생성 순서와 누락 데이터를 체크리스트로 제공한다.

수정 대상:

- `components/report/MonthlyClosePackageModal.jsx`
- `lib/report/package-plan.js`
- `app/report/page.jsx`

구현 방향:

- 1차는 실제 zip 생성이 아니라 체크리스트, 이동, 생성 기록 중심으로 둔다.
- UI 문구가 실제 기능보다 과장되지 않게 한다.
- 실제 파일 생성 여부와 기록 상태가 어긋나지 않게 한다.

검수 기준:

- 기준월, 브랜드, 출력 항목별 준비 상태가 표시된다.
- 생성 불가 항목은 이유와 수정 링크를 제공한다.
- 생성 기록은 파일명, 기준월, 브랜드, 생성일을 남긴다.

### J. 모바일·현장 확인 모드

목표:

- 매장에서 원산지, 알레르기, 영양성분, 판매가를 빠르게 확인한다.

구현 방향:

- 새 라우트를 만들기 전에 기존 원산지/알레르기/영양성분/메뉴 화면에 조회 모드를 붙일 수 있는지 확인한다.
- 편집 기능보다 검색, 큰 터치 영역, 읽기 쉬운 요약을 우선한다.
- 출력 기준과 현장 확인 기준이 달라지지 않게 같은 builder를 사용한다.

검수 기준:

- 390px 폭에서 핵심 정보가 겹치지 않는다.
- 메뉴 검색 후 3터치 이내에 원산지, 알레르기, 영양성분 중 하나를 확인할 수 있다.
- 긴 메뉴명, 긴 원산지, 다수 알레르기에서 줄바꿈이 자연스럽다.

### K. 변경 이력·되돌리기 센터

목표:

- 위험한 변경을 추적하고, 복구가 필요한 상황에서 사용자가 무엇을 했는지 확인할 수 있게 한다.

구현 방향:

- 1차는 기록 전용이다.
- undo는 사용자 결정 전까지 만들지 않는다.
- 식자재 저장/삭제/일괄변경, 메뉴 저장/삭제, 레시피 저장, 판매량/제때 업로드, 백업/복원을 우선 기록한다.

검수 기준:

- viewer 권한에서는 위험 작업 실행 버튼이 노출되지 않는다.
- 기록 삭제나 전체 비우기는 관리자 확인 절차가 있어야 한다.
- 되돌릴 수 없는 작업은 백업 안내를 같이 보여준다.

## 10. 추천 착수 순서

이번 작업은 아래 순서로 끊어서 진행한다.

| 묶음 | 포함 패킷 | 이유 | 커밋 기준 |
|---|---|---|---|
| 1차 안정화 | A, B, C | 현재 토대와 테스트 상태를 고정하고 메뉴마스터 핵심 실수를 줄인다 | 기준선 문서화, 팔레트 이동, readiness 테스트 green |
| 2차 실수 방지 | D, E | 저장 전 영향도와 처리할 일을 연결한다 | impact/action-center targeted test green |
| 3차 반복작업 감소 | F, G | 실제 입력·조회 시간을 줄인다 | 저장된 뷰와 레시피 입력 UX 회귀 없음 |
| 4차 운영 점검 | H, I | 운영 데이터 품질과 월마감 반복 업무를 줄인다 | 품질 점검 빈 상태/브랜드 분리, 월마감 기록 검증 |
| 5차 현장·장기 안정성 | J, K | 모바일 확인과 변경 추적은 범위가 넓어 마지막에 다룬다 | qa:mobile green, 변경 이력 권한 가드 확인 |

1차가 끝난 뒤 Codex가 실제 화면과 테스트 결과를 검수하고, 그 결과를 바탕으로 2차 범위를 확정한다.

## 11. 단계별 필수 검증 명령

문서만 수정한 경우:

```bash
git diff --check
```

코드 또는 테스트를 수정한 경우:

```bash
npm run format:check
npm run lint
git diff --check
```

도메인 로직을 수정한 경우:

```bash
node --experimental-vm-modules node_modules/jest/bin/jest.js <관련 테스트 파일> --runInBand
```

화면 동작을 수정한 경우:

```bash
npm run qa:smoke
npm run qa:workflow
```

모바일 또는 레이아웃을 수정한 경우:

```bash
npm run qa:mobile
```

최종 묶음 커밋 전:

```bash
npm run test:ci
npm run audit:docs
```

단, 이미 실패 중인 테스트가 있는 상태라면 새 작업 때문인지 기존 실패인지 먼저 분리해서 보고한다. 기존 실패를 숨기고 기능 완료로 보고하지 않는다.

## 12. 보류 원칙

아래 작업은 사용자가 명확히 승인하기 전까지 구현하지 않는다.

- 식자재, 메뉴, 레시피, 판매량, 제때 데이터를 대량 삭제하거나 자동 병합하는 기능.
- 변경 이력에서 실제 undo를 실행하는 기능.
- 월마감 패키지의 실제 zip 생성과 자동 다운로드.
- 외부 서비스 연동, 서버 DB 전환, 원격 백업.
- 영양성분 부분 누락 시 출력 차단 정책 변경.
- 과거 단가를 현재 원가 계산에 자동 반영하는 정책 변경.
