## 2. 설계에서 정한 것

- **앱 DB 구조는 바꾸지 않았다.** 미전송 작업은 별도 브라우저 DB(`rnd_sync_outbox`)에 둔다. 앱 DB 버전이 그대로라 이전 코드로 되돌려도 브라우저 데이터를 열 수 있다.
- **서버 DB 마이그레이션이 없다.** 적용한 작업 ID는 비어 있던 `server_settings` 표에 `sync-op:` 키로 기록하고 14일 뒤 지운다. 같은 트랜잭션이라 저장이 실패하면 기록도 남지 않는다.
- 필수 값 검사는 복원을 막지 않고 알리기만 한다. 예전 백업을 되살리는 길을 닫지 않기 위해서다.

## 4. 검증

### 브라우저 (최신 백업을 복원한 임시 PostgreSQL에만 쓰는 서버, 운영 DB 미접속)

|---|---|
| 평상시 저장 | 서버 반영, 보관함 비움 |
| 서버 요청 차단 후 저장 | PC에만 저장, 91건 보관, 화면에 건수 표시, 불러오기 전 경고 |
| 브라우저를 닫았다 다시 켜고 홈만 열기 | 서버에 전송 |

### 복원 시험에서 찾은 문제

첫 번째 전체 복원 시험에서 **서버의 작업 일지 186행이 사라졌다.** PC에는 저장이 끝났지만 전송 보관함에 옮겨 적는 중에 새로고침해, 묶음의 앞부분(저장소 전체 비우기 포함)만 남았기 때문이다. 직전 검토에서 넣은 "500건씩 나눠 쓰기"가 원인이었다. `f5456b42`에서 고친 뒤 같은 시험을 다시 해 모든 저장소의 행 수가 일치함을 확인했다.

## 5. 남은 것과 한계

- 대량 복원처럼 보관함에 옮겨 적는 데 시간이 걸리는 동안 경고를 무시하고 닫으면, 그 묶음은 서버에 가지 않는다(PC에는 저장돼 있고 복원 중단 안내가 뜬다). 설정 / 백업의 "서버로 전체 재전송"으로 맞춘다.
- 서버에 보내지 못한 변경은 그 브라우저에만 있다. 전송 전에 브라우저 데이터를 지우면 사라진다.
- 서버가 내려간 동안 **두 탭에서 같은 항목**을 고치면, 다시 보낼 때 두 탭 사이의 순서는 보장하지 않는다. 한 탭 안의 순서는 지킨다.
- 14일 넘게 보내지 못한 작업은, 이미 적용됐던 것이라도 다시 적용될 수 있다.
- 모듈별 초기화의 복구 파일은 내려받기 요청까지만 확인한다. 저장됐는지 묻는 것은 전체 초기화와 DB 재생성뿐이다.
- 메뉴 하나를 저장해도 서버로 약 90건이 간다(판매가 전체를 다시 쓰기 때문). 속도 개선(3~4단계)에서 볼 일이다.
- 서버의 파괴적 작업 이력(감사 기록)은 추가하지 않았다.

## 6. 확인하지 않은 것

- 실제 PC 재부팅, 실제 저장 공간 부족, 저장소 파일 손상
- 보관 중 닫기 경고가 실제 복원에서 뜨는 것(자동 테스트로만 확인. 두 번째 복원 시험은 보관이 끝난 뒤 새로고침했다)
- 앱 버전이 실제로 올라갈 때 두 탭 사이의 업그레이드 차단(자동 테스트로만 확인)
- LAN의 다른 PC에서의 동작
