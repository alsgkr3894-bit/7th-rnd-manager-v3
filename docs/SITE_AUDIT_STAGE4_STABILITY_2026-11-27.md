## 3. 검증

최신 백업을 복원한 임시 PostgreSQL에만 쓰는 서버 두 개(이전 `e1cfca68`, 새 빌드)를 `.env`가 없는 별도 폴더에서 띄워 같은 조작을 비교했다. 운영 DB에는 접속하지 않았다. (i7-12700K, 약 30만 행)

### 속도·반응

| 항목 | 이전 | 이후 |
|---|---:|---:|
| 시작할 때의 데이터 확인 | 188ms | 1ms |

- 재전송 시간·가장 큰 요청·업로드 전송·묶음 적용 시간은 문장 크기를 1MB로 낮추기 전에 쟀다. 브라우저 없이 잰 처리 시간은 낮춘 뒤에도 같았다.
- 압축 백업(.gz)은 이전에도 읽는 동안 화면이 멈추지 않았다. 읽는 시간은 1.7초에서 2.3초로 조금 늘었고, 진행률과 취소가 생겼다.
- 업로드 중 남는 긴 작업은 파일 해석이 아니라 저장·계산 쪽이다.
- 이전 버전은 69MB 요청이 서버 상한에 걸려 한 건씩 다시 보내는 과정이 있었다.

### 서버 메모리

전체 재전송을 반복하며 서버 프로세스(자식 포함)의 메모리를 쟀다.

| | 이전 | 새 코드 (8MB 문장) | 최종 (1MB 문장) |
|---|---:|---:|---:|
| 최대 | 533~664MB | 785~868MB | 663~780MB |
| 60초 뒤 | 427~481MB | 680~841MB | 564~666MB |

**서버 메모리는 이전보다 약간 높다.** 브라우저 없이 서버 저장 코드만 반복하면, 매번 강제 정리 뒤 사용 중인 JavaScript 힙이 15~17MB로 돌아와 쌓이는 것은 없었다. Node가 확보한 메모리를 바로 돌려주지 않는 것이고, 두 배 빠르게 처리하면서 순간 사용량이 커졌다(같은 시험에서 최대 이전 558~729MB, 최종 786~1,033MB).

## 4. 남은 것과 한계

- 사진 이전(2번)을 하지 않아 사진이 든 저장소의 조회·동기화·메모리는 그대로다.
- 서버는 같은 행을 다시 받아도 갱신 시각을 바꾼다(이전과 같음).
- 서버 메모리는 줄지 않았다. 사진을 행에서 분리하면(2번) 한 번에 다루는 크기가 작아진다.
- 상한 안의 매우 큰 Excel 파일은 별도 스레드에서도 메모리를 많이 쓴다. 브라우저가 중단하면 "작업이 중단됐습니다"로 알린다.
- 서식만 칠한 빈 행이 30만 행을 넘고 그 뒤에 값이 있는 파일은, 뒤의 값을 알아채지 못할 수 있다.
- 복원 파일을 읽은 뒤 저장하는 단계의 시간은 바꾸지 않았다(약 190초).
- 파괴적 작업의 서버 감사 이력은 이번 범위에 넣지 않았다.

## 5. 확인하지 않은 것

- 느린 PC, LAN의 다른 PC
- 실제 휴대폰 사진(HEIC 포함)과 실제 업무 Excel 파일 — 만든 파일로 시험했다
- 영양성분 가져오기의 브라우저 확인(자동 테스트만)
- 3단계의 화면 속도 측정(`baseline:perf`)은 다시 하지 않았다
- 검증은 두 번 중단됐다(PC 로그오프·절전, Windows 저장 공간 정리가 임시 폴더의 파일을 삭제). 임시 DB와 의존성을 다시 만들어 남은 항목을 실행했다
