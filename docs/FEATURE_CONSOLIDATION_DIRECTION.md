# 기능 통합 방향 정리

작성: 2026-06-15  
상태: 방향 정리  
관련 문서: `docs/MENU_MASTER_UNIFICATION_PLAN.md`

---

## 1. 통합 원칙

앱 구조는 **입력/관리 화면은 통합**하고, **분석/보고/출력 화면은 분리 유지**하는 방향으로 정리한다.

```text
입력/관리 화면 = 통합
분석/보고/출력 화면 = 유지
```

사용자가 데이터를 새로 입력하거나 수정하는 기준 화면은 줄이고, 계산 결과나 보고서를 확인하는 화면은 목적별로 유지한다.

---

## 2. 최종 큰 구조

모든 영역은 브랜드별로 완전히 분리한다. 브랜드를 전환하면 메뉴, 레시피, 식자재, 단가, 영양/표기, 판매량, 노트, 백업/복원 대상도 함께 바뀐다.

```text
메뉴관리
 └─ 메뉴 + 레시피 + 원가 입력

식자재관리
 └─ 식자재 + 단가 + 원산지 + 알레르기 + 사용현황

제때데이터
 └─ 단가 업로드 + 출고량 + 관리품목

판매량관리
 └─ 업로드 + 미매칭 + 순위/비교

표기정보/영양
 └─ 영양성분 + 원산지/알레르기 확인 + 표 출력

보고서센터
 └─ 결과 보고서

메뉴개발노트
 └─ 개발 기록
```

## 3. 1순위: 메뉴관리 통합

### 3.1 통합 대상

```text
메뉴마스터
레시피마스터
원가레시피
```

위 세 기능은 사용자 관점에서 모두 "메뉴 하나를 만들고, 그 메뉴의 레시피와 원가를 관리하는 일"에 속한다.

### 3.2 목표 구조

```text
메뉴관리
 ├─ 메뉴 기본정보
 ├─ 판매가
 ├─ 레시피
 ├─ 원가 계산
 └─ 영양/원산지/알레르기 연결 상태
```

### 3.3 방향

- `메뉴마스터`를 단일 진입점으로 둔다.
- 메뉴 상세 안에서 레시피 입력과 원가 계산을 처리한다.
- `레시피마스터`는 메뉴 상세의 레시피 영역으로 흡수한다.
- `원가레시피`는 제거하거나 공통묶음/엣지 관리만 남긴다.
- `원가마진표`는 입력 화면이 아니라 결과 분석 화면이므로 별도 유지한다.

### 3.4 세부 계획

세부 구현 계획은 `docs/MENU_MASTER_UNIFICATION_PLAN.md`를 기준으로 한다.

## 4. 2순위: 식자재관리 통합

### 4.1 통합 대상

```text
식자재 관리
식자재 리스트
제품별 사용현황
재료 단가표
원산지 입력
알레르기 입력
```

현재 식자재는 `cost_ingredients`를 중심으로 기본정보, 제품코드, 기준수량, 수동단가, 원산지, 알레르기 정보가 같이 관리된다.

따라서 DB를 억지로 합치는 것보다, **식자재 상세 화면 하나로 화면 흐름을 통합**하는 것이 자연스럽다.

### 4.2 목표 구조

```text
식자재관리
 ├─ 기본정보
 ├─ 제때 단가/개당 단가
 ├─ 원산지
 ├─ 알레르기
 └─ 사용 메뉴
```

### 4.3 방향

- `식자재 관리`를 단일 진입점으로 둔다.
- 식자재 상세 안에서 단가, 원산지, 알레르기, 사용 메뉴를 확인/수정한다.
- `식자재 리스트`는 식자재관리의 보기 모드로 흡수한다.
- `제품별 사용현황`은 전체 분석 화면으로는 남길 수 있지만, 식자재 상세 안에도 "사용 메뉴"로 포함한다.
- `재료 단가표`는 원가계산 아래 독립 메뉴보다 식자재관리의 단가 탭에 더 가깝다.
- 단, `제때 가격 업로드` 자체는 제때데이터 쪽에 남긴다.
- 제때에 없는 품목은 식자재 수동 단가를 사용한다.

## 5. 3순위: 표기정보/영양 재정리

### 5.1 현재 성격

영양성분, 원산지, 알레르기는 모두 출력/표기와 연결된다. 다만 입력 원본은 서로 다르다.

```text
영양성분 입력 원본 = 영양성분 화면
원산지 입력 원본 = 식자재
알레르기 입력 원본 = 식자재
출력 결과 = 영양/원산지/알레르기 표 출력
```

영양성분은 메뉴 기준 직접 입력값을 최우선으로 하며, 식자재 영양값 자동계산은 제거한다.

원산지와 알레르기는 식자재에 입력된 정보를 레시피 기준으로 모아 출력한다. 기본 메뉴는 `displayGroupKey`로 단일 출력하되, 엣지처럼 옵션별 알레르기가 달라지는 경우에는 `메뉴명 + 엣지명` 파생 출력행을 별도로 만든다.

영양성분은 기본 메뉴 값을 직접 입력하고, 관리 대상 엣지 2종만 사이즈별 조정값을 입력한다. 엣지 파생 영양성분은 `기본 메뉴 영양성분 + 엣지 조정값`으로 만들고, 출력명은 `메뉴명 + 엣지명`을 사용한다.

### 5.2 목표 구조

```text
표기정보/영양
 ├─ 영양성분 입력
 ├─ 엣지 2종 사이즈별 영양 조정값
 ├─ 파생 메뉴/토핑/세트 계산
 ├─ 원산지 확인
 ├─ 알레르기 확인
 ├─ 엣지 파생 알레르기 확인
 └─ 표 출력
```

### 5.3 방향

- 원산지와 알레르기 입력은 식자재 상세에서 관리한다.
- 원산지와 알레르기의 메뉴별 확인/출력은 표기정보/영양 쪽에 유지한다.
- 영양성분 입력, 토핑, 파생 메뉴, 세트 계산은 표기정보/영양 쪽에 유지한다.
- 엣지 2종의 사이즈별 영양 조정값은 직접 입력/검수하며, 식자재 영양값으로 자동 계산하지 않는다.
- 엣지 파생 메뉴의 알레르기는 기본 메뉴 레시피와 해당 엣지 레시피의 식자재 알레르기를 합산해 출력한다.
- 식자재 영양값 기반 자동계산은 제거한다.
- 표 출력은 별도 결과 화면으로 유지한다.

## 6. 4순위: 제때데이터 정리

### 6.1 통합 대상

```text
제때 가격 비교
제품 출고량
제때 설정
관리품목 설정
```

### 6.2 목표 구조

```text
제때데이터
 ├─ 단가 업로드/비교
 ├─ 출고량 업로드/집계
 └─ 관리품목 설정
```

### 6.3 방향

- 제때는 식자재와 완전히 합치지 않는다.
- 제때는 식자재 단가의 **원천 데이터**로 둔다.
- 제때 단가를 업로드하면 식자재관리의 단가 탭에서 최신 단가가 반영된다.
- 제때 최신 단가가 없는 식자재는 식자재 수동 단가를 사용한다.
- 제때 출고량은 제때데이터 안에서 유지한다.
- 운영 정책성 설정은 가능하면 시스템 설정으로 옮기고, 제때 화면에는 관리품목 설정 중심으로 남긴다.

## 7. 5순위: 판매량관리 정리

### 7.1 현재 구조

```text
판매량 업로드
미매칭 관리
순위 및 비교
기간 비교
판매 순위표
분류 규칙
```

### 7.2 목표 구조

```text
판매량관리
 ├─ 업로드
 ├─ 미매칭 정리
 └─ 순위/비교
```

### 7.3 방향

- 판매량은 이미 큰 그룹으로는 잘 묶여 있다.
- 다만 `rank`, `compare`, `rank-compare`처럼 비슷한 분석 화면은 하나로 줄일 수 있다.
- 사용 흐름은 "업로드 → 미매칭 정리 → 분석" 순서로 보이게 한다.
- 분류 규칙은 판매량관리 안에 유지하되, 가능하면 미매칭 정리 흐름과 자연스럽게 연결한다.

## 8. 합치지 않는 것이 좋은 영역

아래 기능은 성격상 독립 유지가 좋다.

```text
메뉴개발노트
보고서센터
홈 대시보드
시스템/백업/계정 설정
```

### 8.1 메뉴개발노트

- 운영 기준 데이터가 아니라 개발 기록과 아이디어 관리 성격이다.
- 메뉴관리와 연결은 가능하지만, 화면 자체는 독립 유지가 좋다.

### 8.2 보고서센터

- 보고서센터는 입력 화면이 아니라 결과물을 모아 보는 곳이다.
- 각 관리 화면과 합치지 않고 별도 유지한다.

### 8.3 홈 대시보드

- 홈은 전체 상태 요약 역할이다.
- 데이터 입력 기능을 직접 흡수하지 않는다.

### 8.4 시스템/백업/계정 설정

- 운영 권한, 백업, 복원, 시스템 정책은 기능 입력 화면과 분리한다.

## 11. 완료 판단 기준

- 메뉴 생성과 레시피 입력의 진입점이 하나다.
- 식자재 기본정보, 단가, 원산지, 알레르기, 사용 메뉴가 한 식자재 상세에서 이어진다.
- 제때 단가는 원천 데이터로 남고, 식자재 단가 화면에서 결과를 확인한다.
- 제때에 없는 식자재는 수동 단가로 원가 계산된다.
- 영양성분은 메뉴 기준 직접 입력값을 사용하고, 식자재 영양값 자동계산에 의존하지 않는다.
- 판매량은 업로드 후 미매칭 정리와 분석으로 자연스럽게 이어진다.
- 보고서와 출력 화면은 입력 화면과 섞이지 않는다.
- 사이드바에서 비슷한 기능이 중복 카드처럼 보이지 않는다.
- 모든 운영 데이터가 브랜드별로 분리되어, 다른 브랜드의 메뉴/레시피/단가/출력 데이터와 섞이지 않는다.
- 레시피 입력 단위는 `g`, `개` 두 가지만 사용한다.

## 12. 작업 전 확인사항과 안전장치

### 12.1 데이터 보존/초기화 정책

- 기존 데이터는 가능하면 살린다.
- 다만 구형 레시피, 중복 레시피, 기준이 맞지 않는 영양/원가 데이터처럼 새 기준과 충돌하는 데이터는 초기화할 수 있다.
- 초기화가 필요한 경우에는 먼저 백업을 만들고, 초기화 범위를 명확히 기록한다.
- 초기화 우선순위는 "전체 초기화"가 아니라 문제가 되는 도메인만 부분 초기화하는 방식이다.

작업 전 백업 대상은 브랜드 단위로 분리해서 만든다. 전체 백업을 만들더라도 복원 시에는 브랜드별 복원 범위를 선택할 수 있어야 한다.

작업 전 백업 대상:

| 영역 | 백업 대상 |
|------|-----------|
| 메뉴 | `menu_master`, `cost_selling_prices` |
| 레시피/원가 | `cost_recipes`, `cost_pizza_detail`, `cost_personal_detail`, `cost_side_detail`, `cost_set_detail`, `cost_edge_dough`, `cost_recipe_groups` |
| 식자재 | `cost_ingredients`, `cost_suppliers`, `cost_ingredient_price_history` |
| 제때 | `price_files`, `price_rows`, `shipment_files`, `shipment_rows`, `ref_shipment_products` |
| 영양/표기 | `nutrition_menu_ref`, `nutrition_raw_values`, `nutrition_pizza_composition`, `nutrition_topping_master`, `nutrition_edge_master`, `nutrition_set_composition` |
| 판매량 | `sales_files`, `sales_rows`, `menu_sales_issues`, `sales_rules`, `ref_sales_aliases` |
| 설정 | localStorage 기반 설정과 백업/복원 대상 설정 |

초기화 후보:

| 후보 | 기준 |
|------|------|
| 구형 레시피 | 새 `menu_recipes` 기준과 충돌하거나 품질이 낮으면 초기화 |
| 식자재 영양값 자동계산 데이터 | 메뉴 직접 입력 영양성분 정책으로 전환 후 미사용 처리 |
| 중복 메뉴/레시피 | 자동 병합이 위험하면 백업 후 초기화 |

### 12.2 안전한 route 정리

- 기존 route는 바로 삭제하지 않는다.
- 1차로 기존 route를 새 화면으로 redirect하거나 안내 화면으로 바꾼다.
- 사이드바에서 먼저 중복 메뉴를 제거한 뒤, 실제 route 삭제는 마지막 단계에서 진행한다.
- 북마크나 내부 링크가 깨지는지 smoke 확인 후 제거한다.

추천 route 처리:

| 현재 route | 추천 처리 |
|------------|-----------|
| `/menu-master` | 유지, 메뉴관리 메인으로 확장 |
| `/cost/recipe-master` | `/menu-master`의 레시피 영역으로 redirect |
| `/cost/recipe` | 공통묶음/엣지 관리가 남기 전까지 안내/redirect, 최종적으로 축소 |
| `/cost/pizza` | `/menu-master` 또는 원가마진표 상세 필터로 redirect |
| `/cost/personal` | `/menu-master` 또는 원가마진표 상세 필터로 redirect |
| `/cost/side` | `/menu-master` 또는 원가마진표 상세 필터로 redirect |
| `/cost/set` | `/menu-master` 또는 원가마진표 상세 필터로 redirect |
| `/cost/margin` | 유지, 결과 분석 화면 |
| `/cost/ingredient-price` | 식자재관리 단가 탭으로 흡수 후 redirect |
| `/ingredient/manage` | 식자재관리 메인으로 유지 |
| `/ingredient/list` | 식자재관리 보기 모드로 흡수 후 redirect |
| `/ingredient/usage` | 전체 분석은 유지 가능, 식자재 상세 사용 메뉴와 연결 |

### 12.3 작업 단위와 커밋 전략

작업은 아래 순서로 나누어 커밋한다.

1. 문서/정책 정리
2. 새 데이터 기준 추가
3. 메뉴관리 UI 통합
4. 원가 계산 연결
5. 원산지/알레르기/영양 출력 연결

각 커밋은 한 가지 목적만 담고, 기존 사용자 변경과 섞지 않는다.

### 12.4 QA 확인 기준

최소 확인 샘플은 아래를 포함한다.

- 피자 L/R 메뉴: 원가와 영양은 사이즈별, 원산지/알레르기는 단일 출력
- 사이드 메뉴: 원가, 원산지, 알레르기, 영양 출력
- 세트 메뉴: 구성품 기준 원가와 출력 영향
- 제때 연동 식자재: 최신 제때 단가 반영
- 제때 미연동 식자재: 수동 단가 반영
- 메뉴 영양성분 직접 입력값: 최종 출력 우선 적용
- 엣지 파생 메뉴: `메뉴명 + 엣지명`으로 영양성분과 알레르기 출력

### 12.5 권한/역할 추천

통합 화면은 한 화면에 여러 기능이 모이므로, 버튼/탭 단위 권한을 나눈다.

| 역할 | 허용 |
|------|------|
| 관리자 | 메뉴, 레시피, 판매가, 식자재, 단가, 영양, 원산지, 알레르기, 설정 전체 |
| R&D | 메뉴, 레시피, 원가 확인, 영양성분 입력, 원산지/알레르기 확인 |
| 운영/구매 | 식자재, 제때 단가, 출고량, 수동 단가, 원산지/알레르기 입력 |
| 조회자 | 모든 화면 조회만 가능, 저장/삭제/초기화 불가 |

위 역할명이 실제 계정 역할과 다르면 기존 역할 체계에 매핑한다. 핵심은 조회자에게 저장/삭제/초기화 버튼이 노출되지 않는 것이다.

### 12.6 브랜드 분리 정책

브랜드는 별도 사업/운영 단위로 보고, 모든 실사용 데이터는 `brandId` 범위 안에서만 연결한다.

| 영역 | 정책 |
|------|------|
| 메뉴 | `brandId + menuCode` 기준으로 고유 관리 |
| 레시피 | `brandId + menuCode` 기준으로 1개 레시피 관리 |
| 원산지/알레르기 | `brandId + displayGroupKey` 기준으로 단일 출력 |
| 영양성분 | 브랜드별 메뉴/사이즈 기준 직접 입력 |
| 식자재/단가 | 브랜드별 식자재와 제때/수동 단가 연결 |
| 판매량 | 브랜드별 업로드, 미매칭, 분석 |
| 메뉴개발노트 | 브랜드별 기록으로 분리 |
| 설정/백업 | 브랜드별 백업/복원 범위 선택 |

브랜드 간 데이터 공유는 기본 기능으로 두지 않는다. 필요한 경우에는 다른 브랜드로 복사해 새 데이터로 생성하고, 원본과 연결하지 않는다.

### 12.7 단위 정책

레시피 입력 단위는 `g`, `개` 두 가지만 허용한다.

| 단위 | 의미 |
|------|------|
| `g` | 중량 기준 식자재 |
| `개` | 낱개/장/봉/통처럼 개수 기준 식자재 |

제때 또는 구매 데이터의 단위가 `kg`, `ml`, `L`, `ea` 등으로 들어오면 식자재 기준수량에서 `g` 또는 `개`로 환산한다. 환산이 불가능한 식자재는 원가 계산/발행 전에 단위 미확정으로 막는다.
