# 사이트 편의성·추가 기능 실행 플랜

기준일: 2026-06-22

이 문서는 사이트에 추가하면 좋은 편의 기능과 보완 기능을 Claude Code가 단계별로 구현하고, Codex가 검수하기 위한 실행 계획이다. 더 넓은 후보 설명은 `docs/CONVENIENCE_FEATURE_ROADMAP.md`, 세부 아이디어 기록은 `docs/CONVENIENCE_FEATURE_IMPLEMENTATION_PLAN.md`를 참고하되, 실제 착수 순서는 이 문서를 우선한다.

## 1. 최종 방향

현재 사이트는 메뉴마스터, 식자재관리, 원가계산, 영양성분, 판매량, 제때데이터, 보고서, 노트, 설정 기능이 이미 넓게 구현되어 있다. 다음 단계는 새 기능을 무작정 늘리기보다 아래 세 가지에 집중한다.

1. 원하는 데이터까지 더 빨리 이동한다.
2. 메뉴 저장, 식자재 수정, 출력 전 실수를 줄인다.
3. 반복 조회와 보고 업무를 한곳에서 처리한다.

외부 서비스 연동, 서버 DB 전환, 원격 백업은 이번 문서 범위에서 제외한다. 내부 운영툴 기준의 편의성, 안정성, 반복 업무 단축을 우선한다.

## 2. 협업 방식

모든 단계는 아래 순서로 진행한다.

1. Claude 1차: 현재 코드 확인, 구현, targeted test, 자체 버그 탐색.
2. Codex 1차: diff, 테스트 결과, 실제 동작, 정책 일치 여부 검수.
3. Claude 2차: Codex 지적사항만 좁게 보완.
4. Codex 2차: 최종 검수 후 `승인 / 조건부 승인 / 수정 필요 / 검증 불가` 판정.
5. 단계가 green일 때만 커밋하고 다음 단계로 이동한다.

각 단계는 `구현 -> 테스트/검사/버그탐색 -> 사이트 확인 -> 한 번 더 검증 -> 커밋 -> 다음 단계` 순서로 닫는다.

## 3. 공통 원칙

1. 현재 작업트리에 미커밋 변경이 많으므로 기존 변경을 되돌리거나 덮어쓰지 않는다.
2. 기능별 커밋 단위를 작게 유지한다.
3. 사용자 데이터 삭제, DB 초기화, 대량 복원, 자동 병합, 실제 undo는 사용자 승인 전까지 만들지 않는다.
4. 관리자 전용 작업은 UI 제한뿐 아니라 store/helper 레벨에서도 권한 가드를 확인한다.
5. 브랜드별 데이터가 섞이지 않도록 모든 저장값과 진단값에 브랜드 범위를 확인한다.
6. 기능명이 실제 동작보다 과장되면 안 된다. 예를 들어 월마감 기능이 실제 zip 생성이 아니라면 체크리스트와 생성 기록 기능으로 표시한다.
7. 문서와 코드가 다르면 코드 동작을 기준으로 문서를 갱신한다.

## 4. 우선순위 요약

| 순서 | 단계 | 목표 | 사용자 가치 |
|---:|---|---|---|
| 0 | 기준선·충돌 감사 | 현재 미커밋 변경, 테스트 수치, 구현 토대 확인 | 중복 구현과 회귀 방지 |
| 1 | 빠른 이동·검색 | 검색 결과에서 실제 수정 위치로 이동 | 다시 찾는 시간 감소 |
| 2 | 저장 전 실수 방지 | 메뉴 출시 준비와 식자재 변경 영향을 미리 확인 | 저장 후 수정 작업 감소 |
| 3 | 입력 속도 개선 | 메뉴·레시피·식자재 입력을 키보드 중심으로 빠르게 처리 | 반복 입력 시간 감소 |
| 4 | 오늘 할 일 통합 | 홈과 상단에서 처리할 일을 한 번에 확인 | 여러 화면 이동 감소 |
| 5 | 반복 업무 저장 | 자주 쓰는 필터, 보고 흐름, 월마감 흐름 저장 | 반복 조회 시간 감소 |
| 6 | 데이터 품질 점검 | 누락, 중복, 이상값을 한 화면에서 확인 | 운영 데이터 신뢰도 향상 |
| 7 | 현장 확인·감사 | 모바일 확인과 변경 이력 기록 | 매장 확인과 추적 안정화 |

## 5. 현재 코드 토대 확인 대상

Claude Code는 새로 만들기 전에 아래 파일들이 이미 동작하는지 먼저 판정한다.

| 기능 | 확인 대상 | 판정 기준 |
|---|---|---|
| 업무 액션 센터 | `components/action-center/`, `lib/action-center/`, `components/home/ActionCenterWidget.jsx` | 홈과 TopBar가 같은 builder를 쓸 수 있는지 |
| 메뉴 출시 체크리스트 | `components/menu-master/MenuReadinessPanel.jsx`, `lib/menu-master/readiness.js` | 메뉴 유형별 누락 기준이 맞는지 |
| 식자재 변경 영향도 | `components/impact/`, `lib/impact/` | 저장 전 preview와 저장 후 결과가 일치하는지 |
| 저장된 필터·뷰 | `components/ui/SavedViewSelector.jsx`, `lib/saved-views.js` | 브랜드별 저장과 손상값 fallback이 되는지 |
| 월마감 패키지 | `components/report/MonthlyClosePackageModal.jsx`, `lib/report/package-plan.js` | 체크리스트/생성 기록 중심인지 |
| 변경 이력 | `components/change-log/`, `lib/change-log/` | 1차 기록 전용이며 undo가 섞이지 않았는지 |
| 커맨드 팔레트 | `components/CommandPalette.jsx`, `hooks/usePaletteItems.js` | 검색 결과 deep link와 fallback이 되는지 |

각 항목은 `사용 중`, `부분 구현`, `미연결`, `보류`로 분류하고, 부족한 테스트와 화면 확인 항목을 기록한다.

## 6. 단계별 작업 계획

### 0단계. 기준선·충돌 감사

작업 목표:

- 현재 작업트리와 테스트 기준선을 먼저 고정한다.

요구사항:

1. `git status --short`로 변경 범위를 확인한다.
2. 새 작업으로 건드릴 파일과 이미 변경되어 있는 파일을 구분한다.
3. `docs/SITE_STATUS.md`의 테스트 수치와 실제 기준선이 맞는지 확인한다.
4. 실패 중인 테스트가 있으면 새 기능 구현 전에 원인과 영향 범위를 기록한다.

완료 기준:

- 기존 변경을 되돌리지 않는다.
- 이번 단계에서 새로 수정한 파일이 명확히 구분된다.
- 기준 테스트와 문서 수치 불일치가 있으면 먼저 정리한다.

### 1단계. 빠른 이동·검색

작업 목표:

- 커맨드 팔레트와 검색 결과에서 식자재, 메뉴, 이슈의 실제 수정 위치까지 바로 이동하게 한다.

요구사항:

1. 식자재 검색 결과는 `/ingredient/manage`에서 검색어 적용, 대상 행 페이지 이동, 스크롤, 하이라이트를 처리한다.
2. 메뉴 검색 결과는 메뉴마스터에서 해당 메뉴 수정창 또는 행 위치로 이동한다.
3. 가능하면 `id`, `productCode`, `menuCode`, `query` fallback을 함께 지원한다.
4. 삭제된 대상, 다른 브랜드 대상, 잘못된 URL 파라미터는 일반 목록으로 fallback한다.
5. 이동 후 하이라이트는 2~3초 뒤 자연스럽게 사라진다.

수정 대상 후보:

- `hooks/usePaletteItems.js`
- `components/CommandPalette.jsx`
- `app/ingredient/manage/page.jsx`
- `app/menu-master/page.jsx`
- `components/ingredient/ManageRow.jsx`

테스트:

- URL 파라미터 구조 테스트.
- 삭제된 대상 fallback 테스트.
- 브랜드 불일치 fallback 테스트.
- 가능하면 Playwright로 식자재관리와 메뉴마스터 진입 확인.

완료 기준:

- 검색 결과 클릭 후 추가 검색 없이 대상 행이나 수정 위치가 보인다.
- 잘못된 파라미터로 화면이 깨지지 않는다.

### 2단계. 저장 전 실수 방지

작업 목표:

- 메뉴 출시 전 누락과 식자재 변경 영향을 저장 전에 확인한다.

요구사항:

1. 메뉴 출시 체크리스트는 판매가, 레시피, 수량, 단가, 원산지, 알레르기, 영양성분, 표출력 가능 여부를 진단한다.
2. 피자 L/R, 세트박스, 단일, 1인피자, 사이드, 소스, 음료, 엣지 기준을 섞지 않는다.
3. 원산지와 알레르기는 메뉴 단위로, 원가와 영양성분은 필요한 경우 사이즈 단위로 판단한다.
4. 공통원가가 포함된 메뉴를 수량 누락으로 오탐하지 않는다.
5. 식자재 단가, 원산지, 알레르기 변경 시 영향 메뉴와 출력물 영향을 preview로 보여준다.
6. preview 값은 저장 후 실제 계산 결과와 일치해야 한다.

수정 대상 후보:

- `lib/menu-master/readiness.js`
- `components/menu-master/MenuReadinessPanel.jsx`
- `components/impact/ImpactPreviewPanel.jsx`
- `lib/impact/ingredient-impact.js`
- `app/ingredient/manage/IngredientForm.jsx`

테스트:

- 메뉴 유형별 readiness 테스트.
- 공통원가 포함 메뉴의 수량 누락 오탐 방지 테스트.
- 식자재 변경 영향 preview와 실제 저장 결과 일치 테스트.
- 원산지/알레르기 출력 영향 테스트.

완료 기준:

- 체크리스트 이슈가 실제 저장/출력 결과와 맞는다.
- 이슈별 수정 링크가 실제 수정 화면으로 이동한다.

### 3단계. 입력 속도 개선

작업 목표:

- 메뉴마스터와 식자재관리 입력 흐름을 키보드와 재사용 중심으로 빠르게 만든다.

요구사항:

1. 레시피 구성품 검색은 Enter, Tab, 방향키로 선택과 이동이 가능해야 한다.
2. 구성품 행 복사, 위/아래 이동, 빠른 삭제를 제공한다.
3. 규격은 드롭다운과 직접 입력을 모두 지원한다.
4. 같은 메뉴 L/R 또는 비슷한 메뉴에서 레시피를 복사할 수 있게 한다.
5. 별도 레시피 저장 버튼 없이 메뉴 저장 하나로 기본정보와 레시피가 함께 저장되는 흐름을 유지한다.
6. 식자재관리 입력창은 기본정보, 단가, 규격, 원산지, 알레르기, 사진, 사용현황 순서가 실제 입력 흐름에 맞아야 한다.

수정 대상 후보:

- `app/menu-master/page.jsx`
- `components/menu-master/MenuMasterDialogs.jsx`
- `components/menu-master/recipeComponentRows.js`
- `components/cost/shared/IngredientSearch.jsx`
- `app/ingredient/manage/IngredientForm.jsx`
- `app/ingredient/manage/IngredientFormSections.jsx`

테스트:

- 키보드 입력 구조 테스트.
- 메뉴 저장 시 레시피 동시 저장 회귀 테스트.
- 중복 구성품, 단가 없음, 수량 없음 경고 테스트.
- 식자재 폼 필수 입력/빈 상태 테스트.

완료 기준:

- 마우스 없이 기본 레시피 구성품 입력 흐름이 가능하다.
- 저장 전 경고가 `수량`, `단가`, `중복`, `공통원가`, `판매가`를 구분한다.

### 4단계. 오늘 할 일 통합

작업 목표:

- 홈, 상단 알림, 진단 화면의 처리할 일을 같은 기준으로 보여준다.

요구사항:

1. action item builder를 한곳으로 정리한다.
2. 홈 위젯과 TopBar 알림이 같은 action builder를 사용한다.
3. 미매칭 메뉴, 단가 없음, 오래된 업로드, 백업 권장, 출시 준비 이슈를 포함한다.
4. `완료`, `나중에`, `숨김`은 원본 데이터를 바꾸지 않는 local state로 관리한다.
5. 원인 데이터가 해결되면 action은 자동으로 사라진다.
6. viewer 권한에서는 수정 action 대신 확인용 이동 또는 tooltip을 제공한다.

수정 대상 후보:

- `lib/action-center/`
- `components/action-center/ActionCenterPanel.jsx`
- `components/home/ActionCenterWidget.jsx`
- `components/TopBar.jsx`
- `app/page.jsx`

테스트:

- action id 안정성 테스트.
- 원인 해결 후 자동 제거 테스트.
- 숨김/나중에 local state 테스트.
- viewer 권한 표시 테스트.

완료 기준:

- 홈과 TopBar 숫자가 같은 기준으로 표시된다.
- action 클릭 시 실제 수정 화면 또는 필터 상태로 이동한다.

### 5단계. 반복 업무 저장

작업 목표:

- 자주 쓰는 필터와 월별 보고 흐름을 저장하고 재사용한다.

요구사항:

1. 저장된 필터·뷰를 식자재관리 적용 상태부터 점검한다.
2. 원가마진표, 메뉴판매량, 보고서 목록, 노트 목록 순으로 확산한다.
3. 브랜드별 저장, 기본 뷰, 이름 변경, 삭제를 지원한다.
4. 손상된 localStorage 값은 화면을 깨뜨리지 않고 기본값으로 복구한다.
5. 월마감은 기준월과 브랜드를 선택하고, 판매량/원가/단가/출고량/원산지/알레르기/영양성분 출력 준비 상태를 보여준다.
6. 1차 월마감은 실제 zip 자동 생성이 아니라 체크리스트와 생성 기록 중심으로 둔다.

수정 대상 후보:

- `lib/saved-views.js`
- `components/ui/SavedViewSelector.jsx`
- `app/cost/margin/page.jsx`
- `app/menu-sales/page.jsx`
- `components/report/MonthlyClosePackageModal.jsx`
- `lib/report/package-plan.js`

테스트:

- 브랜드별 저장/조회/삭제 테스트.
- 손상된 localStorage fallback 테스트.
- 월마감 체크리스트 기준 테스트.
- 생성 기록과 실제 출력 가능 상태 불일치 방지 테스트.

완료 기준:

- 브랜드를 바꿔도 저장된 뷰가 섞이지 않는다.
- 월마감 UI가 실제 기능 범위를 과장하지 않는다.

### 6단계. 데이터 품질 점검

작업 목표:

- 운영 데이터의 누락, 중복, 이상값을 한 화면에서 확인하고 수정 위치로 이동한다.

요구사항:

1. 메뉴, 레시피, 식자재, 단가, 판매량, 영양성분, 원산지, 알레르기 진단을 묶는다.
2. 중복 코드, 중복 이름 의심, 단가 없음, 기준수량 누락, 메뉴 가격 없음, 레시피 없음, 영양성분 누락, 출력 불가 상태를 표시한다.
3. 각 이슈는 심각도, 영향 범위, 수정 링크를 가진다.
4. action-center, readiness, impact 계산 로직을 재사용한다.
5. 빈 DB와 다른 브랜드 전환에서 화면이 깨지지 않아야 한다.

수정 대상 후보:

- `lib/action-center/`
- `lib/menu-master/readiness.js`
- `lib/impact/ingredient-impact.js`
- 새 quality builder/helper
- 홈 또는 설정/진단 화면

테스트:

- 빈 DB 테스트.
- 브랜드 전환 테스트.
- 중복 코드/중복 이름 테스트.
- 단가 없음/레시피 없음/영양성분 누락 테스트.

완료 기준:

- 데이터 품질 점검판과 액션 센터 숫자가 서로 다르게 나오지 않는다.
- 모든 이슈가 수정 가능한 위치로 연결된다.

### 7단계. 현장 확인·감사

작업 목표:

- 매장에서는 확인용 정보를 빠르게 보고, 관리자는 변경 이력을 추적한다.

요구사항:

1. 모바일 확인 모드는 원산지, 알레르기, 영양성분, 판매가를 빠르게 확인하는 읽기 중심 흐름으로 만든다.
2. 390px 화면에서 핵심 정보가 겹치지 않아야 한다.
3. 출력 기준과 현장 확인 기준은 같은 builder를 사용한다.
4. 변경 이력은 1차 기록 전용으로 시작한다.
5. 식자재 저장/삭제/일괄변경, 메뉴 저장/삭제, 레시피 저장, 판매량/제때 업로드, 백업/복원을 기록한다.
6. 실제 undo 기능은 사용자 승인 전까지 보류한다.

수정 대상 후보:

- `components/change-log/`
- `lib/change-log/`
- 원산지/알레르기/영양성분 조회 화면
- `scripts/mobile-qa.mjs`

테스트:

- `npm run qa:mobile`
- 변경 이력 기록 테스트.
- viewer 권한 표시 테스트.
- 관리자 확인 절차 테스트.

완료 기준:

- 모바일 390px에서 핵심 정보가 3터치 이내 접근 가능하다.
- 변경 이력은 기록 전용이며 실제 데이터 복구 기능을 실행하지 않는다.

## 7. 각 단계 공통 테스트

최소 실행:

```sh
npm run format:check
npm run lint
git diff --check
```

기능별 targeted Jest 테스트를 반드시 추가하거나 갱신한다.

화면 변경이 있는 경우:

```sh
npm run qa:smoke
npm run qa:mobile
```

메뉴마스터, 식자재관리, 백업/복원, 업로드 흐름이 바뀌는 경우:

```sh
npm run qa:workflow
```

문서 수치가 바뀌면:

```sh
npm run audit:docs
```

## 9. Codex 검수 기준

Codex는 Claude Code의 완료 보고만 믿지 않고 아래를 직접 확인한다.

1. 요구사항 일치
   - 사용자가 요청한 기능이 실제 동작하는가.
   - 일부 요구사항이 빠지지 않았는가.
   - 요청하지 않은 위험한 동작 변경이 없는가.
2. 데이터 안전
   - 브랜드별 데이터가 섞이지 않는가.
   - viewer 권한에서 편집, 삭제, 복원, 되돌리기가 막히는가.
   - 임시 단가와 식자재 원본 단가 의미가 섞이지 않는가.
3. 기능 정확성
   - 빈 DB, 잘못된 URL, 삭제된 대상, 손상된 localStorage에서 깨지지 않는가.
   - 저장 전 preview와 저장 후 실제 결과가 일치하는가.
   - 메뉴 L/R, 단일, 1인피자, 사이드, 소스, 음료, 엣지가 섞이지 않는가.
4. UX와 접근성
   - 긴 메뉴명, 긴 원산지, 다수 알레르기 표시가 겹치지 않는가.
   - 키보드만으로 핵심 입력 흐름이 가능한가.
   - 오류와 빈 상태 메시지가 사용자가 이해할 수 있는가.
5. 테스트 신뢰도
   - 새 테스트가 단순 import 검사에 그치지 않고 실제 정책을 검증하는가.
   - 화면 동작은 수동 확인 또는 Playwright QA 결과가 있는가.
   - 테스트 수치가 바뀌면 `docs/SITE_STATUS.md`가 갱신되었는가.

판정은 `승인`, `조건부 승인`, `수정 필요`, `검증 불가` 중 하나로 남긴다.

## 10. 보류 항목

아래는 사용자가 명확히 승인하기 전까지 구현하지 않는다.

| 항목 | 보류 이유 | 추천 |
|---|---|---|
| 실제 undo 기능 | 데이터 복구 책임이 크고 정책 결정 필요 | 1차는 변경 이력 기록 전용 |
| 월마감 zip 자동 생성 | 다운로드 묶음, 파일명, 실패 처리 정책 필요 | 1차는 체크리스트와 생성 기록 |
| 과거 단가 원가 계산 반영 | 현재 원가 계산 기준을 바꾸는 정책 변경 | 1차는 조회 전용 또는 사용자 결정 후 진행 |
| 영양성분 일부 누락 출력 차단 | 운영 출력 흐름을 막을 수 있음 | 1차는 경고 표시, 차단은 사용자 결정 |
| 외부 서비스 연동 | 서버, 인증, 네트워크 정책 필요 | 별도 프로젝트 |
| 서버 DB 전환 | 저장 구조 전체에 영향 | `docs/LOCAL_DB_DEPLOY_PLAN.md`에서 관리 |

아래 블록은 1차 작업 시작 시 Claude Code에 그대로 전달한다.

```md
# 작업: 편의성 개선 1차

## 작업 목표
현재 작업트리에 이미 들어온 편의 기능 토대를 살리면서, 사용자가 바로 체감할 수 있는 빠른 이동과 저장 전 실수 방지 기능을 먼저 마감한다.

## 작업 순서
1. 기준선·충돌 감사
   - `git status --short`
   - 기존 변경 되돌림 금지
   - 현재 테스트 수치와 문서 수치 확인
2. 빠른 이동·검색
   - 식자재관리와 메뉴마스터 deep link 확인
   - 검색어 적용, 대상 행 스크롤, 하이라이트, fallback 구현
3. 저장 전 실수 방지
   - 메뉴 출시 체크리스트 기준 검증
   - 공통원가 수량 누락 오탐 제거
   - 식자재 변경 영향 preview와 저장 후 결과 일치 검증

## 변경 금지
- 사용자 데이터 삭제, DB 초기화, 대량 복원, 자동 병합 금지
- 실제 undo 기능 금지
- 외부 서비스 연동과 서버 DB 전환 금지

## 테스트
- 관련 targeted Jest 테스트
- `npm run format:check`
- `npm run lint`
- `git diff --check`
- 화면 변경 시 dev 서버에서 식자재관리와 메뉴마스터 실제 진입 확인

## 완료 보고
변경 파일, 구현 내용, 테스트 결과, 화면 확인 결과, 남은 위험, Codex 검수 요청 항목을 보고한다.
```
